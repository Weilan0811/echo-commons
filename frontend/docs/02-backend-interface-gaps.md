# 后端接口缺口清单

状态：规划，尚未实现。
更新日期：2026-10-03。
提交方：前端。
接收方：后端。

本文列出前端在建设用户端和管理员端时依赖、但当前 [HTTP 参考](../../server/docs/reference/http-api.md) 未提供的接口。每项按 [推进计划](../../docs/01-project-roadmap.md) 的要求说明操作范围、路径、请求、响应、可见范围与完成语义。

**本文不是已实现能力的清单。** 当前可用的接口只有 HTTP 参考第 2 节列出的那些，本文任何条目都不应被写入"当前公开接口"。

## 1. 背景

当前契约把 `player_id` 作为请求字段或查询参数由客户端提供，服务端据此判断读取或发送主体。这是本地测试期的形态，前端据此实现当前页面。

但现有接口缺少按玩家发现对象的入口：列会话和列角色都需要先有 `community_id`，而没有任何接口可以列出一个玩家加入了哪些社群，也没有接口可以读取该玩家的社群成员关系。多用户形态下，前端无法构建首页。

## 2. 优先级与影响

| 优先级 | 需求 | 影响 |
|---|---|---|
| P1 | 社群发现与成员关系读取 | 用户端第一版可以手工输入 `community_id` 绕过，但正式页面不可接受 |
| P1 | 玩家维度的会话列表 | 会话列表页无法按参与者过滤，需要前端加载全量后自行筛选 |
| P2 | 未读与最后消息摘要 | 多用户下没有通知入口，测试效率显著下降 |
| P2 | `401` / `403` 错误语义 | 没有凭据场景，无法表达身份问题 |
| P3 | 写入的乐观并发复核 | 多用户同时操作时前端无法区分冲突与失败 |
| P3 | 活动对象列表与读取 | 阶段五活动接入前需要，当前可延后 |

P1 影响用户端可用性，建议在用户端页面结构稳定后尽快确定；P2 应在真人多用户测试前完成；P3 随活动接入排期。

## 3. P1 社群发现与成员关系读取

### 操作范围

读取当前玩家的社群参与情况。用途是用户端首页、社群选择器，以及管理端按玩家定位社群。

### 建议路径

```text
GET /api/communities
GET /api/communities/{community_id}/membership
```

### 请求

`GET /api/communities` 无查询参数时，返回当前 `player_id` 加入的社群。玩家身份仍按现有形态由客户端提供（`player_id` 查询参数），待账户认证落地后改为服务端推导。

`GET /api/communities/{community_id}/membership` 用于读取该社群中当前玩家的成员关系。

### 响应

第一个接口返回 `CommunityView` 数组。若需要显示玩家与社群的关系状态，可为每个元素附带成员关系信息，或由第二个接口提供。

第二个接口返回 `MembershipView`，其结构与现有会话成员操作返回的 `MembershipView` 一致：包含 `membership_id`、`community_id`、`conversation_id`、`actor`、`joined_at_utc`、`left_at_utc`。若社群成员关系不与具体会话绑定，`conversation_id` 需要有明确取值规则，前端才能正确解析。

### 可见范围

只返回该玩家有权看到的社群和成员关系。

### 完成语义

读取操作，无副作用。玩家未加入该社群时返回 `404`，与现有业务对象不存在的处理一致。

### 需要后端明确的点

当前社群成员关系只在会话成员操作中被体现，没有独立的社群级成员记录和读取接口。`PUT /api/communities/{community_id}/players/{player_id}` 建立成员关系，但没有对应的读取路径。需要确认社群级成员关系是否作为独立事实保存，以及 `MembershipView` 是否适用于非会话范围。

## 4. P1 玩家维度的会话列表

### 操作范围

读取当前玩家参与并可见的会话。用于用户端会话列表。

### 建议路径

```text
GET /api/conversations
```

### 请求

`player_id` 必填。可选 `community_id` 限定范围。

### 响应

`ConversationView` 数组。此外前端列表需要展示最近一条消息摘要和未读状态，这两项由 P2 决定；P1 可先只返回 `ConversationView`，列表页暂不显示摘要。

### 可见范围

返回该玩家当前有效成员区间内的会话。玩家已离开的会话是否出现需要明确：建议不返回，或返回并附带成员状态，由前端决定是否灰显。

私有消息的存在不能通过会话列表泄露。列表项不包含其他参与者的私有消息内容。

### 完成语义

读取操作，无副作用。

### 与现有接口的关系

`GET /api/communities/{community_id}/conversations` 返回该社群全部会话，不按玩家过滤。前端可以自行筛选，但这会让每个页面重复实现过滤逻辑，且无法表达会话成员状态。建议提供玩家维度入口，而不是改变现有接口语义。

## 5. P2 未读与最后消息摘要

### 操作范围

维护并读取会话层面的未读标记和最近消息摘要。

### 建议路径

```text
GET  /api/conversations/{conversation_id}/state
PUT  /api/conversations/{conversation_id}/read
```

### 请求

读取与标记已读都需要 `player_id`。

### 响应

未读数量、最近一条可见消息的 `message_id` 和时间，以及可用于列表展示的摘要字段。

### 可见范围

未读数量按读取玩家分别计算。私有消息只对该玩家可见，不能影响其他参与者的未读数。摘要只能取该玩家可见的消息。

### 完成语义

标记已读为幂等操作，重复调用返回当前状态。

### 需要后端明确的点

当前消息读取是基于游标向前的增量读取，没有未读概念。契约中"合法私有缺口"说明序号可能不连续，因此未读不能简单用最大序号差计算。

## 6. P2 身份相关的错误语义

### 操作范围

后端引入凭据后，明确身份校验失败的错误形状。

### 现状

当前错误协议见 HTTP 参考第 5 节，只有 `400`、`404`、`409`、`422`、`500`、`503`，没有凭据缺失或无效的场景。

### 建议

| 情况 | 建议状态 | 说明 |
|---|---|---|
| 凭据缺失或无效 | `401` | 沿用 `{"error":{"code","message"}}` 结构 |
| 已认证但对对象无权限 | `404` | 不返回 `403`，避免暴露对象是否存在 |

`422` 保持 FastAPI 默认的 `detail` 数组，代码生成工具需要区分这两种形状。

### 前端约定

前端需要一处统一的错误归一入口，把 `401` 转为身份失效的界面提示，而不是在每个页面分别处理。该入口在选型中已经确定，手写请求层负责两种错误形状的归一。

### 完成语义

不适用。

## 7. P3 写入的乐观并发复核

### 操作范围

多用户同时操作同一对象时，让前端能区分"我的操作过期"与"操作失败"。

### 背景

`CommunityView` 已有 `state_version`，`ConversationView` 已有 `membership_version`。活动接入设计还要求活动状态版本复核。这些字段已经存在，但当前写入路径没有要求客户端提交期望版本。

### 建议

成员加入、离开等改变成员关系的写入操作，以及阶段五的活动操作，接收可选的期望版本；不匹配时返回 `409`，`code` 中区分版本冲突与当前的幂等内容冲突。

### 前端约定

前端将在统一位置处理 `409`：保留原输入，提示状态已变化并触发重新读取。不在页面各处内联重试。

### 完成语义

不匹配时不得产生任何写入。重复提交相同期望版本的操作返回原结果，不按冲突处理。

## 8. P3 活动对象读取

阶段五接入前需要，当前只登记范围，不在此确定路径。

需要前端能够：列出某社群的进行中活动、读取活动权威状态和状态版本、读取当前主体的观察视图（含私有手牌）、列出合法动作、提交动作、读取活动结果与来源。

完整设计见 [活动接入设计](../../server/docs/design/activity-integration.md)，其中 `create`、`observe`、`legal_actions`、`validate`、`apply`、`summarize` 已确定接口职责。

前端在 [ADR-0002](adr/0002-scene-rendering-as-view-layer.md) 约定：活动状态由服务端下发，渲染层只呈现，不回写。

## 9. 当前不需要的接口

以下内容前端不依赖，后端不需要为前端实现：

- 逐字输出或流式发言。当前为整体消息提交后轮询读取，前端不显示打字机效果。
- WebSocket 或 SSE 推送。当前轮询可完成真人聊天测试。
- 模型密钥、模型路由或供应商配置。前端不请求模型供应商。
- 玩家账户体系本身。`player_id` 到账户的映射由后端设计，前端只要求当前主体来源集中，见 [ADR-0001](adr/0001-identity-and-server-state-single-source.md)。
