# 后端接口缺口清单

状态：四项待实现（含视觉资产两项），其余已核对解决。
更新日期：2026-10-09。
提交方：前端。
接收方：后端。

本文只列两类内容：前端需要、但当前契约未提供的能力，以及需要后端作出决定的设计问题。已实现的能力见 [HTTP 参考](../../server/docs/reference/http-api.md) 与 [管理接口参考](../../server/docs/reference/management-api.md)，前端的适配方式记在 [前端状态](status.md) 与 [页面设计](03-page-design.md)。

每项按 [推进计划](../../docs/01-project-roadmap.md) 的要求说明操作范围、路径、请求、响应、可见范围与完成语义。

## 1. 契约基线

前端类型由 `server/docs/reference/openapi.json` 生成，核对时为 67 个路径（`/api` 33 个、`/internal` 34 个）、216 个 schema。本文所有字段说明以该文件为准，不在这里复制，避免两处说法不一致。

## 2. 缺口清单

| 优先级 | 需求 | 影响 | 章节 |
|---|---|---|---|
| P3 | 活动对象读取 | 阶段五接入前需要 | 3 |

## 3. 缺口详情

### 3.1 P3 活动对象读取

阶段五接入前需要，当前契约未提供任何活动端点。完整设计见 [活动接入设计](../../server/docs/design/activity-integration.md)。

需要前端能够列出进行中活动、读取权威状态与状态版本、读取当前主体的观察视图、列出合法动作、提交动作、读取结果与来源。

前端在 [ADR-0002](adr/0002-scene-rendering-as-view-layer.md) 约定：活动状态由服务端下发，渲染层只呈现，不回写。

### 3.2 P2 记忆索引端点响应缺类型定义

#### 现状

`GET /internal/characters/{character_id}/memory-index` 与同路径的 `POST .../rebuild` 在契约里的响应 schema 都是空对象 `{}`。

实际返回为 `documents`、`vectors`、`vector_enabled`、`model_identity` 与 `failures`，与 [管理接口参考](../../server/docs/reference/management-api.md) 的描述一致，但 OpenAPI 无法表达。其中 `failures` 的元素结构完全没有定义。

#### 影响

前端只能按实际响应自行定义类型。这意味着后端改名或增删字段时不会有编译错误，只会在运行时变成 `undefined`。`failures` 更无从判断，界面只能显示数量并按原样展开内容。

#### 需求

为这两个端点声明响应结构。索引状态是排障时经常需要读取的诊断信息，字段稳定比字段数量更重要。`failures` 元素建议包含失败原因与对应材料编号。

#### 前端约定

前端按当前实际响应定义类型，并在类型注释中标明它来自实际响应而非契约。契约补齐后只做核对，不改渲染逻辑。

### 3.3 P1 社群封面引用字段

#### 背景

视觉改版把社群页改为「世界选择」：每个社群展示一张横幅封面。第一版封面全部是随前端发布的官方预设（深夜食堂、校园黄昏、湖边小镇等），不产生用户文件；未来封面与聊天背景再支持用户上传与 AI 生成（见 3.4）。

#### 需求

为社群增加可空的封面引用，并能区分预设与未来的用户资产，建议：

- `cover_kind`：`preset` 或 `asset`（缺省为空，表示未设置，前端使用程序化渐变兜底）
- `cover_ref`：`preset` 时为官方预设清单中的稳定 key；`asset` 时为 3.4 的资产 ID

两个字段需要在社群创建与社群更新接口中都可写，在社群查询响应中返回。预设清单本身是随包数据，不需要后端存储或管理接口。

选择预设不产生任何服务端文件，因此该需求不依赖资产服务，可以先于 3.4 实现。

#### 前端约定

前端内置预设 key 到素材路径的映射；字段为空或无法识别时回退到按社群派生色的渐变封面，不显示裂图。

### 3.4 P2 统一图像资产服务（上传与 AI 生成）

#### 背景

当前服务端没有文件上传接口、静态文件服务与图片存储；`avatar_url` 只是最长 2000 字符的普通字符串，不校验、不抓取、不托管。视觉改版后，玩家希望自定义角色头像（AI 生成为主、上传为辅），未来希望自定义社群封面与聊天背景。这些能力共用同一套资产管线，不应为角色与社群各写一套。

#### 需求

1. 统一资产对象与归属
   - 资产记录至少包含：资产 ID、所属玩家、用途（角色头像 / 社群封面 / 聊天背景）、来源（`upload` / `generated`）、MIME、宽高、字节数、创建时间
   - 业务表只保存引用：角色沿用现有 `avatar_url`（接受资产 URL 或资产 ID 均可，取一种约定即可），社群使用 3.3 的 `cover_kind=asset` + `cover_ref`
   - 更换图片只改业务引用；旧资产需要明确的回收策略（引用计数或定期清理无引用资产）
2. 角色肖像约定：竖版完整插画，不抠图
   - 角色肖像是单张**带虚化暖背景的竖版完整插画**，人物光影与背景一体，服务端不需要抠图或透明底处理；生成图目标尺寸为 **1080×1350（短边约 1k）**，不追求更高分辨率
   - 方形头像是该插画的取景产物：前端提供裁剪组件（方形取景框、缩放拖动），由玩家确认后输出方形 WebP；官方角色随包提供默认取景
   - 因此每个角色头像对应两个资产对象：竖版原图（图鉴、角色卡、创作预览装框展示）与方形头像（聊天列表、会话头部）；两者建立关联，更换肖像时作为一组处理
3. 分辨率约定：官方预设高分辨率，用户生成图按约 1k
   - 官方随包素材是一次性成本，保留高分辨率基准（聊天背景 3840×2160、封面横幅 3200×1200）
   - 用户生成/上传的图按实际最大展示尺寸定标，控制生图成本：聊天背景 **1920×1080**（背景会被压暗弱化，不需要更高）、社群封面 **1600×600**、竖版插画 1080×1350；窄屏背景由横版中心裁切，不单独生成
   - 服务端转码为 WebP 并生成多档尺寸，前端按场景取档：方形头像 256/512；竖版插画保留 1080 原图档与一档压缩档；聊天背景只提供 1080 档；社群封面 768/1536（2400 档仅官方预设有，用户图不产出）
4. 上传入口
   - 接收 multipart 图片，按用途校验：仅允许 WebP/PNG/JPEG 位图（**禁止 SVG 等可内嵌脚本的格式**），服务端按文件内容而非扩展名判断；建议头像类 5MB、封面类 8MB 上限
   - 上传图超过该用途目标分辨率时由服务端等比缩小，不保存超规格原图
5. AI 生成入口
   - 提交生成请求（用途与业务上下文，如草稿 ID 或人设描述），返回生成任务 ID；前端按现有异步任务模式轮询状态，成功后先产出竖版插画，玩家在线裁剪确认后再保存方形头像，二者都是与上传同构的资产对象
   - 生成尺寸固定按第 3 点的约 1k 标准，不向玩家开放分辨率选项；无模型凭据时沿用现有 `authoring_model_unavailable` 同款明确错误语义，前端如实提示「当前环境不可用」，不提供假结果
   - 生成风格预设（保证与官方画风统一）的清单希望由后端或蓝图配置给出，前端只做选择
6. 读取与安全
   - 提供按 ID 与尺寸档位读取资产的路径，响应带 `Cache-Control` 与 `X-Content-Type-Options: nosniff`
   - 用户内容与官方随包素材分路径提供；未来上 CDN 时应可拆到独立域名
   - 存储实现开发期可用本地目录，接口形态需要能替换为对象存储（OSS/S3），前端不关心实际存放位置

#### 明确不在本需求内

- 玩家个人头像：当前没有玩家头像字段，本期不需要
- 聊天图片、表情贴图、立绘差分：与视觉改版无关，不做
- 官方蓝图角色立绘与默认背景属于随包美术，不走资产服务

#### 前端约定

资产服务未上线前，自定义角色使用装饰性占位头像，社群使用预设或渐变封面，界面上不出现无法使用的上传/生成入口；接口就绪后按同一资产对象接入，不改既有业务流程。

## 4. 已核对解决

以下三项在前一版列出，现已由后端实现。前端据此继续实现，记录结论以免重复讨论。

### 4.1 会话摘要补显示名称

`PlayerConversationSummary` 增加 `display_name`，同时新增 `self_membership_status`、`self_membership_id` 与 `can_send`。

前端会话列表直接使用 `display_name`，不再显示会话标识，也不再为群聊逐个查询成员。`GET /api/conversations/{conversation_id}/members` 在会话页只用于头像与提及候选。

### 4.2 发言产物结构定义

`ConversationResultView.payload` 按 `status` 声明为 `oneOf` 与 `discriminator`：

| 变体 | 结构 |
|---|---|
| `completed` | `output.contract` 与 `output.payload`；后者含 `utterance`、可空 `thought`、可空 `reply_to_message_id` |
| `no_proposal` | `output` 为 `null` |

产物另含 `steps` 数组，每步有 `step_index`、`response_kind`、`tool_activities`、`usage_summary`、`duration_ms` 与 `diagnostic_codes`。

此前的表述疑问也已澄清：模型返回的 `{"outcome":"silent"}` 转换为 `no_proposal`，通过审核后参与决定才成为 `outcome=silent`。三者分属模型输出、生成结果与参与决定三个层级。

前端按此结构渲染，不再解析无类型 JSON。

### 4.3 Thought 清理策略

机制已实装，语义如下：

- 发言产物不重复保存内心正文，管理查询从独立 Thought 记录读取已审核保存的正文
- 没有记录或已清除时 `thought` 为 `null`，清除时间见 `thought_removed_at_utc`
- `thought_removed_at_utc` 表达的是「数据库中不可查」；显式开启的模型捕获文件独立保存，不随数据库清除而删除
- 玩家消息接口继续不返回内心

前端两种状态都正确呈现：未清除时展示正文，已清除时展示清除时间与说明。

### 4.4 写入的乐观并发复核

管理侧的成员写入已实现：`ManageMembership` 含必填的 `client_operation_id` 与 `expected_membership_version`，不匹配时返回 `409` 并区分版本冲突与幂等内容冲突。

玩家侧未实现，但当前不需要：玩家端只有加入社群这一项成员关系写入，主体是自身，不存在与他人并发冲突的场景。前端在统一位置处理 `409`，保留原输入并触发重新读取。

## 5. 已决定不做

以下事项前端已确认不再需要，后端无需投入实现。

| 事项 | 决定 | 依据 | 后端文档状态 |
|---|---|---|---|
| `401` / `403` 错误语义 | 不做 | 没有凭据场景：玩家标识由使用者指定，管理面只面向部署者本人 | HTTP 参考的错误码表只列实际支持的码，未声称凭据语义 |
| 管理端鉴权与权限模型 | 不做 | 开源部署中每个实例只有部署者可以访问，不存在需要区分的管理角色 | 管理接口参考已新增 1.1 访问边界一节 |
| 管理端写操作的前端入口 | 不做 | 契约保留 5 个写端点，前端不提供界面入口 | 无需改动 |
| 材料导出的界面入口 | 不做 | 只有开发者读取数据，现有命令行已覆盖 | 无需改动 |

管理端访问边界的前端对应处理见 [页面设计的导航与路由一节](03-page-design.md)：不保存凭据、不做权限控制。

## 6. 不需要的能力

- 逐字输出或流式发言。当前为整体消息提交后轮询读取。
- WebSocket 或 SSE 推送。当前轮询可完成真人聊天测试。
- 模型密钥、模型路由或供应商配置。前端不请求模型供应商。
- 玩家账户体系本身。`player_id` 到账户的映射由后端设计，前端只要求当前主体来源集中，见 [ADR-0001](adr/0001-identity-and-server-state-single-source.md)。
- 历史私有消息的界面标记。已确认这类数据可以删除，前端不提供创建入口，也不保留显示标记。
