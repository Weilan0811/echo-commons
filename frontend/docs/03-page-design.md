# 页面与交互设计

状态：布局与视觉方向已确定；页面实现尚未开始。
更新日期：2026-10-03。
适用范围：用户端与管理端的页面结构、视觉语言和关键交互。

本文只定义页面与交互。业务规则由 [后端文档](../../server/docs/README.md) 定义，字段与结构以 [HTTP 参考](../../server/docs/reference/http-api.md) 为准。

## 1. 设计原则

### 要做的

- 内容为主体，导航退到边缘。
- 状态用颜色、位置和微动效表达，不用文字堆叠说明。
- 角色有稳定可辨的视觉标识，不依赖图片资源。

### 明确不做的

| 不做 | 原因 |
|---|---|
| 密集表格、树形导航、灰底平铺 | 那是管理页的形态，与社交平台相反 |
| 用图片资产区分角色 | 见第 4 节的取舍与后续条件 |
| 把未接入的功能显示为可用 | 后端未提供的接口不显示为可操作入口 |
| 前端补造后端未返回的数据 | 消息集合完全来自服务端响应 |

## 2. 布局结构

三栏，每栏职责单一：

| 区域 | 内容 | 宽度意图 |
|---|---|---|
| 顶栏 | 社群名、世界时间、当前身份与社群切换 | 固定高度，通栏 |
| 导航栏 | 聊天、游戏两项 | 极窄，图标加文字 |
| 列表栏 | 会话列表，或游戏列表 | 中等，随内容自适应 |
| 主舞台 | 消息流与输入器，或游戏桌面 | 占剩余全部空间 |

**游戏进行中聊天不能中断。** 后端活动设计要求聊天任务与活动任务独立推进，两者互不阻塞。因此游戏桌面需带一个可折叠的聊天侧栏，使棋局与消息同时可见。

窄屏下列表栏折叠为主舞台上方的抽屉，导航栏收为顶部横排。布局不改变职责划分。

## 3. 导航与路由

聊天与游戏是并列的两项能力，不是同一件事，因此并列出现在导航栏，而不是把游戏做成某个会话。

| 路由 | 页面 | 说明 |
|---|---|---|
| `/app/setup` | 主体与社群入口 | 首次访问与切换身份时进入 |
| `/app/chat` | 聊天 | 默认落地页 |
| `/app/chat/:conversationId` | 会话线程 | 具体会话 |
| `/app/games` | 游戏列表 | 阶段五接入前为空状态 |
| `/admin` | 管理端首页 | 与用户端分开导航 |
| `/admin/connection` | 连接与运行状态 | 由现有连接页迁入，属运行事实 |

连接状态属于运行事实，移到管理端。用户端不展示诊断信息。

## 4. 角色形象

### 决定

当前不做图片资产，但数据结构与组件按可扩展方式实现。

头像组件采用回退链：

1. 人物模板的 `avatar` 有值时渲染图片；
2. 否则渲染由 `character_id` 派生的背景色加 `display_name` 首字。

配色规则：`character_id` 哈希映射到固定饱和度与亮度的色相。同一角色在气泡、头像、提及、棋子标记中始终同色。

### 理由

聊天场景中，首字加纯色块已足够辨识。Discord、Telegram、Slack 都采用这一方式，图像在读消息时需要额外解码，收益有限。

游戏场景不同。棋盘上的棋子需要在小尺寸下可辨的视觉标记，文字与纯色块在密集布局中区分度不足。因此头像组件同时承担棋子标记的职责，只需在 24px 下仍可辨识。

### 为什么不先做图

| 方式 | 问题 |
|---|---|
| 逐角色设计 | 有内容管线开销，角色数量增加后不可持续 |
| AI 按统一风格批量生成 | 风格一致性难以控制，混合后观感更差 |
| 通用头像集 | 需要一套设计，且不解决角色专属辨识 |

若未来支持用户自建角色，逐角色方案的产出要求会随用户增长，通用头像集是唯一可扩展的路径。因此不在无明确需求时投入美术资产。

### 升级路径

后端在人物模板中增加可选、默认为空的 `avatar` 字段。之后具备资产时，只需填充数据，组件与页面无需改动。

### 一项需要留意的取舍

后端当前定义角色为身份、状态、关系与记忆，不含外观。增加形象不只是界面决定，它让角色获得了视觉定义：外观可能与文字设定不一致，而形象一旦存在，使用者对它的预期会比对文字更具体。

因此补充形象时应同步确认人物设定与形象是否一致，而不是单纯补一个字段。

## 5. 视觉语言

### 主题

深色为主。社交平台长时间阅读为主，深色降低疲劳；游戏桌面在深色下更易突出棋盘与状态色。

### 颜色

角色配色由 `character_id` 派生，用于头像、气泡名称、提及高亮与棋子标记。玩家使用固定的中性强调色，与角色配色区分。

界面底色、边框、文字层级共用一组中性令牌，只通过间距与字号表达信息密度差异，不引入第二套配色。

### 动效

| 场景 | 表现 |
|---|---|
| 新消息进入 | 淡入并轻微上移 |
| 角色正在回应 | 角色名旁呼吸动画 |
| 轮次结束 | 状态提示淡出 |
| 面板切换 | 短距离位移或淡入 |

动效只用于表达状态变化，不做装饰性动画。帧率与模型无关，角色回应是秒级到分钟级，界面不能等待模型逐帧驱动。

## 6. 页面职责

| 页面 | 职责 | 边界 |
|---|---|---|
| 主体与社群入口 | 选择当前玩家，进入或创建社群 | 后端无账户认证，当前主体是本地测试身份 |
| 会话列表 | 群聊与私聊分组，显示最近活动 | 不显示后端未返回的成员与摘要 |
| 会话线程 | 消息流、轮次状态、输入器 | 不推断不可见内容，不补齐序号 |
| 游戏列表 | 已有玩法入口 | 阶段五接入前显示空状态 |
| 对局桌面 | 棋盘、轮序提示、合法操作、并行聊天 | 状态由服务端下发，渲染层不回写 |

## 7. 聊天页交互

### 输入器

一个输入区域承担两种状态，不拆成多个表单：

| 能力 | 交互 |
|---|---|
| 发送 | 每次发送生成 `client_message_id`，网络重试复用同一个标识与完全相同的字段 |
| 提及 | 点选角色加入提及；提及用于调度优先，不改变可见范围 |
| 回复 | 显示被回复消息的引用预览 |

**界面不提供指定受众的入口。** 会话内消息对全部成员可见，需要私下沟通时另开私聊。在同一会话里制造只有部分人看得到的记录，会让不同参与者看到不同的消息历史，且发送者的记录里看不出这条消息别人看不到。契约已移除可见范围字段，渲染逻辑也不再保留对应标记。

一次角色回应保存为一条完整消息，界面可按显示需要拆成多个气泡，但不向后端逐个发送气泡。

### 状态栏

状态栏位于输入器上方，是容器的核心部分。轮次状态如实呈现，且不能被误读为故障：

| 后端状态 | 界面表现 |
|---|---|
| 角色已被选择 | 角色名旁呼吸动画 |
| 角色已完成但无消息 | 淡出，或标注选择沉默 |
| 角色回应失败 | 明确标注失败，与沉默区分 |

`selection_order` 是规划选择次序，不表示发言完成顺序，界面不按它排序展示完成情况。

轮次完成且没有角色消息属于正常状态，界面不显示为故障。

### 消息展示

- 连续同一发送者合并成组，只在组首显示头像。
- 私有消息加锁形标记与不同底色。
- 提及对象高亮为可点击的色块。
- **不渲染消息缺口占位。** 后端说明合法私有缺口存在，界面若画占位块等于向使用者断言存在其无法核实的内容。
- 消息集合完全来自服务端响应，按 `message_id` 去重。

### 读取

`messages` 与 `turns` 是两个端点，各自独立轮询，节奏不同。页面不可见时暂停，可见时立即读取。切换玩家或会话时丢弃对应游标与缓存。

## 8. 游戏页交互

阶段五接入前只有空状态。以下为接入时确定的方向，不在当前实现。

- 棋盘由服务端状态渲染，渲染层可有本地插值与动画，不回写服务端。
- 语义状态在服务端低频提交，客户端插值到像素，因此平滑不依赖高频通信。
- 合法操作由服务端列出，界面只提交选择，不本地判定。
- 过期操作与越权操作展示服务端返回的明确结果，不在前端预判。
- 聊天与棋局并行，聊天失败或沉默不阻止棋局推进，界面不把两者关联成一次成败。

## 9. 契约对页面的影响

后端已在 `feat/backend` 补齐管理侧能力，页面设计据此调整。当前仍有两项限制：

| 限制 | 对页面的影响 | 当前处理 |
|---|---|---|
| 会话列表不按玩家过滤 | 需取社群全量会话，再逐个读取成员区间判断当前玩家是否在内 | 已适配，会话数量增加后需要后端提供玩家维度入口 |
| 参与者只能从管理接口读取 | 玩家端会话列表依赖 `/internal` 路径 | 只读成员身份，不读消息正文、记忆或诊断 |

参与者接口返回成员区间，含 `joined_after_sequence` 与 `left_at_sequence`，因此可以判断某个序号区间内当前玩家是否在会话中，比单一成员列表更准确。私有消息可见性依赖这些区间，界面不自行推断。

完整清单与优先级见 [接口缺口](02-backend-interface-gaps.md)。
