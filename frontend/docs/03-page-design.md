# 页面与交互设计

状态：用户端聊天与三个主体页已实现；管理员端查询与社群维护已实现；活动界面待阶段五。
更新日期：2026-10-17。
适用范围：用户端与管理端的页面结构、视觉语言和关键交互。

本文只定义页面与交互。业务规则由 [后端文档](../../server/docs/README.md) 定义，字段与结构以 [HTTP 参考](../../server/docs/reference/http-api.md) 为准。

## 1. 设计原则

### 要做的

- 内容为主体，导航退到边缘。
- 状态用颜色、位置和微动效表达，不用文字堆叠说明。
- 角色有稳定可辨的视觉标识，不依赖图片资源。

### 明确不做的

| 不做                         | 原因                               |
| ---------------------------- | ---------------------------------- |
| 密集表格、树形导航、灰底平铺 | 那是管理页的形态，与社交平台相反   |
| 把未接入的功能显示为可用     | 后端未提供的接口不显示为可操作入口 |
| 前端补造后端未返回的数据     | 消息集合完全来自服务端响应         |

## 2. 布局结构

三栏，每栏职责单一：

| 区域   | 内容                                 | 宽度意图           |
| ------ | ------------------------------------ | ------------------ |
| 顶栏   | 当前社群切换、世界时间、当前身份入口 | 固定高度，通栏 |
| 导航栏 | 聊天、社群、角色、身份、游戏 | 极窄，图标加文字 |
| 列表栏 | 会话列表，或游戏列表                 | 中等，随内容自适应 |
| 主舞台 | 消息流与输入器，或游戏桌面           | 占剩余全部空间     |

**游戏进行中聊天不能中断。** 后端活动设计要求聊天任务与活动任务独立推进，两者互不阻塞。因此游戏桌面需带一个可折叠的聊天侧栏，使棋局与消息同时可见。

窄屏下列表栏折叠为主舞台上方的抽屉，导航栏收为顶部横排。布局不改变职责划分。

## 3. 导航与路由

聊天与游戏是并列的两项能力，不是同一件事，因此并列出现在导航栏，而不是把游戏做成某个会话。

| 路由                        | 页面           | 说明                         |
| --------------------------- | -------------- | ---------------------------- |
| `/app/identity`             | 身份登记       | 本地身份登记与切换           |
| `/app/communities`          | 社群列表       | 场景卡、创建入口与邀请加入   |
| `/app/communities/new`      | 创建社群       | 名称、官方封面、时区与可选标识 |
| `/app/communities/:communityId` | 社群详情   | 封面预览、成员与运行状态     |
| `/app/characters`           | 角色           | 当前社群的角色、记忆状态与重试 |
| `/app/chat`                 | 聊天           | 默认落地页                   |
| `/app/chat/:conversationId` | 会话线程       | 具体会话                     |
| `/app/games`                | 游戏大厅       | 已支持游戏的目录与选择       |
| `/app/games/types/:gameType` | 游戏对局列表   | 当前社群的对局筛选与创建     |
| `/app/games/:gameId`         | 游戏房间       | 真实棋局、席位与局内聊天     |
| `/admin`                    | 管理端运行状态 | 与用户端分开导航             |
| `/admin/connection`         | 后端连接       | 存活、就绪与后台工作进程     |
| `/admin/communities`        | 社群总览       | 管理查询的起点               |
| `/admin/communities/:id`    | 社群诊断       | 角色、会话、任务与成员       |
| `/admin/communities/:id/conversations/:cid` | 会话诊断 | 消息、轮次与成员区间   |
| `/admin/communities/:id/characters/:rid`   | 角色诊断 | 状态、关系、记忆索引、记忆与反思 |
| `/admin/communities/:id/characters/:rid/tasks/:tid` | 任务诊断 | 冻结输入、审核与恢复 |
| `/admin/players`            | 玩家           | 不按社群过滤                 |

连接状态属于运行事实，移到管理端。用户端不展示诊断信息。

左侧导航提供聊天、社群、角色、身份和游戏入口，按当前页面显示选中状态。顶栏提供当前社群切换和身份入口；主体页保留全局导航，省略会话或游戏列表栏。

三个主体页承担全部数据建立：注册玩家、创建或加入社群、创作角色。新环境不依赖命令行即可产生第一个会话。

## 3.1 管理端的组织方式

管理端是**本地开发者工具**，不是运营后台，也不是用户界面。已确认管理面只面向部署者本人，因此页面不保存凭据、不做权限控制、不隐藏端点。这个定位决定呈现方式与用户端相反：

| 方面       | 用户端                   | 管理端                       |
| ---------- | ------------------------ | ---------------------------- |
| 术语       | 换成中文说法             | 直接用字段名与枚举值         |
| 错误       | 归一为可读提示           | 原样展示后端返回的内容与状态码 |
| 加载与空态 | 骨架屏、插画、友好文案   | 「读取中」与「没有记录」     |
| 信息密度   | 留白优先                 | 密度优先                     |

按管理接入文档的顺序组织：先发现社群，再沿社群进入会话与角色，最后到任务。

一条范围内并列的对象不拆成多个页面。社群下的角色、会话、任务与成员属于同一个范围，拆开会让排障时来回切换。角色记忆在同一诊断页按材料段、连续摘要、事实记录、角色认知分组；段摘要显示实际起止时间、场景范围及只读前情，连续摘要显示累计覆盖段，事实显示陈述归属和原始依据，认知显示支持事实、形成时间及版本变化。

每项记录先显示自然的人物称呼、主题、性质和状态，展开后读取正文、正式编号与逐项来源。事实与认知按自己的字段呈现，旧版本和原始内容继续按权限查看；不可读取正文时明确保留来源身份和读取状态。长期记录没有会话字段时不套用会话筛选。两个阶段的实际完成、失败和恢复显示在原有反思详情中，不把事实已提交显示成认知也已完成。定义见 [长期整理](../../server/docs/design/reflection/memory-organize.md)。

私有正文默认折叠。管理接口会返回角色内心、冻结输入与记忆正文，它们通常很长，而排障时往往先看状态与最近失败。追踪按需请求：玩家消息不限定角色，角色消息才带角色标识——用玩家标识限定会返回 404。

### 管理端关系描述

角色诊断的关系区按自然称呼显示目标，展开后查看态度正文、正式身份、数值和来源证据。每个目标显示最近的刷新状态、来源版本与内部诊断，运行详情复用反思图的查看和恢复操作。

完整记忆模式提供“重新整理关系描述”和“重新整理全部关系描述”；全部操作由后端遍历已初始化目标，不受当前列表分页限制。正在安排或执行时相应按钮禁用，查询每三秒读取进度。网络失败保留请求编号，恢复后重试同一次操作。缺少证据显示管理诊断，旧正文与关系数值保持可读，简单模式和陌生人不提供刷新。

### 执行链路、反思节点与记忆索引

一次玩家输入触发一个轮次，轮次决定谁来回应，回应各自建立任务，任务产出经过审核才成为消息。这几件事分别落在会话、任务与消息三处，排障时必须来回跳。因此轮次展开为一条链路，按发生顺序串起来：

| 步骤   | 内容                                                     |
| ------ | -------------------------------------------------------- |
| 输入   | 轮次给出的输入消息，按编号读取                           |
| 受众   | 成员区间编号，对应会话详情里的成员区间表                 |
| 选择   | 每个角色的参与决定：原因、规划次序、状态与实际结果       |
| 任务   | 本轮建立的任务，含逐步执行、产物、审核、恢复历史与冻结上下文 |
| 提交   | 本轮产生的消息                                           |

链路本身已经说明顺序，因此每一步都按需展开，不常驻显示细节。任务编号由轮次给出，但按编号读详情需要角色标识，而角色标识只能从任务列表取，因此先读该会话的任务列表筛出本轮任务；筛不到时说明是列表范围或已清理，而不是本轮没有任务。

反思节点按拓扑顺序排列，不按接口返回顺序：依赖关系决定执行顺序，按返回顺序看会出现「依赖还没跑就已经完成」的错觉。未激活节点的状态是拓扑决定的正常结果，因此「已激活」与「状态」分开表达。节点输入按需读取，`input_ready` 为假时说明输入尚未具备，不显示一个空输入框。

记忆索引回答「有多少材料应该可查」：可检索文档数、向量数、是否启用向量与失败记录。向量数为零时区分未启用向量与已启用但尚未建成。状态与失败项均有正式响应类型，前端类型由 OpenAPI 生成；失败详情按契约字段展示。管理端当前不提供重建索引入口。

角色诊断中的核心记忆区块展示一份正文、字符上限及支持的事实和认知，提供完整模式的正式重建操作。重建前后正文并列、私有正文按需展开；显示本轮记录、成功读取与未读进度、来源状态及内部错误。展开运行详情后查看冻结材料、产物、审核及实际调用。运行中每三秒查询进度并禁用重复安排；网络失败保留请求编号用于重试，成功后刷新该角色管理缓存。业务规则见 [认识刷新](../../server/docs/design/reflection/view-refresh.md)。

公开响应省略角色记忆、人物候选和图片任务的内部错误字段。用户页面使用操作提示，业务错误供客户端处理冲突与重试；内部错误文字、编号及任务诊断仅在管理端展示。接口与访问范围见 [管理接口参考](../../server/docs/reference/management-api.md)。

管理玩家列表展开玩家后显示图片生成与人物创作诊断，分别按游标加载。图片提供内部错误类型、外部任务编号与期限；人物候选提供错误类型、草稿修订、模型与请求次数。消息发送与批量人物采访同样使用用户提示，内部原因保留供管理查询。

管理社群列表按游标加载，每页 20 个，显示已加载数量；`q` 在服务端按名称或编号进行子串查询，查询范围绑定分页游标。详情提供暂停、清理范围预览和确认删除。预览展示数量、阻止对象及保留资源，执行再次检查范围，失败重新读取预览。成功后清除被删除社群缓存及本地当前社群选择。

## 3.2 身份登记

玩家标识由手填，没有账户体系兜底，因此保存前先回答「后端认不认这个玩家」：

| 后端状态         | 提示                             | 按钮           |
| ---------------- | -------------------------------- | -------------- |
| 已存在           | 后端已有这个玩家                 | 保存并进入     |
| 不存在（404）    | 后端没有这个玩家，进入时会先注册 | 注册并进入     |
| 无法确认（网络） | 无法确认，请先解决后再保存       | 禁用           |

不做「保存即注册」：那会把打错的标识也变成真实数据，之后无法分辨填错与新来。

## 3.3 社群操作

社群列表使用场景卡展示已加入的世界：封面、名称、成员头像、运行状态与当前所在标记。目录查询沿服务端游标读完全部已加入社群和成员，完成后统一交给列表、详情、顶栏和聊天选择器使用；卡片人数按完整成员列表计算，读取途中保留加载状态。卡片的进入按钮切换当前社群并前往聊天；独立的详情图标打开该社群详情，两个按钮分别接受键盘焦点。列表下方保留“开辟新天地”和“前往朋友的世界”入口。邀请入口展开简短表单，填写朋友提供的社群标识；失败保留输入，成功刷新列表并收起表单。

详情地址为 `/app/communities/:communityId`，查看详情不切换当前社群。宽屏在现有玻璃舞台内展示居中的详情面板，窄屏铺满内容区。上方展示完整封面、名字与时区，中间展示实际成员、运行状态和官方封面。创建页 `/app/communities/new` 共用封面预览、返回入口和底部操作布局。底部主要操作位于滚动区域之外，长内容与窄屏下仍然可见。

官方封面以缩略图和名称选择，包含默认渐变与现有三个场景。详情的预览选择独立于已保存封面：点击保存才提交，放弃编辑恢复原外观；已有资产封面在主动保存其他选择前保留。列表与聊天继续读取已保存引用。封面生成、上传和聊天背景生成没有玩家入口。

详情按后端 `PublicCommunityView.capabilities` 显示封面与启停操作，许可含义见 [社群读取规则](../../server/docs/design/identity-and-communities.md#6-读取与变化边界)。封面和状态共用一次写入状态，请求期间禁用这两类变更；请求携带最新 `state_version`，成功后先使用返回对象更新详情缓存，再刷新目录。失败保留封面选择并重新读取详情；版本冲突后可以用新版本再次保存，用户提示不显示内部错误类型。

创建仅要求名字，默认采用浏览器所在时区，可选择支持的时区；社群标识在“详细选项”中展开，留空由后端分配。失败保留名字、封面、时区和标识，标识已使用时提示更换。创建与详情的写入失败提示放在底部操作区域，窄屏下也能直接看见；版本冲突重新读取后提示再次操作。成功打开新社群详情，提供进入与启动操作。新社群保持暂停，创建、查看与进入均不自动启动。

从列表打开详情或创建页时，返回入口和浏览器返回均恢复列表及原入口焦点；详情支持刷新和直接打开，直接打开后返回列表。页面进入时将焦点移到标题。没有身份、加载中、空列表、读取失败与非成员访问均展示实际状态，不提供无法执行的操作。

## 4. 角色形象与创作

### 头像回退链

头像依次选择：

1. 后端返回的 `avatar_url` 有值时渲染图片；
2. 官方角色没有后端地址时使用随包头像；
3. 没有图片时渲染由 `character_id` 派生的背景色加 `display_name` 首字。

配色规则：`character_id` 哈希映射到固定饱和度与亮度的色相。同一角色在气泡、头像、提及、棋子标记中始终同色。

### 显示名与头像的来源

`CharacterView.display_name` 按实例绑定的模板版本取得，因此同一模板创建的多个角色在界面上同名。头像与插画读取实例外观覆盖，未覆盖时使用模板默认。

自定义人物实现后这个问题实际缓解：每个创作草稿会生成独立的自定义模板，`CustomBlueprintView` 自带 `display_name` 与 `avatar_url`，所以不同角色通常来自不同模板。仍然同名的情况只出现在同一模板被刻意创建多个实例时。

### 角色插画与头像选择

草稿「初识」章节在外貌区标题旁提供带文字说明的生成图标。点击先保存当前自介资料，成功后使用返回的新修订号打开插画面板；失败保留输入。生成使用已保存外貌，面板只填写画风和此次姿态、场景补充；插画完成后由作者选择方形头像范围，服务端裁剪并保存资产。头像资产编号写入草稿，定格时成为模板默认外观。人物档案可更换当前实例的插画与头像，写入携带外观版本，恢复默认时清除实例覆盖。该操作保留人物设定与其他实例外观。

使用 `react-easy-crop`（裁剪组件）处理拖动、缩放和裁剪区域，服务端校验并生成实际头像。图片地址 `/api/` 由统一客户端解析为后端地址。生成任务编号保存在本地，关闭面板或刷新后继续读取进度；提交结果未知时复用生成请求编号，外观保存失败后复用已经裁剪的头像。插画库按游标读取。用户页面显示操作提示。具体请求见 [图像资产接入](../../server/docs/guides/frontend-integration.md#图像资产与展示)。

### 角色创作流程

后端已实现完整创作流程，前端已于 2026-10-08 按本节设计接入：独立路由 `/app/characters/authoring/:draftId`（`new` 为起始屏），入口与草稿/固定人物分区在角色页。阶段划分、材料归属与校准规则由 [自定义人物创作](../../server/docs/design/custom-character-authoring.md) 定义，本节只记录页面形态与前端必须保证的约束。

当前限制：采访题只支持在默认 15 题中删减保留 10～15 题，不支持作者自定义题目；契约没有删除草稿与固定人物的接口，界面也不提供删除入口。

#### 步骤结构

创作界面采用分步向导，一次只呈现一个阶段。原因是三阶段的材料形态差别很大：基础阶段是自介卡与可展开的详细设定，故事是自由写作，采访是十到十五道题。把它们放在同一屏会变成一个信息密度过高的长表单。

| 步骤     | 内容                                   | 可否跳过 |
| -------- | -------------------------------------- | -------- |
| 基础人设 | 名字、五组自介资料、可选简述与详细正文     | 不可     |
| 过去故事 | 经历关键词或自行撰写的故事             | 可       |
| 人物采访 | 从 15 题中保留 10～15 题并作答        | 可       |
| 确认     | 校准三份正文、审核、确认固定、创建实例 | 不可     |

前一步确认后可以随时结束创作，不必走完三步。故事与采访都可跳过，因此从基础阶段确认后可以直接进入确认步骤。背景篇幅不构成进入采访的资格条件。

采访一旦进入，该阶段的选定问题必须全部有回答；明确拒答或说明不记得同样是有效回答，界面不能把未作答当作未完成以外的状态。

#### 导航不锁死

步骤指示器显示每步状态：`pending`、`accepted`、`review_required` 与 `unused`，其中 `unused` 表示作者主动跳过。

但向导不是单向的：已确认的步骤可以随时回去修改，修改会让下游进入 `review_required`。因此指示器上的完成标记不能禁用点击，界面要允许来回，并在下游步骤上显示需要复核的说明。

「下一步」在当前阶段未确认时禁用，但「跳到确认」在基础阶段确认后即可用——它是提前结束的出口，不能藏在流程末尾。

向导整体包在角色创作的外框（`AuthoringFrame`）内，顶栏始终保留「← 返回角色」入口，进入向导后不需要靠浏览器返回才能离开。

#### 章节核对态与编辑态

每一章默认停在**核对态**：所有输入只读，AI 辅助可用，底部只放「再次编辑」与章节确认/导航动作。需要改内容时点「再次编辑」才进入**编辑态**，此时 AI 生成入口禁用，底部换成「暂存本章」与「放弃修改」；暂存不做完整性校验（未写完也可以先存），放弃则把表单恢复为已保存内容。保存成功、或草稿因外部更新推进版本后，界面强制回到核对态。

这样作者在核对 AI 产出与已存内容时不会误改，「改」成为一次需要明确开始的动作。

#### 跨阶段状态的呈现位置

三份正文的审核状态 `documents_review` 不属于任何单个阶段，它在故事与采访确认后都可能变化。因此它显示在确认步骤，同时在每一步的顶部以一行状态提示可见，避免作者在前面三步里看不到正文待审核。

`interview_basis` 失效是另一种情况，只影响采访步骤，因此在第三步内表达。它的处理入口就地放在对谈章唯一的 AI 模块内（见下节），而不是进章即展示的阻断横幅——尚未开始选题、也没有任何回答时，谈不上「依据已失效」。阶段 `review_required` 与依据失效不能合并成同一句提示，两者的处理动作不同。

#### 候选与校准的位置

四类候选操作都属于某一步的局部动作，在对应步骤内呈现：基础阶段的基础人设创作、故事阶段的背景故事创作、采访阶段的角色采访。校准不占用步骤，它处理的是三份正文而不是某一步的材料，因此放在确认步骤——那时三阶段材料齐备，校准一次性针对全部材料产出三份正文的最终版本。

#### 三份运行正文贯穿全程

新草稿只需名字即可建立。基础章显示五组自介资料与形象预览，三份正文默认放在「详细设定」展开区。资料可留空或自定义；列表每行一项。按资料生成正文不调用模型，先展示简述与三份正文的原稿和修改稿，接受时由后端复核预览版本。保存自介不自动替换正文；修改资料后显示待审核状态。

`profile`、`voice` 与 `relational_dynamics` 在基础阶段就产生，之后每个阶段确认后都可能因校准而更新。它们是角色运行时真正读取的内容，故事与采访作为作者材料独立保存。

因此每一步的正文区要同时呈现两类东西：作者材料（可编辑的故事与问答）和三份正文（由作者编辑或接受候选更新）。两者不是同一份数据的两种视图，编辑入口也不同。

#### 四类 AI 操作与各自更新范围

| 操作         | 依据                     | 接受后只更新               |
| ------------ | ------------------------ | -------------------------- |
| 基础人设创作 | 基础输入与作者补充要求   | 三份正文与基础描述         |
| 背景故事创作 | 已确认的人设与故事草稿   | 故事                       |
| 角色采访     | 三份正文、故事与选定问题 | 指定回答                   |
| 人设校准     | 三阶段材料与现有正文     | 三份正文                   |

接受操作的范围由后端保证，界面要按操作类型展示修改了什么，而不是笼统提示已更新。校准结果会附带修改依据与待处理冲突，冲突涉及身份、价值取舍或经历时保留出处等待作者决定，界面不代替作者选择。

手工创作的全过程必须可用：接受候选不是必经环节，三份正文可以全部由作者手写。界面不能把 AI 辅助做成默认必选路径。

#### 候选生命周期与前端责任

| 事项       | 约定                                                   |
| ---------- | ------------------------------------------------------ |
| 候选编号   | 由客户端生成，同编号同请求幂等，不同请求返回冲突       |
| 是否可接受 | 比较候选的 `input_revision` 与草稿当前 `revision`     |
| 期限       | 候选返回 `deadline_utc`，界面据此显示剩余时间         |
| 次数       | 候选返回 `model_requests`，界面显示已用次数           |
| 中断       | 超过期限的 `processing` 候选在读取时被标记为中断     |
| 失败后重试 | 使用新的候选编号，不复用失败编号                     |

界面只按 `status` 的三个值分支：`processing` 显示处理中，`completed` 显示候选内容，`failed` 显示生成失败并提供重试。失败原因不需要按错误码分类展示——界面表达「这次生成没成功，可以重来」就足够，读者要查细节可以看管理端。

期限与次数的具体数值由后端设计确定，契约只给出实际值：界面从 `deadline_utc` 计算剩余时间，从 `model_requests` 读取已用次数，都不自行假定上限。设计文档给出的是 90 秒与两次逻辑请求，但这属于后端配置，前端硬编码会在后端调整后静默失准。

**倒计时归零不等于已中断。** 超过期限的候选是在读取时才被标记，因此本地时间到零与后端给出结论之间存在间隔。这段时间界面显示「正在确认状态」并继续按节奏读取，不提前宣布失败。

**候选是否过期由前端比较得出**，不依赖后端返回的错误码：候选的 `input_revision` 小于草稿当前 `revision` 时，接受入口直接置为不可用，候选内容仍然可读并提示重新生成。接受操作本身失败时重新读取草稿与候选即可。

#### 对谈章的选题与一键成稿

对谈章是十五张题卡，交互按「先选题、再成稿」组织：

- 尚未开始选题时，核对态只有一个「开始选择问题（默认十五题）」动作。点击后进入编辑态并一次性载入模板的全部 15 题，作者只做删减，保留数量低于 10 时不能暂存；也可以「清空采访」留白跳过本章。
- 全章只有**一个** AI 模块（「创作灵感 · 对谈回答」），不出现在题卡上逐题放生成按钮。模块统计所有回答为空的保留问题，一个动作「为 N 个未回答的问题请 TA 回答」完成整章。
- 后端单次采访候选最多携带 5 题，前端按这个契约把问题自动切成多批：逐批请求、轮询、校验未过期且无冲突后接受，再用返回的新 `revision` 发下一批。界面显示每批的等待/进行/已写入状态；停止或离开页面后，尚未发送接受请求的候选保留为未接受，不修改草稿，已经提交接受请求的批次等待实际结果。生成、轮询或接受失败均显示操作提示，流程退出时恢复运行状态和编辑入口。作者可对剩余未回答问题「继续请 TA 回答」，已写入的回答不重复生成。
- 生成的前置条件（基础与故事已定稿、正文已审核）在模块内逐项表达。正文未审核时，模块内直接展开三份正文的只读通读区，勾选「我已通读并确认一致」后就地审核通过，不需要跳到确认步骤再折回来。

#### 阶段依赖与两种失效

阶段状态有 `pending`、`accepted`、`review_required` 与 `unused` 四种，其中 `unused` 表示作者主动跳过。修改上游材料会让下游进入 `review_required`：修改基础设定或手写正文使故事与采访需要复核，修改故事使采访需要复核。

`interview_basis` 是采访所依据的正文与设定快照。它失效是独立于阶段状态的另一种情况，此时后续回答需要先重新审核前置设定才能继续。界面要把这两种失效分别表达，不能合并成一句「需要复核」。

#### 最终固定与创建实例

这两步合在向导的第四步，因为确认固定之后紧接着就是创建实例，中间没有其他决策。

最终确认要求基础阶段已确认、已填写的后续阶段没有待复核材料、三份正文已通过审核。确认需要显式提交当前版本并表明知悉背景将固定——这是一次不可逆操作，界面必须先说明确认后不能编辑，只能复制得到新草稿。

改名需要重新审核正文并重建采访依据，改头像则保留流程状态。因此名称与头像在流程末端要分别说明后果，不能一律提示「将无法修改」。

草稿本身不具备社群角色身份。确认固定资源后创建实例，作者属于目标社群才可创建。同社群其他成员可以正常与实例交流。

运行模式在创建实例时选择，默认简单模式，**创建后不可切换**，因此选项旁要直接写明。有故事或采访的角色需要完成相应初始化后才能加入会话，只有基础人设时直接可用。`material_processing` 为 `stored_only` 表示材料已保存但尚未形成可检索记忆，界面要表达这一区别于「已就绪」。

### 角色记忆状态

`CharacterView` 提供 `memory_mode`（运行模式）、`memory_status` 与 `memory_phase`。角色创建后需要准备初始材料，用户页面显示准备进度或友好失败提示；内部错误类型只在管理端展示。

玩家端因此必须提供重试入口：`POST /api/communities/{community_id}/characters/{character_id}/memory/retry`。角色处于失败状态时界面要能重试而不是只显示失败——准备失败是需要处理的状态，不是终态。

管理端对应有 `GET /internal/characters/{character_id}/memory-index` 与 `memory-index/rebuild`，用于检查与重建全文投影。

### 一项需要留意的取舍

外观与人物设定一起维护。生成插画使用角色资料与作者提供的外观补充，选择之前预览实际图片，保存后同时展示插画与裁剪头像。

## 5. 视觉语言

### 主题

玩家端采用夜景背景和带紫棕色的深灰玻璃，色相由实际主题变量集中维护。暖光从面板边缘透入，正文与按钮使用清楚的独立底色。主题颜色见 `src/styles/index.css`，游戏桌面在同一外壳中使用局部暖木色棋盘。

### 层次

层次按「内容最亮、外围最暗」安排，与常见后台相反。后台的注意力在数据表格，聊天和游戏的注意力在对话与桌面，外围压暗能把视线收进中间。

| 区域     | 令牌                | 用途                     |
| -------- | ------------------- | ------------------------ |
| 顶栏导航 | `--color-surface-sunken` | 天花板，形成 L 形包围 |
| 列表栏   | `--color-surface`   | 会话与游戏列表           |
| 主舞台   | `--color-surface-raised` | 消息流、游戏桌面、页面正文 |
| 悬浮层   | `--color-surface-overlay` | 选中项、气泡、对话框   |

### 颜色

强调色用琥珀。深蓝灰底上的蓝会整体发闷，琥珀是少数既跳又不刺眼的选择，也贴合夜晚场景的暖光。同一色相派生强调与提示，不引入第三个色相。

角色配色由 `character_id` 派生，用于头像、气泡名称、提及高亮与棋子标记。玩家使用强调色，与角色配色区分。

别人的气泡用角色派生色掺进面板色，而不是直接用角色色：派生色的色相均匀分布，落在底色色相附近时直接使用会整块融进背景，掺色后无论什么色相都保有明度差。自己的气泡用琥珀实心加深色文字，在一屏低饱和气泡里一眼可辨。

未读用列表左缘的竖条而不是圆点。深色界面上圆点容易被头像吞掉，竖条贴着边缘，未读与已读的分界一眼可见。

### 字体

拉丁与数字由 Inter 承担，中文回落到 Noto Sans SC，两者都是 SIL OFL 1.1。顺序不能颠倒：Noto Sans SC 自带拉丁字形，排在前会把拉丁字符一起吃掉，而数字和小写字母在深色小字号下的观感会明显变差。

只声明 400 与 600 两个字重：深色底上细体会糊，粗体过抢。字体文件放在 `public/fonts` 连同许可文件原样分发，`src/styles/fonts.css` 集中注册全部 `@font-face` 与字体族变量，换字体只改那一处。

序号、时间与玩家标识在列表里要纵向对齐才好比较，因此这些位置使用等宽数字。

### 动效

| 场景         | 表现             |
| ------------ | ---------------- |
| 新消息进入   | 淡入并轻微上移   |
| 角色正在回应 | 角色名旁呼吸动画 |
| 轮次结束     | 状态提示淡出     |
| 面板切换     | 短距离位移或淡入 |

动效只用于表达状态变化，不做装饰性动画。帧率与模型无关，角色回应是秒级到分钟级，界面不能等待模型逐帧驱动。

## 6. 页面职责

| 页面           | 职责                               | 边界                                   |
| -------------- | ---------------------------------- | -------------------------------------- |
| 身份登记       | 登记或切换当前玩家                 | 后端无账户认证，当前主体是本地测试身份 |
| 社群           | 切换、创建或加入社群               | 成员列表只有读取接口                   |
| 角色           | 查看角色、记忆状态与重试；模板创建与自定义人物志从同一页进入 | 记忆准备中或失败时提供重试入口                 |
| 会话列表       | 群聊与私聊分组，显示最近活动       | 不显示后端未返回的成员与摘要           |
| 会话线程       | 消息流、轮次状态、输入器           | 不推断不可见内容，不补齐序号           |
| 游戏大厅       | 真实玩法与当前社群的棋桌             | 查询、筛选、创建与进入房间             |
| 游戏房间       | 实际席位、局势、结局与桌边聊天       | 按参与资格展示棋盘与会话               |
| 对局桌面       | 棋盘、轮序提示、合法操作、并行聊天 | 状态由服务端下发，渲染层不回写         |

## 7. 聊天页交互

### 会话列表与详情

列表提供活动、历史、隐藏和已结束四个范围，筛选由后端执行。每个范围独立保存查询键和游标，通过“加载更多会话”继续请求，直到后端没有下一页。会话详情独立读取，切换筛选或个人隐藏后，当前选中的历史仍可阅读。

标题旁的“会话详情”打开沿用页面配色的圆角详情面板，展示名称、类型、状态、创建者和当前成员。已退出者显示历史读取范围，不读取当前成员名单。创建者未知的旧群聊明确显示未保存创建者，不从成员顺序推断。操作集中在详情底部，按后端许可显示退出、重新加入和结束；个人隐藏与找回始终通过正式接口保存。

退出和结束有确认说明。退出关闭当前成员区间，最后一名玩家退出时群聊自动结束；结束群聊后停止交流并保留历史。个人“从我的列表移除”只隐藏列表，找回保留原成员状态。成员或状态更新清除原实时消息缓存并重新读取实际范围；失去发送资格时卸载输入器，重新加入使用新成员区间建立空输入器。

新群聊需要选中至少两位其他成员，连同发起玩家共三人；人数要求同时由后端校验。私聊选择一位角色后使用“打开私聊”，同一社群的同一组合继续使用原会话，退出后再次打开建立新成员区间，历史缺口保持不可见。创建、结束和列表规则见 [会话设计](../../server/docs/design/conversation-and-social.md#11-创建成员与个人列表)。

### 输入器

一个输入区域承担两种状态，不拆成多个表单：

| 能力 | 交互                                                                     |
| ---- | ------------------------------------------------------------------------ |
| 发送 | 每次发送生成 `client_message_id`，网络重试复用同一个标识与完全相同的字段 |
| 提及 | 输入触发角色选择，表示希望谁回应；消息对会话成员可见                     |
| 回复 | 显示被回复消息的引用预览                                                 |

**界面不提供指定受众的入口。** 会话内消息对全部成员可见，需要私下沟通时另开私聊。在同一会话里制造只有部分人看得到的记录，会让不同参与者看到不同的消息历史，且发送者的记录里看不出这条消息别人看不到。契约已移除可见范围字段，渲染逻辑也不再保留对应标记。

一次角色回应保存为一条完整消息，界面可按显示需要拆成多个气泡，但不向后端逐个发送气泡。

角色消息里的换行表示真实的说话停顿，因此按换行拆成独立气泡，并依次错开入场：延迟由前面各段的长度累加，长段落后面等得久一些，单段的贡献有上限，五段在两秒内发完。真实感来自间隔不一致而不是间隔长。玩家消息的换行来自输入框，保留原文不拆，也不出入场延迟。

只有比进入会话时已存在的最大序号更新的消息才逐段入场。刚打开会话时历史消息一次全部出现，否则会把已经发生过的对话看成角色正在慢慢打字。

### 状态栏

状态栏位于输入器上方，是容器的核心部分。轮次状态如实呈现，且不能被误读为故障：

| 后端状态           | 界面表现                 |
| ------------------ | ------------------------ |
| 角色已被选择       | 角色名旁呼吸动画         |
| 角色已完成但无消息 | 淡出，或标注选择沉默     |
| 角色回应失败       | 明确标注失败，与沉默区分 |

`selection_order` 是规划选择次序，不表示发言完成顺序，界面不按它排序展示完成情况。

轮次完成且没有角色消息属于正常状态，界面不显示为故障。

### 消息展示

- 连续同一发送者合并成组，只在组首显示头像。
- 名称与头像取自消息携带的 `sender_display`，界面不维护标识到名称的映射。
- 历史私有消息按服务端返回的范围显示锁形标记与不同底色。新消息没有受众选择，私聊通过独立会话进行。
- 提及对象高亮为可点击的色块，名称取自会话成员列表。
- **不渲染消息缺口占位。** 后端说明成员经历与历史私有记录可能产生序号缺口，界面若画占位块等于向使用者断言存在其无法核实的内容。
- 消息集合完全来自服务端响应，按 `message_id` 去重。
- 会话停在最新消息；使用者往回翻阅时不抢滚动位置。

### 读取

用户路由按玩家与当前社群共用一条 SSE（服务器推送事件）连接。首次进入先取得事件游标，再加载页面查询，查询完成后从该游标连接。消息直接合并到当前会话增量缓存，并按消息编号去重；轮次、摘要、成员与外观变化刷新各自查询。会话列表、消息和轮次通过事件更新；角色记忆准备、人物候选与图片任务继续查询进度。请求顺序见 [初次同步、事件与历史](../../server/docs/guides/frontend-integration.md#2-初次同步事件与历史)。

断网时关闭连接并显示恢复提示，恢复网络后从最后事件或检查点继续读取；其他连接错误按间隔递增重试。游标过期时先取得新游标，再重建页面查询，最后连接。成员访问撤销时取消读取并清除玩家查询缓存及当前社群。切换玩家或社群、离开用户路由时关闭连接；切换会话继续使用社群连接。轮次状态栏读取整条回应链的活动状态，上一轮结束后仍可显示后续回应正在继续。

阅读位置没有读取端点：未读以会话摘要的 `last_read_sequence` 判断，展示新消息后提交 `PUT` 推进。

历史页保留各自结果，每次用返回的 `older_cursor` 继续，`has_older=false` 后隐藏翻页按钮。翻页请求期间禁用按钮，失败保留已有消息并显示错误。增量读取保存返回的 `cursor`，`has_more=true` 时立即读取下一页，包括过滤后没有可见消息的页；全部消息按编号去重、按序号排序。

### 角色准备

模板创建明确使用 `memory_mode=simple`。角色列表优先显示 `memory_status`：`preparing` 显示「记忆准备中」并每四秒读取，`failed` 显示友好提示和「重新准备」按钮，`ready` 再结合 `availability_status` 判断能否参与对话。重试通过正式接口执行，返回后立即更新状态并恢复进度查询。

新建会话同时读取社群成员和角色状态。准备中、准备失败、不可用或状态尚未取得的角色保留显示，但不能选择；创建时只提交当前仍然符合条件的成员。

## 8. 游戏页交互

游戏入口分为游戏目录、所选游戏的对局列表和对局页面。目录标题为“游戏”，卡片展示图形、名称、人数、简短规则和“查看对局”；内容来自正式注册目录与对应游戏的展示资料。选择游戏后，单独显示当前社群的对局、状态筛选、规则和“创建对局”。公共列表按实际游戏类型查询，人数与容量取服务端返回值。

已接入五子棋的真实创建、房间概要、本人当前局势和独立局内聊天。棋盘显示实际落子、坐标、最后一手与正式结局。进入对局只执行读取，席位名称与头像使用公开成员数据；对局内返回所选游戏的对局列表。

`GamesPage` 负责游戏目录，`GameRoomsPage` 负责公共对局列表，`GamePage` 负责实际对局。具体游戏的图形、说明、规则与创建参数放在自身场景目录，由 `sceneRegistry` 登记。新增玩法时接入真实契约和场景，目录与列表继续复用。

宽屏保留导航，在棋盘旁显示约 320px 的桌边聊天；手机将导航收进顶栏菜单，通过“棋盘／聊天”切换，棋盘约 349px 宽。切换保持聊天草稿与回复目标，隐藏聊天不推进阅读位置。原聊天页和局内聊天共同使用 `ConversationPanel`，消息提供回复入口与原文预览。

真人操作已接入创建、入座、等待时离开、开始、落子、认输、取消与结束活动。按钮依据后端返回的实际资格显示；认输、取消、离开和结束活动说明后果并要求确认。鼠标点击落子，键盘使用方向键选择交点、Enter 或空格提交；触屏选择交点后通过“确认落子”提交。正式棋盘只使用服务端确认的状态。

每次操作在发送前将完整原请求保存在 `sessionStorage`（当前标签页存储），按玩家、社群和对局分别保存；创建请求按游戏类型保存。网络失败时保留原编号和内容，提供重新确认入口；恢复网络或刷新后读取原回执，尚无回执时重试原请求。明确的版本或机会冲突会重新读取，玩家再次选择后创建新请求。旧回执用于确认执行结果，页面始终重新读取当前局势。

游戏复用当前社群的单条 SSE 连接。`game.changed` 只触发查询刷新，活动结束时即使棋局版本没有增加也刷新资格。通知位置过期后重新读取页面与聊天历史，保持聊天组件和草稿。游戏列表、房间与局势缓存均按实际读取范围区分。切换社群时返回游戏大厅；分享地址属于其他社群时提示进入所属社群。

对局标题旁的问号打开“规则与说明”弹窗，简要说明当前玩法、离开与认输、取消与结束活动的后果。支持关闭按钮、点击遮罩及 Esc（退出键）关闭，关闭后焦点返回问号入口。棋盘底部只保留状态与对局操作。

调试记录通过管理端“社群→会话→游戏会话详情”的“游戏对局”查看，包含完整状态、参与区间、正式事件、落子回执和生命周期回执。管理查询使用独立接口与缓存范围，逐页读取记录；接口定义见[游戏对局诊断](../../server/docs/reference/management-api.md#31-游戏对局诊断)。

共同交互约定与后续角色接入要求：

- 大厅通过 `GET /api/game-types` 选择玩法，再按 `game_type` 查询房间；`POST /api/games` 携带所选类型与规则创建对局，进入已有房间按 `game_id` 查询。接口与请求例子见[统一契约](../../docs/gameplay/游戏与角色活动接口.md#2-游戏类型目录与大厅)。
- 等待房间的空席位向创建者提供“邀请角色”，弹窗分页展示本社群候选，不能邀请的角色显示具体原因。选定后确认入座；角色席位标记“角色”，等待时提供带确认窗口的撤回。候选与房间资格在窗口打开或角色已入座时定期刷新，提交由后端再次检查；状态变化导致无法开始时显示原因。
- 邀请前和角色入座后明确说明自动行动与局内接话尚未接入。轮到角色时显示实际等待状态，真人不能代替角色落子。邀请、撤回复用完整请求保存、原回执恢复与共享通知，390px 布局下仍可操作。
- 棋盘由服务端状态渲染，渲染层可有本地插值与动画，不回写服务端。
- 语义状态在服务端低频提交，客户端插值到像素，因此平滑不依赖高频通信。
- 合法操作由服务端列出，界面只提交选择，不本地判定。
- 过期操作与越权操作展示服务端返回的明确结果，不在前端预判。
- 等待房间展示游戏返回的席位占用和可用操作，提供加入、等待时离开及创建者开始。进行中的退出按游戏显示认输或不支持提示，关闭页面不退出；规则见[生命周期契约](../../docs/gameplay/游戏与角色活动接口.md#3-对局生命周期与参与)。
- 每局使用独立的 `game` 会话，开始后固定参与者；游戏桌面复用消息组件与社群 SSE 连接，普通群聊与私聊保持各自会话。
- 玩家可随时发言，角色行动遵守游戏轮序。局内接话与行动可以形成一次联合决策，界面展示真实等待和执行结果，不假定它们总能分别成功。
- 游戏结算后保留赛后交流；明确结束活动后会话只读，历史消息和棋局结果继续可查。
- 首个完整页面是五子棋，使用现有 React、SVG 与 CSS。文件、依赖与阶段见[共同基础](../../docs/gameplay/共同基础与文件结构.md)，角色触发及失败规则见[活动设计](../../server/docs/design/activity-integration.md)。

## 9. 契约对页面的影响

### 参与者与可见性

参与者身份由 `GET /api/conversations/{conversation_id}/members` 提供，玩家端不依赖 `/internal` 路径。消息读取由后端按实际成员区间与受众过滤，界面直接展示返回的消息，不自行推断可见性。

### 角色显示名

`CharacterView.display_name` 按实例绑定的模板版本取得。头像与插画读取实例外观覆盖，未覆盖时使用模板默认；人物档案提供更换与恢复入口，详见 [角色插画与头像选择](#角色插画与头像选择)。

### 角色记忆状态

公开角色响应提供记忆模式与准备状态，管理响应另外提供 `memory_error_code`。用户页面保留准备失败后的重试入口，详见第 4 节。

### 会话名称

会话列表与会话标题统一使用后端摘要的 `display_name`。名称由后端派生，规则见 [HTTP 参考](../../server/docs/reference/http-api.md#4-会话概要阅读与成员)；成员查询用于头像、人数和提及候选。
