# 前端技术选型

状态：已确定，应用骨架已建立。
更新日期：2026-10-05。
适用范围：`frontend/` 下的用户端和管理员端。

## 1. 选型清单

| 层 | 选择 |
|---|---|
| 框架 | React 19 + TypeScript（strict） |
| 构建 | Vite，纯单页应用 |
| 路由 | React Router（库模式） |
| 服务端数据 | TanStack Query |
| 接口类型 | openapi-typescript 从后端 OpenAPI 契约生成类型，加手写请求层 |
| 查询键 | 统一查询键工厂 |
| 样式 | Tailwind CSS + CSS 变量主题令牌，按需使用 Radix 无样式基元 |
| 局部状态 | React 内置状态与 Context |
| 场景渲染 | 首版使用 DOM 与 CSS；不预设图形引擎 |
| 组件与页面测试 | Vitest + Testing Library |
| 端到端测试 | Playwright，对接真实后端 |
| 应用组织 | 单个应用，两套路由树 |
| 部署 | 静态产物加独立静态服务，前端直连后端绝对地址 |

选型覆盖聊天交互、管理查询、三种游戏界面、正式类型契约和本地开发需要。用户端和管理员端共用接口客户端、通用组件和状态处理，通过路由与布局区分信息展示范围。

## 2. 环境要求

| 项目 | 要求 | 说明 |
|---|---|---|
| Node.js | 22 LTS，最低 22.12.0 | Vite 8 的引擎要求为 `^20.19.0 \|\| >=22.12.0` |
| 包管理器 | npm | 单应用，无工作区需求 |
| 后端 | 已启动，默认 `http://127.0.0.1:8765` | 端口由 `server/config/settings.toml` 的 `[server].port` 决定 |

依赖范围由 `package.json` 声明，安装版本由 `package-lock.json` 固定。使用 `npm ci` 复现依赖，升级 TypeScript 等主要依赖时检查生成工具的兼容要求。

浏览器端到端检查通过 `playwright.config.ts` 选择本机 Chrome。后端使用本仓库 `server/` 的 uv 环境，安装与启动步骤见[配置指南](../../docs/configuration.md)。

跨域来源必须与浏览器地址栏中的来源匹配，配置方法见第 4.2 节。仓库当前开发配置同时允许 `localhost:5173` 和 `127.0.0.1:5173`。

## 3. 目录组织

实际结构如下（`node_modules` 与 `dist` 不列出）：

```text
frontend/
  docs/                选型、接口缺口、架构决策与状态
  index.html
  package.json
  package-lock.json
  vite.config.ts
  vitest.config.ts
  playwright.config.ts
  tsconfig.json / tsconfig.app.json / tsconfig.node.json
  .env.example         环境变量模板；本地覆盖用 .env.local，不提交
  src/
    main.tsx
    router.tsx
    api/
      schema.d.ts      由 OpenAPI 契约生成，不手工编辑
      http.ts          请求与错误归一
      queryKeys.ts     查询键工厂
      health.ts        健康检查查询
      http.test.ts
    components/
      Shell.tsx
      ErrorNotice.tsx
    app/
      layouts/AppLayout.tsx
      pages/ConnectionPage.tsx
    admin/
      layouts/AdminLayout.tsx
      pages/AdminHomePage.tsx
  e2e/
    smoke.spec.ts
  styles/index.css
```

后续按需增加：`src/identity/`（当前主体来源）、`src/scenes/`（场景渲染）、会话与消息相关查询。尚未建设的目录不预先创建。

组织原则：

- `src/api/` 是唯一与后端契约耦合的目录。契约字段不手工抄写到其他位置。
- 页面不直接拼请求路径，不自行读取本地存储取得当前主体。
- `src/scenes/` 集中全部场景渲染代码。渲染实现可以整体替换，业务代码不受影响。
- 管理员端不引入后端诊断接口到用户端代码路径中。

## 4. 启动、构建与接口地址

### 4.1 接口地址配置

接口地址由环境变量提供，不写入代码：

```text
VITE_API_BASE_URL=http://127.0.0.1:8765
```

留空时前端使用后端默认监听地址 `http://127.0.0.1:8765`，因此本地开发可以不设置该变量；切换后端实例或远程测试地址时再在 `.env.local` 中覆盖。`.env.local` 不提交，模板见 `.env.example`。

前端配置只包含接口地址和界面偏好，**不包含模型密钥，也不请求模型供应商**。

### 4.2 跨域配置

后端 `cors_origins` 默认为空，即默认不允许跨站访问。启动前端开发服务前，必须在后端 `config/settings.toml` 的 `[server]` 段写入前端完整来源：

```toml
[server]
cors_origins = ["http://localhost:5173"]
```

浏览器发出的 `Origin`（页面来源）取决于地址栏中的主机名与端口。上述示例允许 `http://localhost:5173`；使用 `http://127.0.0.1:5173` 时，也将它加入列表。仓库当前的 `server/config/settings.toml` 已包含这两个来源，包内默认设置保持空列表。修改后重启后端。

### 4.3 不使用开发代理

开发期不使用 Vite 代理转发请求，前端直接请求后端绝对地址。

原因：代理会让开发环境不经过跨域路径，问题在生产或远程测试时才暴露。要求本地与远程行为一致，就必须让两者走同一条请求链路。代价是本地必须配置 `cors_origins`，这是一次性配置。

### 4.4 命令

| 目的 | 命令 |
|---|---|
| 安装依赖 | `npm install` |
| 启动开发服务 | `npm run dev`，监听 `http://127.0.0.1:5173` |
| 生成接口类型 | `npm run api:types` |
| 类型检查 | `npm run typecheck` |
| 组件与页面测试 | `npm test` |
| 端到端测试 | `npm run test:e2e`，需后端已启动并已配置跨域来源 |
| 构建 | `npm run build`，产物在 `dist/` |

`npm run api:types` 从 `server/docs/reference/openapi.json` 生成 `src/api/schema.d.ts`。契约变更后需要重新生成，该文件不接受手工修改。

端到端测试使用系统已安装的 Chrome（Playwright `channel: 'chrome'`），不需要下载浏览器。若本机可访问 Playwright 下载源，也可执行 `npx playwright install chromium` 后去掉 `channel` 配置。

### 4.5 部署形态

`npm run build` 产出静态文件，由任意静态服务提供，不要求后端托管。

后端当前没有挂载静态文件，也没有前端路由兜底，因此静态服务需要把未知路径回退到 `index.html`，否则刷新用户端和管理员端页面会出现 404。

用户端与管理员端的访问边界不能依靠隐藏导航承担。当前没有账户认证，管理员端页面的可达性没有服务端约束，这一点在远程真人测试前需要按部署方式处理。

## 5. 选择理由与被放弃的方案

### 5.1 React 而非 Vue 或 Svelte

决定因素是活动接入和渲染多样性。共享世界与桌游都在设想范围内，需要棋盘分层、卡牌交互、相机移动和动画；管理员端需要密集表格和长文本诊断展示。React 在渲染库集成、虚拟滚动和表格方向上的现成方案最多。

OpenAPI 代码生成生态也以 React 为主要目标。

Vue 3 的开发体验同样可靠，在只有桌游的场景下差距不大；一旦进入共享世界，两者差距会拉开，因此不选。Svelte 的生态规模在图形与表格方向更薄。

### 5.2 Vite 纯单页应用，而非 SSR 框架

不使用 Next.js 或 Remix。

服务端没有账户认证，`player_id` 是显式请求字段，页面不存在会话 Cookie，因此没有服务端渲染的实际收益。SSR 会引入第二个 Node 进程，与后端单进程的部署形态冲突，并使构建产物和部署步骤翻倍。

棋盘、聊天和管理端都是重交互的客户端逻辑，SSR 不参与。

### 5.3 React Router 库模式

使用 `createBrowserRouter` 定义两套路由树。路由规模有限，不需要文件路由约定。

TanStack Router 的类型安全路由能力更强，但当前路由结构和参数都很简单，引入它会增加概念负担而不解决实际问题。若将来路由参数需要编译期校验，可以重新评估。

### 5.4 TanStack Query

选择依据是后端契约的实际要求，不是通用偏好：

- `messages` 返回 `messages`、`cursor`、`has_more`，游标原样回传，需要受控缓存和去重。
- `turns` 与 `messages` 是两个端点，需要各自独立的轮询节奏。
- 503 可重试、409 需要保留原输入，两者都要求统一的请求策略。
- 契约允许合法私有缺口，页面的消息集合必须来自服务端返回，不能由前端拼接。

服务端状态如何存放见 [ADR-0001](adr/0001-identity-and-server-state-single-source.md)。

### 5.5 接口类型生成，请求层手写

`openapi-typescript` 只生成类型，不生成请求函数。

原因是后端存在两种错误形状：`400`、`404`、`409`、`500`、`503` 返回 `{"error":{"code","message"}}`，而 `422` 返回 FastAPI 的 `detail` 数组。任何生成器都不会归一化这两种结构，这一层无论如何都要手写。既然手写不可省略，就只把类型交给生成器，请求层保持可读且可调试。

当前后端 OpenAPI 契约质量足够高：`openapi.json` 为 OpenAPI 3.1，29 个 schema 全部为具名的 PascalCase 类型，没有内联业务对象，字段为 snake_case。因此类型可以作为正式契约使用。

若接口数量增长到手写查询函数明显吃力，可评估由 Orval 等工具接管查询函数生成。这是将来的取舍，当前不预先引入。

### 5.6 Tailwind CSS

选择 Tailwind 处理布局与视觉，配合 CSS 变量保存主题令牌。

不引入完整组件库。聊天界面与管理员端的信息密度和视觉要求差异明显，完整组件库会带来体积、样式冲突和改造阻力。按需引入 Radix 的无样式基元处理下拉、对话框、标签页和滚动区域，基元不带默认外观。

纯 CSS Modules 也能完成，但同等效果的代码量明显更多；CSS-in-JS 带来运行时开销和构建复杂度。

### 5.7 不引入全局状态容器

不引入 Redux 或 Zustand。

当前判断依据是：服务器状态只有一处存放才不会被复制到组件局部状态，从而在多用户场景下出现两份真相。具体理由和将来的多用户条件见 [ADR-0001](adr/0001-identity-and-server-state-single-source.md)。

### 5.8 场景渲染不预设引擎

首版 demo 只做桌游，DOM 与 CSS 足以渲染棋盘和卡牌。共享世界已在设想范围内，但初期不需要图形引擎。

不把任何引擎设为全局前提，理由和维护边界见 [ADR-0002](adr/0002-scene-rendering-as-view-layer.md)。

### 5.9 测试组合

组件与纯逻辑使用 Vitest 和 Testing Library。端到端使用 Playwright 对接**真实后端**，符合"端到端验收使用真实后端执行"的要求。

`http.ts` 的错误归一化用构造的错误对象做单元测试，因为两种错误形状无法由真实后端稳定产生。

端到端测试使用真实后端。常规检查使用空模型凭据验证不可用路径；采访停止与离开页面的模型专项需要后端已配置真实凭据，并设置 `E2E_REAL_MODELS=1`。运行 `npx playwright test e2e/authoring.spec.ts --grep '真实模型采访' --workers=1` 检查候选生成完成后仍未接受、草稿内容与修订号保持不变。模型专项会产生真实模型费用，密钥只由后端读取。

## 6. 与后端契约相关的实现约定

以下六条由 [HTTP 参考](../../server/docs/reference/http-api.md) 和 [前端接入指南](../../server/docs/guides/frontend-integration.md) 直接推论，不是界面风格偏好。

### 6.1 游标与查询缓存成套

游标绑定社群、会话、读取玩家和扫描位置。`messages` 与 `turns` 的查询键必须包含 `community_id`、`conversation_id`、`player_id` 三项，并由查询键工厂生成。

切换玩家或会话时，丢弃对应缓存与游标，不复用。不得解析游标内部结构。

`has_more` 为 `true` 时必须继续请求下一页，即使本页经过过滤没有消息。无新消息时保存返回的游标。

### 6.2 不渲染消息缺口

契约明确合法私有缺口存在，且客户端不需要补齐每个序号。界面不显示"此处有不可见消息"之类的占位，否则等于向用户断言存在其无法核实的内容。

消息集合完全来自服务端返回，按 `message_id` 去重。

### 6.3 一次角色回应是一条消息

契约中一次角色回应保存一条完整消息。界面可以按展示需要拆成多个气泡，但不向后端逐个发送气泡。

发送与重试使用同一个 `client_message_id` 和完全相同的字段。字段冲突返回 409，界面保留原输入并提示，不自动改写。

### 6.4 轮次状态独立展示

轮次提供 `participation`，其中 `reason_code`、`status`、`outcome` 区分未参与、沉默、失败和完成。轮次完成但没有角色消息是正常状态，界面不能显示为网络故障。

`selection_order` 是规划选择次序，不表示发言完成顺序，界面不按它排序展示完成情况。

### 6.5 轮询策略

`messages` 与 `turns` 各自独立轮询，节奏不同。页面不可见时暂停轮询，恢复可见时立即读取。

当前没有 WebSocket、SSE 或逐字输出接口，界面不显示打字机效果或逐步文字。将来推送接口落地后按 ADR-0001 更新查询缓存。

### 6.6 可见性由后端过滤

前端不根据可见性自行补齐或裁剪消息。成员离开期间的消息不因重新加入而变为可见，因此客户端缓存必须按当前读取身份刷新，不能自行推断。

内部 `context`、反思结果和 `traces` 属于开发诊断，不进入普通玩家界面。

## 7. 前端实现约定

以下是写前端代码时需要持续遵循的约定。实现层面的具体原因记在代码注释中，不在此重复。

### 预览数据

后端接口未确定前，页面可以使用预览数据核对界面效果。约定：

- 集中在单个文件，文件头写明用途与删除时机，不分散到各页面。
- 所有标识带可辨识前缀（当前为 `preview-`）。这样即使文件被遗留，失败方式也是响亮的：请求返回未找到，不会静默写入真实数据。
- 预览页面不提供发送入口。发送回调直接抛出并说明原因，避免看起来可用。
- 接口接入后删除该文件，并替换引用它的取数函数。

### 未接入的能力

后端未提供的接口不显示为可用入口，不用占位数据或假成功掩盖。确实需要提前说明时，写明未接入的原因。

### 可见范围

会话内消息对全部成员可见，界面不提供指定受众的入口，渲染逻辑也不保留对应标记。需要私下沟通时另开私聊。

单条消息只对部分参与者可见，会导致发送者看到的消息历史与其他人不同，且发送者无法从自己的记录看出这条消息别人看不到。契约已移除该字段。

### 渲染约束

- 百分比形式的尺寸上限（例如 `max-w` 里的百分比）只能放在宽度由父级确定的容器上。若放在宽度由内容自身决定的元素上，会形成循环依赖，浏览器会把可用宽度算成极小值。气泡因此自身只用 `w-fit`，宽度上限放在分组容器上。
- 同一角色的视觉标识由 `character_id` 派生，在头像、气泡、提及与棋子标记中保持一致。
- 服务端状态只进入查询缓存，不复制到局部状态或全局容器。
