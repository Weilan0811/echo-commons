# 身份与服务端状态的单一来源

状态：生效。适用于 `frontend/` 全部代码。

## 决定

当前主体（当前玩家身份）只有一个来源，页面不自行读取本地存储。

来自服务端的数据只存在于查询缓存。组件不把服务端数据复制到局部状态或全局容器。需要展示派生结果时由组件基于查询结果计算，不另存一份可变副本。

所有查询键由 `src/api/queryKeys.ts` 生成，页面不手写键数组。

## 实际影响

查询键集中后，身份维度是键的一段。契约要求游标绑定社群、会话和读取玩家，且换玩家或会话时不能复用游标；集中生成使这项要求由一处代码保证，而不是依赖每个页面的自觉。

发送消息属于本地已知意图，可以先在本地显示为已发送，但最终状态以服务端返回的消息替换，并按 `message_id` 去重。这个乐观显示不构成第二份业务事实。

将来接入账户认证时，`player_id` 不再由前端发送。此时只需修改两处：主体来源改为服务端返回的身份，查询键工厂去掉玩家维度。其余页面代码不受影响，因为没有任何页面直接构造过键或读取过本地存储。

## 背景与成立条件

当前后端没有账户认证，`player_id` 是本地测试身份，单人本地测试不会出现主体切换。因此这条约束在当前阶段没有立即压力，但代价极低：它只是"不复制"和"键集中"两条编码约定。

真实约束出现在多人使用时。`player_id` 迟早由服务端从凭据推导，前端不再提供该值。届时散落在各处的查询键和主体读取会成为全局范围的改动。

另一项约束来自查询缓存的性质：每个浏览器标签页持有独立缓存，多标签页和多设备天然不共享状态，靠重新读取保证新鲜度。这个特性只有在服务端状态不复制到容器时才成立。

## 维护影响

推送接口落地时，订阅层只负责写入查询缓存，渲染仍然读取缓存。页面不订阅、不维护自己的消息集合。

若将来需要实时协作编辑或乐观并发写入，冲突处理仍是同一原则：错误按统一入口转成界面提示，不在页面各处内联重试逻辑。

这条决策与后端 `state_version`、`membership_version` 的乐观并发方向一致：状态由服务端确认，客户端只暂存视图。

不因此引入全局状态容器，也不自研缓存层；TanStack Query 已提供所需能力。
