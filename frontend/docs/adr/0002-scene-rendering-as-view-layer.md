# 场景渲染是视图层

状态：生效。适用于 `src/scenes/` 及所有玩法界面。

## 决定

场景状态由服务端下发，渲染层只负责呈现。渲染层可以有本地插值、动画和过渡，但不回写服务端。

不把任何图形引擎或物理引擎设为全局前提。是否引入以及引入哪一个，按具体玩法判断；引入时代码集中在 `src/scenes/`，对外只暴露场景组件。

## 实际影响

桌游玩法（棋盘、卡牌、骰子结果）用 DOM 与 CSS 渲染，不引入引擎。棋盘是有限的格子，卡牌是有限的牌面，没有物理计算和渲染主循环，引擎在这个范围内只增加体积和阅读成本。

共享世界需要连续移动和相机跟随时，渲染实现可以整体替换为 Canvas 或三维渲染，只要保持"输入场景状态、输出视图"的接口形状。玩法与业务代码不感知渲染实现。

## 背景与成立条件

后端的权威模型已经确定：活动状态由服务端保存，提交时复核 `state_version`、行动机会和参与身份。客户端渲染与服务端权威是两件不同的事，这不构成矛盾——服务端权威的联网游戏普遍在客户端做预测和本地模拟，再由服务端对账。**客户端有本地模拟不等于出现第二份权威，前提是本地结果永远不被直接采信。**

角色由模型驱动，模型只在决策点被调用并返回状态或行动提议。渲染帧率与模型无关，任何要求角色逐帧响应的设计在这个平台上不成立。因此渲染层承担的是状态变化的呈现，不是模拟本身。

连续移动的平滑效果不依赖高频通信：服务端保存区域、相邻对象、可交互性等语义状态，低频提交；客户端把语义状态插值到像素。只有语义状态回写服务端。

## 维护影响

场景状态以服务端返回的数据为准，不放在组件局部状态中。组件局部状态只保存渲染过程量，例如动画进度和当前悬停项。

渲染循环不放入框架的状态更新路径中。把每帧变化的坐标交给框架协调会显著增加开销，正确做法是让循环独立运行，界面外壳只负责容器和抬头显示。这与是否使用引擎无关，用 DOM 绘制移动对象同样适用。

`src/scenes/` 下新增渲染实现时，需保持既有场景组件接口，并确认没有把权威字段写入渲染侧状态。

需要新增依赖、构建管线（纹理打包、着色器编译）或独立发布产物时，应重新评估这条决策，而不是默认引擎已经就位。共享世界接入前不需要为它预建任何抽象层或插件系统。

具体玩法接入设计见 [活动接入设计](../../../server/docs/design/activity-integration.md)。
