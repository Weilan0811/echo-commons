用户端三个主体页承担全部数据建立：注册玩家、创建或加入社群、创作角色。管理端按管理接入文档组织已接入的 `/internal` 只读查询。

模板创建明确使用简单记忆模式。角色页面展示准备中、失败与可用状态，准备中自动刷新，失败提供正式重试入口；新建会话同时检查角色可用状态与记忆准备状态。自定义人物创作接口已在后端实现，前端创作页面尚未接入。

历史消息通过分页查询缓存保留，增量读取推进扫描位置并读取全部积压，合并时按消息编号去重、按序号排序。同一次发送失败后保留请求编号及内容，修改内容后分配新编号；已读提交立即刷新当前玩家的会话列表。

会话列表与标题统一使用后端的 `display_name`。角色一次回应里的换行按独立气泡依次入场，延迟由前文长度累加并设单段上限；进入会话时已存在的消息一次全部出现，不重播入场。管理端按正式类型区分发言与沉默，分别展示发言、内心正文及清除时间，并保留可展开的运行详情；具体契约见 [管理接口参考](../../server/docs/reference/management-api.md)。

技术栈：React 19.3、TypeScript 5.9、Vite 8.3、React Router 7.18、TanStack Query 5.104、Tailwind CSS 4.3；测试使用 Vitest 5.0、Testing Library 16.3 与 Playwright 1.63。字体为 Inter 与 Noto Sans SC，自托管于 `public/fonts`。

## 3. 本轮修正的问题

| 问题 | 原因 | 处理 |
|---|---|---|
| 消息显示发送者标识而非名称 | 组件从 `sender.actor_id` 取名 | 改用消息携带的 `sender_display` |
| 已读推进无效 | `/read` 只有 `PUT`，此前用它读取 | 改用会话摘要的 `last_read_sequence` |
| 提及提交被拒 | 把展示用身份键当作 `actor_id` | 提交契约要求的参与者引用 |
| 私聊创建被拒 | 参与者未包含发起人 | 发起人始终加入，对方只列角色 |
| 填入的玩家标识一律 404 | 注册接口只写了接口层 | 入口页先确认玩家是否存在 |
| 主体页高亮「聊天」 | 主体页复用了聊天区域标识 | 主体页不显示窄栏，应用名作为回聊天入口 |
| 追踪查询 404 | 玩家消息用玩家标识限定角色 | 只有角色消息才限定角色 |
| 会话列表「下一序号」为空 | 列表项不携带该字段 | 列表改显成员版本，详情仍显下一序号 |

## 4. 两次实施任务

后端契约已补齐角色创作流程、发言产物类型与会话显示名称。剩余工作分两次推进，每次完成并验证后再开始下一次。

### 第一次：管理端

管理端已接入 25 个查询端点，发言产物按 `completed` 与 `no_proposal` 分派渲染，内心正文与清除时间分别呈现，并保留可展开的运行详情。原先缺的「把一次执行的事实串起来」与「已备好接口但没有入口的读取能力」已全部接入：

| 工作 | 交付与验收 |
|---|---|
| 执行链路视图 | 会话诊断的轮次展开为链路：输入、受众、参与决定、任务与提交消息；每步按需展开，任务按编号从会话任务列表筛出 |
| 逐步执行 | 展示每步的 `response_kind`、`tool_activities`、`duration_ms` 与 `diagnostic_codes`，替代只看原始 JSON |
| 记忆详情 | 记忆五类按 `record_kind` 分别渲染详情，不再只显示概要 |
| 关系证据 | 关系数值可展开查看实际证据 |
| 反思图详情与节点输入 | 图详情含节点、来源范围、产物、审核与写入事实；节点按拓扑顺序排列而非接口返回顺序；`input_ready` 为假时显示尚未具备，不显示空内容 |
| 记忆索引 | 角色诊断显示可检索文档数、向量数、向量模型与失败数量；向量数为零时区分未启用与尚未建成；不提供重建入口，重建属于写操作 |

管理端仍不提供任何写操作入口。记忆索引两个端点在契约里的响应 schema 是空对象，前端按实际响应定义类型并注明来源，缺口记录见 [接口缺口](02-backend-interface-gaps.md#32-p2-记忆索引端点响应缺类型定义)。

### 第二次：用户端

用户端已完成会话名称、角色记忆状态展示与失败重试。缺的是角色创作流程，界面目前仍是从模板创建。

创作流程的阶段划分与材料规则由后端设计定义，见 [自定义人物创作](../../server/docs/design/custom-character-authoring.md)。前端要接的不只是表单，重点在下列几处：

| 工作 | 交付与验收 |
|---|---|
| 分步向导 | 四步：基础人设、过去故事、人物采访、确认。故事与采访可跳过，基础确认后可直接进入确认步骤 |
| 导航不锁死 | 已确认的步骤可回去修改，指示器显示四种阶段状态；下游需复核时给出说明 |
| 跨阶段状态位置 | 三份正文的审核状态在确认步骤呈现，并在每步顶部一行提示可见；采访依据失效只在采访步骤表达 |
| 材料与正文分列 | 作者材料（故事、采访）与三份运行正文分别呈现，不混为同一份数据 |
| 候选生命周期 | 按 `status` 三态分支；剩余时间由 `deadline_utc` 计算、次数读 `model_requests`，不硬编码上限；倒计时归零显示「正在确认状态」 |
| 按操作范围展示更新 | 四类操作接受后更新的内容不同，界面说明改了什么；校准附带依据与冲突 |
| 最终固定 | 一次不可逆操作，先说明后果；名称与头像的后果分别提示 |
| 创建实例 | 选择运行模式且提示不可切换；`stored_only` 与已就绪要区分 |

其余待办：窄屏布局，列表栏折叠为抽屉，导航收为顶部横排。
