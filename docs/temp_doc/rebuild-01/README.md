## 本次改造的完成范围

改造结束时，后端具有以下能力：

- 使用显式的社群、玩家、角色实例和会话，运行单角色对话与基础群聊。
- 同一人物模板可以产生多个状态和记忆独立的角色实例。
- 已结束且同受众的玩家输入可以组合成一次社会交互轮次，每个被选角色拥有自己的任务、观察、上下文与提交结果。
- 角色观察、内部状态与关系认识、私有记忆分别读取，再由任务组装为一致输入；检索与反思来源使用共同可见资格规则。
- 玩家输入使用安静窗口，角色输出共用批次并立即结束收集；界面气泡不产生重复输入，连续角色接话保持未实现。
- 模型执行、任务租约、提案审核、事务提交和运行追踪继续使用已有机制。
- `segment_reflect`、`continuity_compress`、`memory_organize` 保持已实现能力，并适配新的身份和来源边界。
- 新配置、新 HTTP 接口、新数据库和完整工程文档共同构成 `0.1.0` 基线。

基础群聊属于底层结构的验收：它证明一个输入可以生成多个独立角色任务。复杂话题判断、模型参与意愿评估和角色持续自主聊天不在本次实现范围。

## 后续扩展的位置

Activity（共享活动）将在独立模块中管理规则、公开与私有状态、合法动作和结果。ActivityTask 与 ConversationTask 独立执行，共享 Agent 与调度资源；玩法行动顺序与聊天轮次分别管理，角色可以在等待行动时发言。本次明确接入契约与归属，暂不创建空活动模块或实现小游戏。

`diary_compose`、`view_refresh`、动态记忆取回策略及生活模拟保持现有未完成状态。相关已存在的契约和存储继续保留，文档准确标记完成度。

## 执行规则

1. 删除旧接口、旧字段、旧格式加载、旧运行默认值与兼容分支；修改所有实际调用方。
2. 复用仍有价值的算法和执行机制，按职责移动代码。文件名称相同并不要求保留旧接口。
3. 同一规则只有一个实现位置；输入、轮次、任务和记忆分别拥有自己的状态，角色观察只读所属业务事实。
4. 功能扩展以明确接口接入。只有真实实现会使用的接口才进入代码。
5. 验证使用真实领域对象、SQLite、正式服务路径和真实模型。模拟回复与替身实现从新基线移除。
6. 旧数据库保留原样，新程序使用新数据库。旧资料的编号保留其历史含义，新有效文件从初始版本开始。
