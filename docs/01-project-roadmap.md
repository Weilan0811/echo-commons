# Echo Commons 整体推进计划

更新日期：2026-10-04。

## 1. 目标与当前阶段

项目目标是让真人玩家与多个持续拥有身份、关系和记忆的角色共同生活，并参与有明确规则的活动。当前后端能够运行多角色聊天，三种主要反思流程已有执行与存储实现；长期记忆整理仍缺少足够真人素材下的质量验证，日记和认识刷新尚未完整接入。

推进顺序为：文档归档准备 → 用户端与管理员端建设、真人测试 → 记忆整理 → 长期生活 → 活动接入。阶段顺序表示共同验收的依赖，前后端各自的开发不需要逐项互相等待。

正式文档整理及本地测试管理后端接口已完成。前端可以依据已有聊天和管理契约完成选型、目录创建与页面接入。真人测试产生的经历材料用于后续功能设计与质量验收；技术测试通过不能代替真实内容质量评价。

## 2. 目录与文档职责

| 位置 | 职责 |
|---|---|
| `docs/` | 整体阶段、跨端依赖、共同验收与项目级决定 |
| `server/` | 后端实现、配置和测试 |
| `server/docs/` | 后端完整设计、真实接口、开发说明、能力与待办 |
| `frontend/` | 前端应用、构建与测试；包含用户端和管理员端 |
| `frontend/docs/` | 前端选型、页面与交互、接口使用、开发说明及前端状态 |
| `docs/temp_doc/rebuild-01/` | 已归档的重构方案、核查证据和修复记录 |

后端状态文档只记录后端能力和待办；前端状态文档只记录前端交付。整体进度在本文件维护，不在两个状态文档重复复制。业务规则由后端设计定义，页面交互由前端设计定义。双方通过接口交换数据，前端不读取数据库、后端内部 Python 对象或诊断捕获目录。

用户端是最终用户的日常页面，管理员端是管理测试和查看运行事实的页面。两者的信息展示范围和操作入口明确区分。前端选型时确定应用及构建组织，不提前假设需要两个独立工程。

## 3. 前后端并行工作的方式

### 3.1 使用已完成的聊天契约

[HTTP 参考](../server/docs/reference/http-api.md) 和 [OpenAPI 契约](../server/docs/reference/openapi.json) 是当前接口的确定依据。现有接口覆盖玩家与社群创建、角色创建与列表、会话创建与列表、加入离开、消息发送与增量读取、聊天轮次读取。前端可以立即使用这些能力，按 [接入指南](../server/docs/guides/frontend-integration.md) 开发。

前端负责输入、消息展示、读取缓存和错误反馈；后端负责可见范围、参与决定、生成、保存和恢复。前端接受异步回应、合法沉默、成员经历与历史私有记录产生的序号缺口和不同角色的完成次序。当前采用轮询，无须等待新增推送接口才能完成真人聊天测试。

### 3.2 先确定新增契约，再分别实现

管理员端或后续功能需要新增接口时，先共同确定操作范围、路径、请求、响应、错误、可见范围和完成语义，形成具体契约。规划契约与已经运行的接口分别标明，未经实现的路径不写入“当前公开接口”清单。

契约确定后，前端可以实现页面、输入校验、数据类型、请求处理和真实的等待或不可用状态；后端同时实现服务与接口。尚未接入的页面不提供虚假业务数据，不用预设模型回复验证功能。相关端到端验收在接口完成后使用真实后端执行，其他已接入模块继续独立开发和测试。

接口变更同时更新后端参考和前端使用说明。前端只依赖正式字段，不把关系算法、人物提示、记忆整理规则复制到页面。后端按任务和对象范围提供查询，不根据某个页面组件的内部结构设计业务对象。

### 3.3 并行任务与共同检查点

| 工作 | 前端可以独立推进 | 后端可以独立推进 | 共同检查点 |
|---|---|---|---|
| 用户聊天 | 选型、页面、玩家选择、群聊与私聊、消息及轮次轮询 | 修正测试预期、确认现有接口与运行问题、保留来源事实 | 真人完整交流、私人隔离、失败反馈 |
| 测试管理 | 管理页面、导航、查询条件、已有诊断的展示 | 缺失列表与查询、管理动作、范围化材料导出 | 实际任务、产物与消息之间可追溯；操作经正式服务执行 |
| 错误与恢复 | 等待、失败反馈及管理恢复历史的展示 | 保留具体错误码、完整恢复动作、独立修正提示和正式诊断记录 | 原快照不变；暂停与取消正确；捕获关闭后仍能查询重试原因与处理决定 |
| 记忆整理 | 材料和结果阅读、反馈记录、执行状态展示 | 素材评价、自动调度、审核、保存及补做 | 同一批真实材料的整理质量和运行正确性 |
| 长期生活 | 日记与认识展示、世界时间界面、互动反馈 | 日记、视图、参与意愿及主动行为 | 内容有真实来源，行为与时间规则一致 |
| 活动 | 棋盘、操作输入与独立局内聊天 | 独立游戏包、角色活动能力、局内决策协调与经历来源 | 合法行动、玩家接话、联合决策、恢复与真实来源 |

## 4. 阶段一：文档归档准备

交付内容：重构资料留在归档目录；后端正式文档独立描述当前设计和能力；根文档提供阅读入口及本计划。清除后端中的已完成迁移任务指令、过时审核状态和失效链接，保留完整业务设计、提示文字及长期验证规则。

验收要求：正式文档链接有效；当前能力、尚未完成的功能及内容质量未验收范围明确；归档记录能够查阅。归档资料保留历史判断，后续开发以正式文档和当前任务为依据。

本阶段只整理文档，不更改模型行为、测试代码或业务实现。

## 5. 阶段二：前端建设与真人素材积累

### 5.1 前端选型和创建目录

选型应同时满足聊天交互、管理查询、未来活动界面、正式类型契约和本地开发需要。明确框架、构建工具、路由、服务数据读取、样式与组件组织、测试及部署方式，说明实际维护影响，形成一个完整方案。技术栈尚未决定；选型完成后创建 `frontend/` 与 `frontend/docs/`，记录启动、构建和接口地址配置方法。

选型阶段已完成，结论见 [前端技术选型](../frontend/docs/01-tech-selection.md)。应用目录、依赖安装与请求层已建立，用户端连接页可读取真实后端状态；尚未完成与后端的联调，原因见 [前端状态](../frontend/docs/status.md)。前端依赖但后端尚未提供的接口记录在 [后端接口缺口](../frontend/docs/02-backend-interface-gaps.md)，其中不影响用户端第一版建设。

用户端和管理员端有独立导航与页面职责；共用必要的接口客户端、通用组件和状态处理。业务数据保留在后端。前端配置不包含模型密钥，也不直接请求模型供应商。

### 5.2 用户端

提供玩家身份及社群／会话选择、角色信息、群聊与私聊、输入与发送、提及及回复；与部分成员交流通过独立会话完成。显示已接受消息和后台回应状态，正确处理沉默、失败、重复发送和成员变化。角色一次生成的完整消息可以按展示需要分成气泡，保存语义保持不变。

现有服务没有玩家账户认证。当前页面中的玩家选择表示本地测试身份；它与未来正式账户登录的职责需要在部署设计中明确。

### 5.3 管理员端与对应后端工作

管理页面需要能够定位一次测试的社群、玩家、角色、会话、消息、轮次和任务，查看实际冻结输入、执行追踪、失败原因及已安排反思的节点和结果。查看生成内容与诊断时明确对象归属，私人材料只出现在适当的管理范围内，不混入普通玩家消息接口。

后端已提供对象发现、任务列表、角色事实与记忆查询、上下文和反思诊断、范围化追踪及材料导出，实际范围与字段见 [本地管理接口](../server/docs/reference/management-api.md)。管理页面可以按该契约接入。

当前阶段的后端优先工作还包括 [接口范围与缺口调整](02-api-boundary-review.md) 和 [错误分类、重试与恢复功能完善](../server/docs/design/errors-and-recovery.md)。错误与恢复机制已完成后端实现，保留原持久快照；现有管理响应提供具体原因和恢复历史，前端可按新增生成类型接入。玩家与管理接口已按 [独立实施方案](02-api-boundary-review.md) 完成修正，公开范围、历史分页、已读及成员操作可用于接入；前端页面仍按自身交付记录建设。

材料封段、三种反思安排和符合条件的失败图重新启动已经通过正式服务提供管理接口，页面展示实际段或图编号及执行结果。管理页面不直接修改数据库。尚未实现的日记、认识刷新和部分成功补做不显示为可用操作。

双方先确定管理契约，再同时开发页面与接口。用户聊天建设不等待全部管理功能完成。若真人测试需要远程访问，启动前完成与该部署方式相符的玩家和管理访问边界；隐藏页面或隐藏导航不能承担访问控制。

### 5.4 真人测试与阶段验收

完成几轮真实互动，覆盖公共交流、私聊、不同角色、跨会话回忆、约定、观点变化及关系互动。轮次数量本身不能证明材料足够：每批材料都需要保留实际来源、参与角色、时间和人工反馈，能够支持后续判断。

验收内容包括用户从发送到收到回应的完整体验、私有内容隔离、管理端定位实际问题，以及材料能够从正式记录重新读取。测试数据库和真实材料持续保留；诊断捕获单独管理，不作为唯一素材来源。角色沉默或没有查询记忆按实际选择记录。

普通聊天的素材积累可以在管理端其他页面仍开发时开始。整理素材时同步发现体验或运行问题，分别记录到前端或后端待办。

## 6. 阶段三：记忆整理与质量验收

使用真人材料评价已有三种主要反思：段摘要是否准确、状态和关系是否有依据、连续摘要是否保持约定和未解决事项、长期页是否有独立回忆价值、实体关系是否便于使用。评价保留对方陈述、自身感受和客观经历的区别，禁止把猜想改写成已发生事实。

后端依据结果完善材料选择、审核和保存，再实现完整封段与持续调度、消费规则及部分成功补做。前端并行提供材料与结果阅读、状态反馈及人工评价入口，不复制整理算法。人工评价与角色记忆事实分别保存；管理反馈不得直接冒充角色经历。

共同验收使用能追溯的真实材料，检查正常流程、失败恢复、重复消费、私人范围和内容质量。调用成功、数据库已有记录、模型主动查询次数均不能单独作为质量合格标准。是否修改固定提示须有具体材料和明确授权。

## 7. 阶段四：长期生活

先按正式设计接入日记、关系态度、状态概括和核心记忆刷新，再完善参与意愿与主动交流。后端明确世界时间、真实材料、触发条件、输入、审核、保存及调用预算；前端依据契约展示日记和认识，提供相应互动体验。

前端设计与后端实现可以并行，内容验收依赖实际已保存事实。日记不虚构当天活动，认识刷新不新增关系分数或未经证实的经历。角色主动行为需要明确起因和停止条件，避免自动对话无限继续。

完成条件是多次真实使用中能够形成连贯且有来源的经历、认识与行为，并能定位失败原因；相关输入和正式结果由后端维护，页面只展示适当信息。

## 8. 阶段五：活动接入

先用五子棋完成真实可玩的共同基础：独立 `games/` 包、五项业务接口、社群参与绑定、每局独立的 `game` 会话、前端桌面与保存恢复。宿主继续共用一个进程、端口和 SQLite，游戏管理权威状态，Activity 作为角色能力协调局内决策。

共同基础通过并形成提交后，游戏开发线实现飞行棋与 Kingdomino，角色活动开发线接入五子棋模型对局。局内消息复用群聊参与机制，按类型只进入局内决策；同一角色的行动与接话可在冻结前合并。调用成本、配套发言依赖和记忆来源见[角色活动设计](../server/docs/design/activity-integration.md)。

共同验收覆盖真人整局、角色接话与行动、自动与模型分支、来源合并、抽样恢复、固定成员、旧机会与重复操作、赛后交流、归档和经历来源。两款后续游戏分别完成传统基础规则后，再完成道具与事件卡进阶规则。规则来源、文件归属与阶段见[小游戏计划](gameplay/并行开发计划.md)和[共同基础](gameplay/共同基础与文件结构.md)。

## 9. 下一组可执行工作

1. 完成前端技术选型、页面职责和目录创建，将具体前端方案放入 `frontend/docs/`。
2. 使用现有契约建设用户聊天页面；同步确定管理员端的数据与操作清单。
3. 前端接入已完成的管理契约；后端按评估调整接口范围并完善错误与恢复，双方同步新增字段及管理展示。
4. 完成真实接入与真人测试，持续保存材料和反馈，进入记忆整理质量验收。

以上是后续开发安排。每次实施明确任务范围，完成后更新所属状态文档及本文件中的阶段进度；实际交付情况由真实接入与验收结果记录。
