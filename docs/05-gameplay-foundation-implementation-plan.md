## 1. 阅读方式与目标

本计划安排游戏与角色活动能力分开开发之前的共同阶段，全部在 `.worktrees/gameplay`、`feat/gameplay` 下完成。先阅读第 3 节的六个实施单元，再按各单元的范围、数据处理和验收要求推进。各单元分别完成实现与验证，U06 负责完整交付检查。

共同阶段完成后，游戏开发线继续实现飞行棋与 Kingdomino（多米诺王国），Activity（角色活动能力）开发线首先使用真实五子棋接入模型决策。角色自动下棋、局内接话、联合决策与游戏经历进入长期记忆，均在后续 Activity 开发中交付。

本文参考 [04 号方案](04-experience-and-character-quality-plan.md)的组织方式，保留现状依据、实施顺序、各单元方案、已有数据处理和验收标准。提交、推送、创建工作树及合并按用户明确指令执行；04 号方案中的本地提交安排属于其原任务，不自动适用于本计划。

### 4.5 公共泛型与规则类型（2026-10-16）

公共 `Game` 按配置、内部局势参数化；观察、动作、动作结果、终局结果和规则事件分别具有独立类型参数。公共领域、契约、规则协议、注册表、存储与服务不导入具体玩法。五子棋在 `gomoku/contracts.py` 中指定实际模型组合，玩法默认值由 `GomokuCreateGameCommand` 提供，组合入口显式注册真实规则。

每种规则通过 `GameModels` 登记实际请求、对局、视图、回执与事件模型。请求先按所选定义验证，数据库读取按已保存的玩法及规则版本恢复具体类型；异构目录与列表保留实际模型字段。`RuleTransition` 分别返回新局势、动作结果和规则事件，终局通过 `outcome` 查询，公共编排不要求玩法局势具备 `result` 字段。

本次修正保持原 SQL 与 JSON 字段结构。31 项游戏检查、29 项相关宿主非模型检查，以及 16 个源文件的 MyPy 静态类型检查通过；独立游戏和宿主安装验收使用真实构建包。具体泛型使用及新增玩法方式见 [游戏包说明](../games/README.md#公共模型与具体玩法)。

## 5. U02：对局参与与局内会话

### 5.1 修改结果

通过宿主正式业务服务完成创建、加入、等待时离开、开始、认输、取消与结束活动。每场对局拥有独立 `game` 会话，真人可以发言并读取自己有资格看到的历史。

### 5.2 生命周期与共同事务

1. 游戏保存创建者、席位占用、稳定主体引用、实际参与区间、固定参赛记录和结果。宿主只保存社群、对局、局内会话及组合操作结果。
2. 新建 `GameParticipationService`，检查真实操作者与社群资格，通过游戏和会话服务完成操作。创建时创建者占用一个合法席位，并建立只有实际成员的局内会话；等待房间人数可以从一人变为两人。
3. 在会话服务中提取接收连接的创建、成员变更和归档业务方法；原私聊、群聊公开入口调用同一业务步骤。参与服务使用这些方法，禁止直接写入会话表。
4. 创建、加入、等待时离开、开始时成员复核及结束活动，在一个短写事务完成。游戏、会话与宿主关联任一保存失败，整个操作回滚。
5. 开始前检查人数、配置、参与资格与成员一致性；开始后固定名单。普通会话创建、加入、退出和结束入口不能绕过游戏的参与与结束规则。
6. 五子棋认输由游戏结算对手获胜并保留棋谱；结算后继续允许赛后交流。取消后停止新动作和新消息，明确结束活动后归档会话；已结算结果保持原值。
7. 创建者等待时离开，同时取消房间并归档会话。断线、刷新、进程重启或社群暂停均不自动释放席位或认输。

### 5.3 重复请求、历史与消息分流

- 生命周期操作与游戏动作分别使用契约定义的请求范围和回执。先确认真实身份与原结果读取资格，再读取已接受请求；相同内容返回原结果，不同内容使用相同编号则拒绝。
- 原请求重试可以返回已离开或已归档之前的实际结果；新请求再检查当前版本和操作资格。旧离开请求不能影响后来使用该席位的人。
- 等待时重新加入产生新的 `participation_id` 和会话成员区间。游戏历史、消息受众和回执按实际参与身份检查，不能仅按 `seat_id` 读取。
- 局内消息继续使用现有发送、索引、历史、提及、回复和通知能力。写入资格经注入的参与读取能力检查，避免会话模块反向依赖游戏 HTTP 层。
- 普通私聊和群聊保持现有调度；`game` 消息在批次收集、扫描、社交规划及任务派发处明确分流。共同阶段仅交付消息保存与真人交流，不创建 Activity 决策任务，不注册空后台处理器，不显示角色正在回应。
- 局内实际消息沿用既有受众及可见经历规则；正式游戏事件进入记忆的消费者由后续 Activity 开发线完成。

### 5.4 已有数据与验收

新增 `game` 类型及必要约束使用新增迁移。已有私聊组合、群聊成员、消息受众、已归档状态和待执行任务保持原业务含义。

1. 两名真人创建、加入、开始并完成真实五子棋；认输、取消和结束分别保存正确结果。
2. 同席位竞争、同主体多席位、人数不足、非法代表他人及开始后修改成员被拒绝。
3. 等待时离开、再次加入和原席位换人后，参与区间、消息历史和原回执正确。
4. 使用真实约束冲突或业务失败验证共同事务：不会留下单独成功的游戏、会话成员或关联；不得替换服务制造成功或失败。
5. 重复创建返回同一游戏与会话；原加入、离开、取消和结束请求重试均不重复执行。
6. 局内消息真实保存，运行现有扫描后没有普通 `ConversationTask`；普通群聊和私聊仍按原流程创建任务。
7. 结算后可聊天，取消或归档后拒绝新消息；历史按原受众保留。

主要文件范围：`games/src/echo_games/`、`modules/communities/game_participation*.py`、`modules/communities/contracts.py`、`modules/conversations/`、相关 `modules/social/` 入口及真实集成测试。这里的 `modules/` 均相对 `server/src/echo_commons/`。

### 7.7 数据、请求与恢复要求

1. `api/games.ts` 封装目录、房间、局势、操作和回执，字段直接引用生成类型，查询键包含真实读取范围。完整事件及诊断回执由 `api/admin.ts` 经独立管理接口读取，查询键包含社群、会话和记录种类，变更范围重新开始分页。
2. `GamePage` 负责路由与身份，`GameSession` 负责读取、操作与恢复，`sceneRegistry` 只登记五子棋。`Board` 接收有类型的局势、合法操作和动作回调，仅保存焦点及预览等本地状态。
3. 每次操作在首次发送前固定完整请求：主体、社群、对局、参与编号、版本、机会与 `request_id`。待确认请求使用 `sessionStorage`（当前浏览器标签页存储）保存，创建请求也能在详情地址尚未取得时恢复。网络失败与刷新不改变原请求内容。
4. 结果未知时显示“正在确认操作结果”，读取原回执；尚无回执时重试原请求。普通网络恢复与页面重挂载不能生成新编号重做操作。明确的版本或机会冲突触发重新读取，玩家重新选择后才建立新操作。
5. 提交期间阻止重复操作，服务端确认后更新正式棋盘。收到较旧回执时恢复操作反馈，同时重新读取当前状态，避免旧结果覆盖较新局势。请求取消、身份变化和社群变化时隔离原范围的响应与待确认请求。
6. 首次进入沿用“取得社群事件位置→读取页面数据→连接原位置”的顺序，把游戏查询加入原有读取等待范围。通知只触发查询刷新；结算后的活动结束仍刷新会话状态与操作资格，不能仅凭棋局版本相等跳过。
7. 普通断线从原 SSE 位置补充；超过保留期时重新取得位置并读取房间、局势、聊天及所需正式历史。把游戏加入恢复、访问撤销和缓存清理范围，维持单条共享社群连接。
8. 房间地址可能属于另一社群。通过公开房间响应确认所属范围；提示用户进入所属社群并使用相应实时连接。切换当前社群后返回对应大厅，防止显示旧房间并监听另一社群。
9. 共同聊天面板接收明确的玩家、会话和显示模式，不自行读取路由。读取和发送沿用原接口；发言资格取实际摘要，已取消与已归档时显示相应只读状态。局内聊天使用真实消息，普通轮次状态仅用于已有普通聊天。

## 8. U05：角色参与与真实观察

### 8.1 修改结果

创建者可以通过正式入口邀请符合资格的社群角色、在等待时撤回邀请，游戏和会话持久保存其真实参与记录。Activity 的观察服务可以使用角色自身身份读取同版本局势与行动机会。

本单元只建立真实参与和观察能力。界面明确显示角色行动与接话尚未接入，不显示虚假的思考进度，也不代替角色选择落点。真人整局继续通过两名真人独立验收；角色参与读取可以在独立真实对局中验收，轮到角色时等待后续行动接入。

### 8.2 实现要求

1. 复用 U02 的参与服务和 U03 的加入接口，保留实际邀请者。检查创建者权限、角色所属社群、准备及可用状态；不能用邀请者的身份读取角色局势。
2. 明确本阶段的能力资格：实际提供的是游戏观察读取，活动行动与局内回应尚未注册。本阶段的邀请和读取检查只声明已实现能力；完整 Activity 接入时，再由其正式执行能力决定任务是否可以安排。
3. 现有只读工具的 `CapabilityResolver` 继续保持职责。观察接入不伪造局内模型用途、输出契约或可执行能力，不添加占位开关；资格的正式定义同步到角色活动设计和接口契约。
4. 在 `modules/activities/contracts.py`、`observation.py` 实现实际使用的读取契约与观察转换。依赖注入社群资格、身份转换和对局关联协议，通过游戏 `find_participations` 等公开方法查找席位。
5. 使用角色的真实 `SeatAccess` 读取游戏观察、合法操作和可见事件，生成具备真实对局身份、主体、发生时间、状态版本和来源的 `ActivityObservation`。观察来自正式游戏查询，不根据聊天猜测棋局。
6. 游戏包不导入 Activity；Activity 不导入 `app/games` 或直接查询游戏表。HTTP 和角色读取使用同一游戏服务与权限定义。
7. 对尚未实现的任务存储、模型决策、80%／20% 调用策略、来源协调、配套发言和记忆消费者，仅保留已有正式设计，不创建空处理器或假任务。

### 8.3 已有数据与验收

- 真实创建角色或使用隔离环境中的实际角色，通过正式邀请入口占用席位；观察中的主体、席位、参与编号与会话成员一致。
- 等待时撤回、重新邀请产生新的区间；旧访问上下文不能执行新的参与操作，历史仍按原资格读取。
- 非创建者代表角色加入、跨社群角色、准备未完成或无真实观察资格的请求被拒绝。
- 开始后取得真实棋盘、行动者及合法操作，重启后仍可通过持久参与查询找到角色；没有注册的执行能力不产生模型任务或调用。
- 角色读取和真人读取符合相同业务规则。用真实主体、不同参与区间及越权请求检查范围，不为五子棋虚构私人手牌。
- 既有人物设定、记忆模式、资料和密钥保持原值；不得为了邀请改写已固定的人物正文。

### 9.3 后续两条开发线

共同基础验证完成后整理可检查的变更，按用户授权形成共同提交，再从相同提交建立或复用 `feat/activity` 工作树。当前任务不自动创建新工作树、提交或合并。

| 开发线 | 后续完整交付 | 使用的共同基础 |
|---|---|---|
| 游戏开发线 `feat/gameplay` | 飞行棋和 Kingdomino 基础规则、前端、素材及各自真实整局，随后独立设计进阶规则 | 独立包、规则注册、生命周期、五项能力、HTTP、SSE 和游戏桌面 |
| Activity 开发线 `feat/activity` | 五子棋角色决策、玩家接话、联合提议、持久抽样、租约恢复、配套发言及真实经历消费者 | 正式角色参与、局内会话、实际观察和行动机会、共享事务业务方法 |

游戏契约由游戏开发线维护；后续宿主组合与共同任务注册由 Activity 开发线维护，前端生成类型由游戏开发线生成。迁移登记、依赖锁定文件及共同事件定义每次由一名维护者修改，另一条线同步完成的变更。共同阶段由当前维护者统一处理这些文件。

角色提交时，后续 Activity 编排必须在同一短事务复核租约，调用游戏服务、会话服务保存获准配套发言，再完成任务。U06 应交接这些真实业务方法及验证入口，后续无需复制游戏规则或另建事务设施。

## 10. 共同开发要求与完成标准

### 10.1 实现与范围

- 一个后端进程、一个端口、一个 SQLite 文件，游戏包与宿主各自管理所属数据。模型、网络与浏览器动画均在写事务外。
- 游戏、HTTP、角色模型和前端分别使用明确的数据对象，通过正式转换合作。公共接口采用成熟类型与标准数据库连接，不引入通用脚本语言、第二个调度器或第二套迁移系统。
- 同一业务事实只有一个维护者，状态查询复用同一资格规则；日志、通知和观察正文不替代权威游戏状态。
- 游戏包仅登记已实现玩法。飞行棋、Kingdomino、进阶道具、事件卡、观战、换人、悔棋、计时和角色主动加入均不在共同阶段实现。
- 本阶段五子棋不依赖新增动画、拖放或游戏引擎；后续所属玩法实现时按正式设计引入所需成熟依赖。

### 10.2 数据与验证

- 使用新增迁移；已有业务库先备份，在副本完成升级验证，保留原始记录与密钥。开发与浏览器测试使用独立数据库。
- 所有验证使用真实规则、业务服务、SQLite、HTTP、队列扫描和浏览器。禁止 mock（模拟对象）、假后端、预设成功结果和为通过测试绕过正式入口。
- 失败路径使用项目实际可达的非法输入、真实约束冲突、事务占用、断网和进程重启。规则单元检查与跨模块完整流程分别记录实际证明的内容。
- 依照改动影响运行检查，通过后不无依据重复扩大范围。没有执行的模型、安装、视觉或恢复场景保持未验证状态。

### 10.3 每个单元的完成标准

1. 所属正式实现、必要迁移、已有数据处理及失败恢复要求完成。
2. 相关接口、生成类型、业务设计、状态文档与验证说明同步，当前实现与后续目标清楚。
3. 本单元必要真实验证通过，结果和证据可以检查；具体限制如实记录。
4. 清理本轮临时服务、浏览器、后台进程和不再使用的临时目录，保留用户已有资源与业务数据。
5. 给出独立可检查的变更范围和完成记录。提交、推送与合并仍按用户授权执行，不混入已有无关修改。

U01～U06 全部完成后，共同阶段交付真人五子棋、独立局内聊天、真实角色参与与观察，以及两条后续开发线可以直接复用的正式业务入口。
