# 角色活动上下文、决定执行与游戏记忆修正计划

更新日期：2026-11-06。状态：单元 1—2 已完成；单元 3—7 待实施。

[06 号计划](06-activity-implementation-plan.md)已经封档。本计划处理该轮实验暴露的身份混淆、重复表达、摘要过细，以及相关的表达时效、任务调度和调用成本问题。下文描述目标行为及实施顺序；当前实现与历史验收仍见[后端状态](../server/docs/status.md)和[飞行棋验收记录](../server/docs/guides/aeroplane-activity.md)。

## 1. 修正目标与依据

| 问题 | 已确认的表现及实现缺陷 | 修正目标 |
|---|---|---|
| 身份混淆 | 蓝方在赛后认领黄方的胜利；摘要中的“我”更换颜色。近期游戏卡片按名字去重，丢失同名参与者，也未提供本人席位及获胜人物的对应 | 人物、本人、席位和经历归属在行动、聊天、反思及回忆中保持一致 |
| 重复表达 | 表达阶段更新棋盘及意图，却沿用原判断的聊天。真实输入曾移除最近自身发言；不同回合的表达随后继续回应旧话题 | 保留直接对话经过；表达使用正确时点的现场；配套话语与原行动共同执行 |
| 摘要过细 | 阶段摘要记录大量普通移动格数，连续摘要继续保留这些经过；整局摘要也继承了错误的人物视角 | 按场景及用途选择材料，保留结果、转折、精彩互动、约定和有后续意义的变化 |

这些现象有程序和输入组织方面的依据。具体措辞仍由模型生成，质量评价需要同时检查实际输入、正式游戏结果及输出。

### 1.1 成本依据

本地配置已完成的多选行动判断共 145 次，其中 127 次由本地直接选择、18 次转交普通模型；18 次转交全部由意图更新触发。另有 156 次单选行动自动执行。当前记录支持保留本地接管能力。

该配置已记录的云端请求共 435 次：正文生成 220 次、摘要及反思 125 次、深入理解行动与接话 81 次、普通聊天 9 次。请求数包含工具后续调用、格式修正、失败重试和排查，不能等同于消息数量。145 次行动判断中有 85 次选择想交流，行动由本地完成后仍可能产生正文调用。

本轮记录跨越多次修复及重启，用于定位消耗来源。费用以实际账单为准；缺失用量保持缺失，本地推理用量与云端付费用量分别统计。

## 2. 共同设计

### 2.1 一次回合形成一份统一决定

一次回合使用共同上下文，形成包含行动、表达目的或正文、意图变更及适用依据的决定。各阶段保存结果，正常执行在同一次回合任务内连续完成。

“本次念头”说明这一次如何理解和选择；“局内意图”保存需要跨回合延续的打算。简短想法只保存模型实际生成的内容，本地结构选择可以形成没有文字内心的有效决定。后续判断继续通过当前意图延续打算。

| 本地判断结果 | 后续处理 |
|---|---|
| 现有意图适用、动作明确、保持安静 | 保存结构化决定，直接执行行动 |
| 现有意图适用、动作明确、需要开口 | 根据已确定的行动与表达目的生成配套正文，再执行行动并立即发表 |
| 新语境、约定或冲突需要深入理解 | 普通模型完成统一决定，同时提出意图变更、行动和可选正文 |

普通模型直接判断时，继续在同一次判断任务中形成上述结果。正文准备只负责表达既有决定；意图变更由决定提出，由正式提交阶段写入。

### 2.2 任务状态与对话经过分别组织

游戏输入包含人设与共同要求、任务状态、正式观察、行动分析、相关记忆及对话经过。任务状态提供完整的本人身份和本局关系：

```xml
<task_state>
  <session_context>游戏、规则与胜利条件、参与者和席位、本人标记</session_context>
  <current_game_state>版本、阶段、行动方、棋盘、本次合法行动</current_game_state>
  <current_intents>当前局内打算及其消息依据</current_intents>
  <communication_state>本次交流来源、最近自身发言、尚未完成的安排</communication_state>
</task_state>
```

规则规定的胜利条件与角色自己的打算分别表达。角色可以依据人设、关系、打趣、挑衅和约定形成不同态度，程序保留真实语境供其选择。

任务状态是所属业务数据在一次输入中的组合。游戏保存权威局势，参与关系保存席位，工作记忆保存局内意图；Activity 负责组织视角。相对稳定部分随参与者及身份变化刷新，局势和意图按实际读取更新。

### 2.3 表达具有明确的时机

随行动的表达绑定原回合和动作，在动作前准备好，在动作成功后立即处理发布。独立聊天、独立事件反应在实际生成时准备当前现场。两类表达分别记录其关系和有效条件。

决定固定之后的新消息保留给后续判断。原行动机会、成员资格及表达时机失效时结束旧处理；已有结果和错误保留真实记录。

### 2.4 模块职责

| 模块 | 本计划中的职责 |
|---|---|
| 游戏及参与关系 | 权威局势、规则、席位、参与区间、行动机会及回执 |
| Activity | 游戏任务状态、观察和分析、统一回合决定、局内意图、行动与配套表达的业务关联 |
| conversation | 共同消息上下文、表达审核、回复对象、受众、正式保存和通知 |
| social | 交流资格、来源安排、顺序、额度和正式完成通知 |
| memory | 可见历史的选择、摘要覆盖、游戏经历材料及记忆检索 |
| reflection | 按场景组织摘要、连续压缩及长期整理，维护产物来源与版本 |
| characters 与 agents | 人物材料、角色能力、模型调用和实际决定输出 |
| execution | 全局运行调度、多队列资源分配、租约、依赖、并发范围、阶段恢复及业务有效性复核的调用 |

领域规则由所属模块提供；运行层根据明确的任务范围、依赖和有效条件安排执行。已有正式入口、存储和共同模型额度继续复用。

### 3.1 单元 1：任务状态、稳定身份与提示组装

交付内容：

- 建立统一的活动任务状态输入，将本局身份与规则、当前局势、意图和交流状态明确分组。普通聊天继续使用消息为主的输入组织。
- 人物对应包含稳定身份、显示名称、席位及本人标记。同名人物分别保存，在聊天、反思、游戏经历卡片和回忆中使用相同对应关系；历史对应依据原参与区间读取。
- 近期游戏卡片保留本人席位、实际参与者与胜负归属；反思材料明确区分本人、其他人、原话及自身认识。
- 使用一致的描述性标签及自然层级。固定指令、身份、规则与来源材料分开；输出结构和来源说明也具有明确段落。相对稳定文字前置，频繁变化内容后置。
- 来源编号使用程序维护的对应；模型材料优先展示可辨认的人物称呼和角色关系，保留必要的追溯引用。

主要修改：`agents/contracts/{activity,context}.py`、`agents/harness/prompt.py`、`modules/activities/{context,experience}.py`、`modules/activities/tasks/prompt.py`、`modules/conversations/tasks/prompt.py`、`modules/memory/services/experiences.py`、`modules/reflection/tasks/{prompt,projection}.py` 及所属提示资源。

验收：同名角色仍有独立的本人标记与席位；角色退出或重新参与后沿用正确区间；普通聊天、游戏及反思的最终输入可分别阅读；可见范围与来源编号保持一致。

### 3.2 单元 2：近期对话保留与独立表达现场

交付内容：

- 为直接回应对象、最近已经发布的自身发言及紧邻交流设置明确的保留优先级；现有摘要覆盖继续保护较早历史。容量不足时压缩可整理历史，必要材料仍受总容量限制。
- 在实际开始独立表达时重新准备可见聊天、当前状态、意图及交流安排，单独保留原决定依据和正式回执。排队期间的新消息进入本次现场，生成期间的新消息进入后续处理。
- 区分独立表达输入和原行动输入的读取截止、版本与来源。已经保存的生成结果直接复用，恢复时继续核对有效性。
- 当前窗口按消息顺序组织，角色自身发言标记清楚；临近群聊和私聊按场景提供背景，沿用原受众和成员区间。
- 缩短等待模型资源后到固定时效性输入之间的间隔，与单元 5 的资源安排共同完成。

主要修改：`modules/activities/expression.py`、`modules/activities/context.py`、`modules/conversations/tasks/{context,prompt}.py`、`modules/memory/services/context.py`、`modules/reflection/context_preparation.py`。

验收：重现已有第 36—39 条连续发言所对应的读取顺序，检查最终输入实际包含最近自身发言及生成前可见的新消息；跨群和私人内容继续遵守资格；恢复后的回复编号对应原输入。

### 3.3 单元 3：统一回合决定与本地接管

交付内容：

- 一次回合形成一份正式决定，关联共同输入、选中动作、表达目的或正文、意图变更及适用条件。决定记录与跨回合意图分别保存。
- 本地直接选择可以形成有效决定，文字内心保持实际空值。新语境需要理解时转交普通模型，转交结果继续属于原回合。
- 将需要深入理解、需要正文措辞和保持安静分别处理。完整理解任务可以同时完成行动、意图和正文；已确定决定的正文准备只负责表达。
- 本地意图问题只针对新增材料与当前打算的关系作判断，旧消息作为背景。意图内容、依据或有效性发生实质变化时更新意图版本，未变化的意图及标识继续沿用。
- 表达意愿说明本次新增的交流目的及相关来源，结合最近自身发言和待表达安排判断是否仍有内容；局内意图继续支持角色的态度和选择。
- 纯正文生成与发布阶段使用已有决定。新的约定通过一次新的角色决定提出意图变化，由正式提交阶段写入一次。

主要修改：`agents/contracts/activity.py`、`modules/activities/tasks/{execution,review,commit,prompt}.py`、`modules/activities/working_memory.py`、`modules/activities/expression.py`、`resources/prompts/activity/`。

验收：本地稳定且沉默的回合完成行动而没有云端调用；需要正文时复用选定动作与原意图；需要理解时保存实际原因并形成完整决定；意图在结算、取消、退出和活动关闭时按原生命周期清除。

### 3.4 单元 4：行动与配套表达共同执行

交付内容：

- 回合任务内部连续完成决定准备、正式动作和配套发表，各阶段分别保存结果。配套正文在动作执行前准备好，动作成功后立即处理审核与发布。
- 普通模型已经形成的联合正文直接进入发布处理；本地决定需要的正文在原行动执行前完成，保留必要的行动资格复核。
- 当前回合的短提交与发布阶段完成后，再启动本局下一次自动行动。真人操作若已推进局面，发表前按实际有效条件检查旧话语。
- 以回合、动作和来源阶段明确表达时机。`comments_on_action` 继续说明内容关联，任务关系另行表达是否必须随原动作发表。
- 动作、公开消息及来源完成分别登记正式结果。已经成功的动作保留；错过绑定时机的配套话语结束，恢复只处理仍有效且未完成的部分。
- 独立接话继续采用先形成决定、再表达的流程。尚未决定的独立交流来源可以合并，保留玩家问题及原来源；各回合的配套话语保持各自时机。

主要修改：`modules/activities/tasks/{handler,execution,commit,recovery}.py`、`modules/activities/expression.py`、`modules/activities/repositories/{tasks,expressions,results,sources}.py`、`modules/social/completion.py`、`modules/conversations/services/expression.py` 及输入输出契约。

验收：正文与动作出自同一决定；配套正文在实际动作前准备完毕；模型及发布失败后动作只执行一次；重启后的过期话语结束；合法沉默和表达结束都完成原 social 安排。

### 3.5 单元 5：全局运行调度与多队列并发

交付内容：

- 对话、Activity 和反思通过共同运行层安排可执行任务。业务模块登记处理器、业务范围、依赖及有效条件，保留所属任务记录和业务资格查询。
- 按游戏回合、独立交流和后台整理设置逻辑队列，复用现有带权轮询作公平分配。执行层统一管理跨队列并发与共享模型额度。
- 将跨队列先后和互斥策略集中到 `execution`；各仓库继续提供同一短事务内的资格读取、领取及租约写入。领取、执行占用与恢复保持一致。
- 普通群聊与游戏允许并行。局内独立交流和行动可以并行准备及推理；同一局意图的变更协调提交，同一角色同一窗口的公开发言保持有序。
- 同一次回合的行动和配套发表依次执行；并发限制只覆盖实际共享状态及必要阶段。输入依赖未准备好时释放执行资源，所需摘要得到调度机会。
- 图像继续使用独立资源设置，运行生命周期沿用共同管理。共享资源的等待不导致大批即时任务提前固定陈旧现场。

主要修改：`execution/{contracts,registry,dispatcher,model_budget,supervisor}.py`，拟新增 `execution/scheduling.py` 集中跨队列策略；修改 `execution/workers/`、所属任务队列和仓库，以及 `app/{composition,settings}.py`。Activity 原有调度策略完成迁移后删除重复实现。

验收：不同窗口与游戏有实际并发执行；同一行动机会不重复执行；意图变更冲突得到明确处理；队列繁忙时其他类别仍能取得机会；等待摘要的任务可以继续，租约和重启恢复不改变已完成的业务事实。

### 3.6 单元 6：游戏摘要选材与旧记忆修正

交付内容：

- 继续使用 reflection 的阶段摘要与连续压缩节点，按来源场景及整理用途提供明确要求。游戏输入保留稳定人物和席位对应，结局与聊天自述的材料性质清楚区分。
- 在 memory 的游戏经历选材中，将连续普通操作组织成简洁进展，突出结果、转折、碰撞等精彩片段、有意义的交流及未完成约定。正式原始动作和事件继续独立保存，行动判断沿用原事件读取契约。
- 阶段摘要保留新增且有后续意义的内容；连续摘要主动合并重复内容并省略失去意义的移动细节，保留事实含义与确定程度。各节点的通用要求与游戏要求使用一致的选材标准。
- 正式关闭信号进入整理目的。胜负产生后继续保留局后聊天；关闭后由已有连续整理形成完整整局回忆，覆盖完成后登记其结果。
- 普通群聊按原场景摘要，跨窗口约定保留真实延续与知情范围。游戏日常检索以摘要和有价值的经历为主，原始逐步记录用于追溯。
- 对受影响的旧材料保留原记录及来源，通过正式反思和纠正入口生成新版本，更新连续摘要及检索索引。已经形成的长期事实列出影响范围，按既有纠正规则处理。实际重建由用户指定角色和批次后执行。

主要修改：`modules/memory/services/{experiences,batches,context}.py`、`modules/reflection/contexts/{segment,summaries}.py`、`modules/reflection/tasks/{prompt,projection}.py`、`resources/prompts/reflection/{common,materials/dialogue,nodes/segment_summary_plan,nodes/continuity_compress}.md`。

验收：摘要能正确说明自己是谁、谁获胜及关键互动；普通移动不再逐步堆积；前后段保持同一视角，旧细节可正确省略；局后发言、跨群约定与私人范围保留；旧摘要修正后索引与来源版本一致。

### 3.7 单元 7：代表场景验收与调用成本交接

交付内容：

- 复用已有素材与正式入口，覆盖同名人物、不同人物、稳定意图与沉默、必要配套表达、新约定、插话、跨群连续交流及局后回忆。
- 按统一决定保存本地接管、意图转交、正文生成和沉默的实际原因，分别统计阶段摘要及连续压缩、工具后续、格式修正和供应商重试。

### 7.1 单元 1：任务状态、稳定身份与提示组装

已实现统一活动任务状态。`ParticipantIdentity` 保存人物身份、名称和本人标记，`ActivityParticipant` 增加实际参与编号、席位和参与时间；`ActivitySessionContext` 组合本局规则与人物对应。聊天、局内判断和反思采用一致的本人标记，来源编号继续由程序维护。

普通及本地活动输入按 `task_state` 的四个子段组织，正式观察、分析、相关记忆、对话、输出契约与来源说明分别提供。合法动作按类型、参数名和参数行完整表示，减少重复文字。近期游戏卡片保留本人席位及正式获胜人物；反思通过独立的 `activity_sessions` 保存原参与区间与材料截止的身份背景，原始事件正文与版本继续保留。

主要修改包含 `agents/contracts/{activity,context}.py`、共同提示辅助、Activity 输入与表达身份准备、游戏经历、聊天上下文与提示、memory 游戏卡片、reflection 输入与提示，以及所属资源和设计。没有新增数据库迁移；新提示布局支持旧冻结字段恢复。

### 7.2 单元 2：近期对话保留与独立表达现场

memory 已增加有明确可见范围的近期原文保留规则。直接回复对象、最近自身发言及紧邻交流在容量分配和摘要覆盖后继续保留；既有摘要仍负责较早历史，必要输入继续受总容量约束。共同消息顺序、跨窗口背景及私人受众沿用原规则。

独立表达在取得共享模型名额后，通过 Activity 和 conversation 读取当前游戏、人物状态、意图、回应安排及聊天。`ExpressionOrigin` 单独保存原决定的时间、范围、实际选择或理解和来源版本。准备期间的新消息进入实际生成现场，生成登记后的消息保留给后续判断；读取本身不推进理解或回应位置。原有联合正文和已经保存的生成结果继续使用原输入与回复编号。

等待检索或摘要时保存准备阶段，释放模型名额并延期，复用 `ActivityMemoryWorker` 和既有反思准备；等待不消耗表达尝试次数。共享额度的预约由 execution 提供，串行模型及工具调用复用同一名额。独立表达布局版本为 3，旧输入继续恢复；没有新增数据库迁移。全局逻辑队列及并发范围继续按单元 5 实施。

主要修改：共同上下文与活动输入契约、memory 选择、conversation 准备、reflection 覆盖刷新、Activity 表达准备与恢复、表达领取和后台材料准备、共享模型额度及对应提示、设计与生成参考。

450 项非模型回归全部通过；前端接口类型生成和类型检查通过，代码规范与差异检查通过。新增三项专项检查覆盖第 36—39 条交流中的自身发言保留、表达准备读取新消息而恢复保留原回复编号，以及等待名额后读取现场并在取消后释放资源。真实模型请求为零，未运行整局验收；行动与配套发表的统一执行及全局逻辑队列继续按后续单元开展。
