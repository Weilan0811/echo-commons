## 1. 目标与当前判断

当前正式文档尚未达到这一目标。上一轮追加说明恢复了部分内容，但五种反思图、关系规则、模型输入语义、接口使用与运行状态仍缺少完整设计。正式文档继续依赖根目录方案。此前的文档完成结论不足，应以本方案的内容验收重新判断。

本轮源码复核也发现实际差异：自身历史 Thought 没有进入对话快照，连续性压缩允许已有批次以 NoOp 结束，partial 图的恢复入口尚未找到。测试通过不能证明这些要求已经实现。具体证据和判断边界见配套复核记录。

## 2. 两类文档及权威关系

| 类型 | 读者需要完成的事情 | 内容要求 |
|---|---|---|
| 设计说明 | 不看源码，理解目标、对象、规则、完整流程、失败后续和扩展约束；可据此实施 | 完整说明业务语义、输入输出、状态、条件、算法和例子；不能用源码引用替代解释 |
| 开发说明 | 查找实现、启动、配置、调试、验证和接入 | 简洁步骤与源码索引，提供实际命令、接口例子及排错入口 |

设计内容拥有三个独立状态：已确认设计、当前实现、已知差异。一个功能尚未接入，也可以拥有完整的已确认设计。功能状态不能用来决定是否保留设计内容。

每项规则指定一份权威设计说明。其他文档链接对应章节并解释本地用途，避免重复定义。源码是实际行为证据；已确认设计是实现应遵守的依据。冲突进入差异登记，经裁定后修正相应对象，不能直接按当前代码删改原设计。

文档中的字段说明包含业务意义、类型、必填性、范围、默认值、来源和修改责任。完整机械字段可从契约生成；关键字段的意义和规则由设计说明承担。

## 4. 设计说明必须展开到什么程度

每项独立功能都应有：目的和设计理由；范围与相邻职责；核心对象及关系；输入材料与输出结果；状态和转换条件；正常流程；分支与失败后续；持久化与事务；重复提交和版本规则；预算与可见性；完整运行例子；当前实现和验证证据。

并非每份文档机械地重复相同标题。状态机与数值算法需要自己的图表或公式；小型功能可集中在一个章节；reflection 的五种图采用独立文档，便于完整解释。

每个反思图必须逐个说明：

1. 为什么需要该图，来源单位和触发条件是什么。
2. 来源选择、观察范围、材料预算以及没有材料时如何处理。
3. 完整拓扑；每条条件边由哪项决策激活。
4. 每个节点的执行方式、输入字段、前驱、输出动作、候选与证据要求。
5. 聚合组合哪些实际产物，候选数量、冲突与空结果如何处理。
6. 图级审核检查什么，允许写入哪些事实或派生视图。
7. 原子提交、版本、覆盖、重复和失败恢复规则。
8. 至少一条完整运行例子，以及对应的已实现和未实现范围。

diary_compose 与 view_refresh 同样展开完整已确认契约，状态附在具体步骤上。禁止仅以“未实现”替代已确认设计。

## 5. 信息恢复与源码复核顺序

### 阶段一：保全信息并建立追踪

先使用 [信息清单](06-documentation-inventory.md) 建立条目去向。参考根目录 01—05、任务 1 的有效行为确认、重建前工程文档及当前源码。旧工程说明可从 `a78c686^` 的 Git 快照读取；旧路径只作为调查线索，长期文档改用当前对象与路径。

原始资料保持原样。每项旧信息只能登记为迁移、已经明确废弃、已确认未来设计、需要裁定或重复引用，必须写明去向和理由。没有去向的有效信息不能随原文档一起删除。

### 阶段二：设计与代码逐项比较

按照范围、入口、输入、规则、输出、事务、异常和恢复检查完整调用链。领域函数存在并不足以证明正式任务会使用它；测试调用某个底层入口也不足以证明模型消费者能够抵达该规则。

比较同时记录“设计有、实现缺”“实现有、设计缺”“设计和实现相冲突”“实际验证不足”。复核记录允许新增差异，不允许为了全部通过而缩小条目要求。

本轮已经执行一次重点复核和真实非模型测试，详细范围见 [源码复核](06-implementation-review.md)。这是当前证据，不代表所有规则已经完成逐项认证。清单中的待查项目继续保留明确任务。

### 阶段三：先重建设计说明

按系统、身份、交流、观察、状态关系、记忆、五种反思图、Agent、任务、持久化、诊断、活动接入的顺序写入长期设计。每份说明以无源码阅读检查，确认读者能解释正常及失败流程。

发现实现偏差时保留原有效设计和实际差异。修改代码属于后续单独任务，本方案没有授权以代码现状覆盖设计，也不启动实现修改。

### 阶段四：补齐参考与开发指南

从真实 OpenAPI 与类型契约核对完整 HTTP 定义；从 Settings 与模型登记核对配置；从加载器核对资源格式；从 SQL 生成数据库参考。为前端、作者、运行维护和扩展开发各提供可执行例子。

源码导航只承担定位，测试入口只承担证据。详细规则链接到长期设计章节，不把读者送回临时方案才能完成理解。

### 阶段五：整体审核和归档

用信息清单逐项验收，处理全部有效旧信息去向，验证长期链接和文档间一致性。更新 `server/README.md` 与正式索引，再删除已经被完整替代的重复工程说明。根目录重建资料归档后仍可作为历史证据。

## 6. 文档完成条件

| 检查 | 通过要求 |
|---|---|
| 独立性 | 暂时忽略根目录重建资料，仅凭 server 内文档能够理解与使用后端 |
| 设计完整性 | 信息清单每项有明确章节；状态、条件、算法、契约和失败后续都有解释 |
| 五图完整性 | 五种图各有完整用途、拓扑、输入输出、审核、消费者和状态说明 |
| 代码一致性 | 每项实现声明有当前调用链与证据；差异公开登记，未查内容不标成符合 |
| 接入可用性 | 前端按指南能建立多人场景、发消息、轮询、读取私有边界和处理错误 |
| 运行可用性 | 配置、路径、示例、模型失败、恢复、导出和安装方法实际成立 |
| 信息保留 | 所有有效原规则有去向；被删除项目有已经确认的废弃依据 |
| 单一权威说明 | 相同规则只在指定位置定义，其他文档采用链接与局部解释 |
| 状态诚实 | 已实现、已确认未实现、偏差和缺少验证分别登记 |

链接存在、字段生成一致、测试通过分别证明自己的检查范围，不能单独证明文档完整或实现完全符合设计。本方案不使用行数或文件数量判断完整性。
