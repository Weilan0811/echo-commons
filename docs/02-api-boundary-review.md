# 前后端接口范围与缺口评估

日期：2026-10-04。状态：评估与契约建议，尚未实施。

依据：[前端接口缺口](../frontend/docs/02-backend-interface-gaps.md)、[页面设计](../frontend/docs/03-page-design.md)、[推进计划](01-project-roadmap.md)、当前后端路由和查询服务。当前实际接口继续以 [HTTP 参考](../server/docs/reference/http-api.md)、[管理接口](../server/docs/reference/management-api.md) 和 [OpenAPI](../server/docs/reference/openapi.json) 为准。

## 1. 结论

后端的聊天发送、消息隔离、轮次查询和管理诊断基础已经具备。需要调整的是玩家日常使用的读取入口和成员操作范围。

建议采用一个明确的分工：

- `/api` 提供本地玩家选择、社群发现、角色公共身份、自己的会话、可见消息、轮次和已读状态。
- `/internal` 提供社群范围的完整记录、成员历史、角色私人材料、诊断、测试管理操作和材料导出。
- 玩家页面的所有数据都能从 `/api` 获取。管理页面有自己的完整对象列表，不再依赖玩家会话列表。
- 创建玩家、社群和角色继续支持现有本地测试流程；涉及社群的玩家操作明确发起者。任意增删其他主体的会话成员关系归入管理操作，玩家端只操作自己的成员关系。

最需要补充的能力是：玩家和社群发现、玩家会话列表、会话详情与当前参与者、最新消息与向上翻阅历史、回复来源读取、服务端已读记录。会话预览应与玩家列表一起返回，首次打开聊天应直接取得最新可见消息。

管理端现有的私人信息范围符合本地测试需要。当前没有账户认证，`player_id` 是选定的测试身份；上述业务范围校验只能保证按照这个身份读取和操作。远程访问安排仍按推进计划单独确定。

保留已有的正确行为：消息受众绑定发生时的成员区间；离开期间的消息不会因重新加入而可见；轮次按照玩家可见来源过滤；发送重试使用同一 `client_message_id`；管理操作通过正式业务服务执行。

## 3. 现有公开接口如何调整

下表描述建议，当前行为见 HTTP 参考。

| 现有能力 | 建议范围和调整 |
|---|---|
| 创建玩家 | 保留为本地测试身份注册入口。创建完成返回实际 `PlayerView`，与玩家选择目录配合使用 |
| 创建社群 | 保留。增加发起者 `player_id`，创建社群与加入该玩家在同一事务完成，避免产生玩家不能进入的空社群 |
| 玩家加入社群 | 保留。路径中的 `player_id` 就是当前选定的本地测试主体；文档明确该操作用于自身加入 |
| 模板列表 | 保留公共展示信息；不增加人物提示、初始私人记忆或模型配置 |
| 创建角色实例 | 保留本地世界配置流程。增加发起者 `player_id`，要求其属于社群，模板和实例归属仍由正式服务检查 |
| 社群角色列表 | 增加读取玩家，要求其属于社群；补充实例对应版本的公共显示名，支持公共头像字段 |
| 创建会话 | 增加发起者 `player_id`，要求其属于社群且包含在 `actors` 中。直接会话保持一个玩家与一个角色；群聊使用明确的同社群参与者 |
| 社群全量会话列表 | 完整范围迁到管理侧。玩家侧采用第 4 节的玩家会话列表，包含可选社群筛选；前端尚未调用旧列表，实施时统一更新使用指南和类型 |
| 任意会话成员加入、离开 | 通用 `actor_kind/actor_id` 路径迁到管理侧。新增玩家自身成员操作，详见第 7 节 |
| 消息发送 | 保留 202 与客户端标识的幂等规则；补充可区分的冲突码和历史回复规则。普通发送无需增加会话全局序号的期望值 |
| 消息增量读取 | 保留游标协议和服务端可见性检查，另补最新历史读取。两个读取方向由不同游标表达 |
| 轮次读取 | 保留可见来源过滤。补充 `input_message_ids`，让前端把当前发送与对应回应状态联系起来，不公开任务快照与内部错误详情 |

新增创建请求中的 `player_id` 仍来自统一的测试主体来源。将来有账户凭据时，后端从凭据取得主体，届时再调整传参方式。

## 4. 需要新增的玩家读取接口

除本地玩家目录外，下列读取都按 `player_id` 检查实际范围。对象不存在或不属于该玩家的读取范围时返回 404；范围存在而列表为空时返回 200。读取无副作用。

新增对象列表统一返回 `items`、`cursor`、`has_more`，默认 `limit=50`，范围 1—200。游标绑定玩家、查询种类和筛选条件；结束时 `cursor=null`。现有消息增量游标继续使用原协议。

| 建议路径 | 请求与响应 | 用途及可见范围 |
|---|---|---|
| `GET /api/players` | 分页 `PlayerView` | 本地测试身份选择目录，只返回身份、名字和创建时间。它明确属于当前本地无账户模式 |
| `GET /api/players/{player_id}` | `PlayerView` | 页面刷新后恢复当前测试主体，无需扫描全体玩家 |
| `GET /api/communities` | 必填 `player_id`；`scope=joined\|available`，默认 `joined`；返回社群卡片及自身成员状态 | 社群切换与加入入口。`joined` 返回已加入社群；当前本地模式下 `available` 返回尚未加入、可通过现有业务入口加入的社群 |
| `GET /api/communities/{community_id}` | 必填 `player_id`；`CommunityView` | 已加入玩家读取社群名、世界时间、时区和运行状态，供顶栏展示 |
| `GET /api/communities/{community_id}/members` | 必填 `player_id`；分页公共主体信息 | 已加入玩家在创建群聊时选择成员，不获取角色关系、状态历史或记忆 |
| `GET /api/conversations` | 必填 `player_id`；可选 `community_id`；`membership=current\|past\|all`，默认 `current`；`status=active\|archived\|all`，默认 `active`；分页 `PlayerConversationSummary` | 返回该玩家参与过的会话，默认显示当前加入且活跃的会话；历史筛选保留离开或归档会话的阅读入口 |
| `GET /api/conversations/{conversation_id}` | 必填 `player_id`；`PlayerConversationSummary` | 直接打开会话链接、刷新页面及更新本会话状态；要求至少存在该玩家的真实历史成员区间 |
| `GET /api/conversations/{conversation_id}/members` | 必填 `player_id`；分页当前参与者公共身份 | 当前成员读取当前名单，用于提及、指定受众和群聊标题。离开的玩家不读取当前名单；历史发送者身份由消息视图提供 |
| `GET /api/conversations/{conversation_id}/messages/history` | 必填 `player_id`；可选 `older_cursor`、`limit`；返回最新可见消息及向前翻页信息 | 首次进入直接读取最新一页，随后向上读取历史；明确契约见第 5 节 |
| `GET /api/conversations/{conversation_id}/messages/{message_id}` | 必填 `player_id`；玩家消息视图 | 加载回复引用或定位单条消息。消息必须对该玩家可见；不通过管理详情补读 |

社群发现卡片只需 `community_id`、`name`、`timezone`、`status` 和自身加入状态；完整世界信息由加入后的详情提供。社群列表与玩家会话列表都在后端筛选和分页，前端无需读取全部社群、全部会话，再逐个请求成员。

### 4.1 公共主体信息

建议使用共享的公共展示类型：`actor`、`display_name`、`avatar_url`。玩家和角色都通过这个类型参与显示与选择。

`avatar_url` 为可空字符串，含义为浏览器可以读取的图片地址；本轮没有图片时返回空值。它在模板资源中只有一个来源，实例视图按实际绑定模板版本取得，前端继续根据 `character_id` 生成回退颜色。增加字段时同时修改资源模型、加载器和返回类型，单独在视图中长期返回空值无法让真实资源被使用。

角色实例的 `display_name` 也从绑定模板版本取得。当前 `CharacterView` 缺少名字，前端需要再关联模板列表；直接返回公共展示投影可以减少页面承担的对象转换。

玩家消息保留已有 `sender` 来源类型，并补充 `sender_display` 公共展示信息。历史消息中已离开的发送者仍能被正确显示。系统来源继续使用独立的 `system` 类型，由系统消息契约提供展示标签，不伪装成玩家或角色。

### 4.2 玩家会话概要

建议 `PlayerConversationSummary` 使用以下结构职责：

| 字段 | 含义 |
|---|---|
| 原 `ConversationView` 字段 | 会话标识、社群、类型、状态、成员版本与创建时间 |
| `self_membership_status` | `current` 或 `past`，由后端根据真实区间计算 |
| `self_membership_id` | 当前成员区间编号；已经离开时为空 |
| `can_send` | 该玩家是否满足实际发送资格，考虑当前成员区间、会话归档和正式业务规则；每次发送仍重新检查 |
| `direct_peer` | 直接会话对方的公共身份；群聊为空。历史直接会话使用对应真实参与身份 |
| `last_message` | 该玩家可见的最后消息概要，包含编号、发送者公共信息、`text_preview`、可见性与时间；没有可见消息时为空 |
| `last_visible_message_at_utc` | 最后一条可见消息的时间；没有时为空 |
| `last_read_sequence`、`unread_count` | 该玩家的已读位置与未读数量；规则见第 6 节 |

概要无需携带社群完整会话成员历史，也无需为每个列表项另请求状态接口。群聊当前名单只在进入该会话时读取；直接会话列表通过 `direct_peer` 展示对方。

列表按玩家可见的最后消息时间倒序排列，没有消息时使用创建时间，再用会话编号确定同时间顺序。重新刷新从第一页开始，并按会话编号去重。

私人消息不得改变无关玩家的预览、未读数量和最近活动排序。排序不能直接使用会话的全局 `updated_at_utc`。概要也不增加全局 `next_sequence`；前端轮询所需位置由后端消息游标表达。

## 5. 最新消息和历史翻页需要独立契约

缺口清单把预览、未读和直接打开最新消息归为同一会话状态需求。其中，最新一页消息仍需要消息读取接口：一条摘要不足以呈现聊天上下文，也不足以继续向上翻页。

建议历史接口响应：

```json
{
  "messages": [],
  "older_cursor": null,
  "has_older": false,
  "poll_cursor": "后端返回的增量读取游标"
}
```

此例只说明响应结构。实际消息来自正式存储。

规则：

1. 首次不传 `older_cursor`。后端在同一读取范围内取得当前扫描终点，从末尾选取最多 `limit` 条玩家可见消息，响应按消息序号升序排列。
2. `older_cursor` 绑定玩家、会话、读取终点与历史位置，继续读取更早的可见消息。它与现有增量游标分别使用，前端不解析内部编码。
3. 首次响应的 `poll_cursor` 接在已经扫描的终点之后，交给现有 `GET .../messages` 继续读取新消息。后续历史页不覆盖增量读取位置。
4. 没有可见消息时仍返回有效的增量游标；读取历史期间的新消息由增量读取取得，不要求重新扫描全部历史。
5. 历史消息、单条读取、最后消息概要、未读计算和轮次来源共同使用正式成员区间与实际受众规则。最新读取不能只过滤全局最后一页，否则最后一批都是私人消息时，会把实际存在的玩家历史错误地显示为空。

玩家消息视图建议增加 `recipients`：仅私有消息返回发生时的实际接收主体，使用公共身份，避免依靠当前名单解释历史私密受众。公共消息不额外返回完整受众区间。该字段允许显示“发送给谁”，不携带管理侧的任务、审核和成员历史详情。

回复指向较早消息时，单条消息接口补充引用预览，仍检查读取玩家可见性。关于重新加入后的旧消息回复，建议允许回复自己真实可见的旧经历，同时重新检查当前发送资格与当前受众；接受服务改用共同的历史可见性规则。引用预览对每位阅读者分别校验，其他玩家看不到原私人消息时不返回其正文。

## 6. 服务端已读记录

新增：`PUT /api/conversations/{conversation_id}/read`。

建议请求：

```json
{"player_id":"当前玩家编号","through_message_id":"已展示消息编号"}
```

返回 200，包含 `conversation_id`、`last_read_sequence`、`unread_count`。没有可见消息时前端无需发送此请求。

- 后端检查该消息属于会话并对玩家可见，取得其正式序号。未知或不可见消息返回 404。
- 已读位置按 `(player_id, conversation_id)` 保存，更新取原值与请求值的较大者。两个标签页同时提交时不会把阅读位置往回改；重复或较旧的标记返回当前结果。
- `unread_count` 统计已读位置之后、属于真实可见范围且发送者为其他主体的消息。自己的消息不计入未读；私有消息只计入实际可见接收者。数量通过可见消息计算，不通过序号相减。
- 会话列表读取、消息抓取和后台轮询都不自动标记已读。前端在玩家实际查看对应消息时提交。
- 离开后仍能阅读原经历并推进相应已读位置；重新加入保留原位置，同时继续排除离开期间的消息。
- 新增数据库迁移保存记录，保留现有材料。既有数据没有可靠阅读记录，默认已读位置为 0，明确把既有可见且非本人消息计为未读，不推断过去已经阅读。

最新消息与预览属于聊天基本体验，建议列为 P1；跨标签页已读及未读数量列为 P2，但应按同一玩家会话概要契约设计。

## 7. 成员操作、版本与幂等

### 7.1 玩家操作与管理操作分别表达

建议玩家端使用：

- `PUT /api/conversations/{conversation_id}/membership`：请求明确 `player_id`，只重新加入自己的已参与会话，检查社群和会话资格。
- `DELETE /api/conversations/{conversation_id}/membership`：查询明确 `player_id` 和 `expected_membership_id`，只结束自己的指定成员区间。

成员操作返回实际成员结果、`membership_version` 与自身成员状态。玩家初次参与由会话创建时的明确 `actors` 或管理加入建立；当前没有邀请业务，不增加邀请流程。

通用成员操作放在 `/internal/communities/{community_id}/conversations/{conversation_id}/members/{actor_kind}/{actor_id}`。管理页面可以增删同社群的指定玩家或角色，仍通过正式服务检查会话类型和归属。

直接会话的身份和重新加入规则需要一起明确：按指定玩家与角色恢复各自成员区间，不允许把直接会话中的玩家替换为另一个玩家。当前 `join` 只检查加入后的当前人数与类型；两人均离开后，逐人加入也会被“必须恰好两人”的检查拒绝。实施时应将直接会话固定参与身份和当前活跃成员区间分别判断，使用既有参与记录恢复，不让加入次序决定是否能够恢复会话。

### 7.2 期望版本只能发现过期操作

`expected_membership_version` 用于管理成员变动：请求必须携带期望版本，后端在写事务中比较；不匹配返回 409、`membership_version_conflict`，没有写入。

自身退出另绑定 `expected_membership_id`，避免旧退出请求结束重新加入后形成的新区间；版本与区间不匹配分别表达明确冲突。

缺口文档中的“重复提交相同期望版本返回原结果”缺少请求身份。第一次操作成功后版本已经增加，单靠旧版本无法识别重复请求。

需要原操作结果的成员写入增加 `client_operation_id`，保存原请求与结果；相同标识和相同内容返回原结果，内容不同返回 `idempotency_conflict`。检查顺序为请求身份重复检查、当前资格和期望版本检查、执行写入。新版本或新成员区间的操作使用新标识。该记录服务于真实网络重试，不推广到无此需求的读取接口。

消息发送已有 `client_message_id`，继续复用；不要求所有消息带 `expected_membership_version`。另一个人进入会话并不必然让一条正常新消息失效，发送事务已经检查发送者、受众、提及和回复来源。

已读写入通过单调推进实现幂等，无需再保存操作编号。已有反思调度按来源复用的规则、失败图重启的状态限制继续保持各自语义。

## 8. 管理端需要补充和保留什么

### 8.1 补齐管理侧独立对象列表

新增：

- `GET /internal/communities/{community_id}/characters`：分页完整角色实例，支持现有管理详情定位。
- `GET /internal/communities/{community_id}/conversations`：分页社群全部会话，可按 `kind`、`status` 筛选。
- 第 7 节的通用成员加入、离开管理路径。

现有管理接口让角色和会话列表借用 `/api`。玩家列表开始按身份筛选后，管理端必须拥有自己的完整列表。两端可以共用存储查询与公共身份转换，各自的响应范围保持明确。

### 8.2 保留现有私人材料范围和有限操作

消息与轮次详情、任务冻结输入、角色内心、关系证据、记忆、反思图、执行追踪及范围导出继续只提供给管理页面。不能为了给玩家增加参与者或会话预览，直接公开这些管理响应。

手动封段返回 200 和实际材料段；反思安排及符合条件的失败图重启返回 202 和真实运行编号。页面继续根据 `outcome` 与图状态判断执行情况。已完成来源被复用时也可能返回 202，不能只根据状态码决定显示“执行中”。

模型密钥、供应商路由和完整模型捕获不进入前端接口。暂无对应前端需求的管理写操作无需扩张。

### 8.3 后续阶段的管理需求

| 阶段需求 | 接口设计方向 |
|---|---|
| 人工评价真实材料与整理结果 | 独立管理反馈记录，关联实际消息、材料段、图或记忆结果及评价身份；先定义记录契约。评价与角色经历分别保存 |
| 社群暂停、恢复和世界时间控制 | 已有 `CommunityService.update`，需要页面控制时提供管理 `PATCH /internal/communities/{community_id}`，要求 `expected_state_version`；不提供倒退世界时间 |
| 会话归档 | 已有正式归档服务。管理页面需要结束测试会话时提供明确归档操作，保留历史并取消相应未完成回应 |
| 部分成功补做、日记和认识刷新 | 等对应正式运行与保存服务具备后确定操作契约；当前不将空入口列为可用接口 |

这些需求分别属于推进计划中的记忆质量和长期生活阶段，不阻塞当前聊天与已有诊断页面接入。

## 9. 错误与访问边界

本地阶段无需为了补齐状态码列表而新增登录系统。当前缺口清单第 8 节已经说明凭据引入后再设计 401，应从当前 P2 清单移到部署依赖中。

当前优先调整具体业务错误码：

| 状态与错误码建议 | 页面行为 |
|---|---|
| 400 `invalid_request` 或 `invalid_cursor` | 指出输入或分页位置无效，重新取得相应第一页 |
| 404 `not_found` | 对象不存在或不属于读取范围，停止展示该对象 |
| 409 `idempotency_conflict` | 保留输入，指出同一操作标识被用于不同内容，禁止自动换标识重试 |
| 409 `membership_version_conflict` / `membership_interval_conflict` | 保留输入，重新读取成员状态，由用户按新状态继续操作 |
| 409 `conversation_archived` | 刷新会话状态并停止发送 |
| 422 | 继续使用现有字段错误结构与前端归一逻辑 |
| 500 / 503 | 保留当前协议，按实际可重试性处理 |

公共路由也应在 OpenAPI 中声明实际 400、404、409、500、503 响应模型。当前管理路由已有这组声明，公共路由主要声明成功和自动生成的 422，生成类型难以表达实际业务错误。

未来引入凭据时，401 表示凭据缺失或失效；对象范围拒绝可统一返回 404，403 用于已认证主体不能执行某类操作。对象归属校验与账户访问控制各自负责不同判断。部署确实采用跨域凭据请求时，同时更新身份来源、请求凭据方式和 CORS（跨域访问配置）；当前只允许 `Content-Type` 请求头的配置无法直接承接 `Authorization`。

账户体系和管理权限属于远程部署前的工作，当前评估不增加账户表、权限框架或兼容模式。

## 10. 活动接口的正确范围

[活动设计](../server/docs/design/activity-integration.md) 明确活动模块、HTTP 接口、队列和数据库表均未实现。缺口清单提到的 `create`、`observe`、`legal_actions`、`validate`、`apply`、`summarize` 未在该文档中形成实际 HTTP 契约，不能据此开展已确定接口的接入。

阶段五需要约定的玩家入口包括：活动创建、按玩家可见范围列出活动、读取自己的观察与合法动作、提交动作、读取结果。建议围绕 `/api/activities` 及活动编号组织；创建请求表达社群、玩法、规则版本与参与者，提交动作包含客户端操作编号、期望状态版本和行动机会编号。

玩家收到自身观察视图，私人手牌只属于该主体；完整权威状态留在后端和管理范围。`validate`、`apply` 与 `summarize` 属于内部规则执行职责，不单独成为前端调用步骤。前端提交一次动作，后端在同一事务检查并执行。

活动与聊天各自有状态、读取位置和任务结果。活动通知须保存正式事件来源，棋局推进不等待聊天模型生成。具体路径、枚举和玩法字段随飞行棋业务契约确定。

## 11. 建议实施优先级与验收

| 优先级 | 交付内容 | 验收重点 |
|---|---|---|
| P1 | 玩家与社群发现、公共主体信息、玩家会话列表及详情、当前参与者、管理独立列表与成员操作范围 | 玩家界面零 `/internal` 请求；列表不返回未参与私聊；离开和归档历史仍有读取入口；深层链接刷新可恢复 |
| P1 | 最新可见消息、历史翻页、单条消息与回复来源、轮次来源编号 | 长历史首次进入直接到最新内容；大量私人尾部消息不造成空历史；向上翻页与新消息读取同时正常；不可见引用不返回正文 |
| P1 | 后台错误分类、重试与恢复功能完善，扩充现有管理诊断响应 | 具体原因跨层保留，暂停与取消状态正确；原快照不变，修正请求包含具体错误码；捕获关闭后仍能查明等待、重试耗尽及处理决定；见 [恢复设计](../server/docs/design/errors-and-recovery.md) |
| P2 | 已读记录与未读数量、成员写入的版本及重复请求语义、明确业务错误码 | 两个标签页阅读位置单调推进；本人发送不增加未读；私人消息不影响无关玩家摘要、排序和未读；旧退出操作不会删除新成员区间 |
| P2 | 公共头像资源字段及加载支持 | 字段来源明确、绑定正确模板版本，空值回退，无需新增图片资产管理系统 |
| 部署前 | 与实际远程使用方式对应的凭据和管理访问控制 | 测试者不能选择其他玩家身份读取；普通玩家不能读取或执行管理请求 |
| 后续业务阶段 | 评价、长期生活管理、活动契约 | 按对应真实数据和正式运行服务验收，业务结果保留来源 |

最新消息和列表摘要从原 P2 提升为 P1；身份状态码移到部署依赖；成员并发由原 P3 提升为多人测试需要的 P2。无需新增逐字输出、WebSocket 或 SSE，现有轮询方式可以承接上述设计。

接口实施时共同更新路由、响应模型、OpenAPI、前端生成类型与接入指南。缺口清单保留规划，参考文档只记录完成并验证的行为。头像回退链和管理适配的完成状态由实际代码记录。

接口评估验证：后端契约生成检查通过；HTTP 与管理接口的 9 项非模型测试通过，3 项模型测试未运行；额外真实 HTTP 检查使用独立临时 SQLite 数据库，验证会话列表范围、成员离开与重入、直接会话参与身份、历史读取、旧区间回复、幂等冲突码与序号含义。前端旧类型为 1132 行，当前同工具生成结果为 5939 行，确认尚未同步。未修改业务实现、已有接口参考或用户正在修改的缺口清单。

## 12. 补充：后台错误分类、重试与恢复

本项与玩家读取接口调整共同列入 P1，支持真实聊天和反思测试中的故障处理。原项目与当前后端的源码比较、具体恢复规则及验收以 [错误分类、重试与恢复](../server/docs/design/errors-and-recovery.md) 为唯一详细说明；本次完成需求整理，功能尚未实施。

恢复工作包括：保留具体错误码与完整恢复动作；正确处理暂停、取消、忽略和次数耗尽；保持持久快照不变，只给模型可修正的审核错误附独立提示；增加捕获关闭后仍可查询的正式恢复历史。部分要求原项目也没有完整实现，按同一设计完成。

前端新增需求集中在已有管理任务、反思节点和追踪详情：显示原因、类别、实际动作、等待时间、下次执行时间、次数耗尽及实际修正提示。复用现有 `/internal` 查询，不公开内部恢复材料。玩家页面依据公开轮次状态展示等待、完成、沉默或失败；消息已接受后发生的后台失败不自动重发玩家消息。

实现时共同更新管理响应、OpenAPI、前端类型和展示，管理页面开发可以与后端恢复工作并行。此次比较未重新执行接口评估中的测试，也未验证尚未实施的恢复流程。
