# 玩家与管理 API 接口修正实施方案

日期：2026-10-04。状态：已审核并完成代码实施与验收；代码保留在本地工作区。

需求依据为 [前端接口缺口](../frontend/docs/02-backend-interface-gaps.md) 和 [页面设计](../frontend/docs/03-page-design.md)。本文件负责修改范围、具体契约、模块职责、实施步骤和验收；项目安排见 [推进计划](01-project-roadmap.md)。当前实际接口继续以 [HTTP 参考](../server/docs/reference/http-api.md)、[管理接口](../server/docs/reference/management-api.md) 和 [OpenAPI 契约](../server/docs/reference/openapi.json) 为准。

## 1. 交付结果与范围

完成后，玩家页面能够通过 `/api` 完成身份选择、社群发现、角色与参与者展示、自己的会话浏览、最新消息读取、历史翻页、回复、轮次查询、已读标记及自身加入和退出。管理页面通过 `/internal` 获取独立完整列表，操作指定主体的成员关系，并继续读取已有私人材料与诊断。

本次一并完成原评估中的剩余 P1、P2：后端业务规则、公开和管理路由、请求与响应模型、数据库迁移、模板公共头像字段、必要测试、接口参考、接入指南、前端生成类型及受影响的现有调用。完整玩家和管理页面的布局与交互由前端任务完成。

当前采用本地测试身份，`player_id` 表示选择的玩家。对象范围校验按该身份执行。账户凭据与管理权限按远程部署任务安排；活动、人工评价、世界时间管理、长期生活功能及推送协议按各自任务安排。

错误与恢复机制已通过本地提交 `b09a1ba` 完成，设计见 [错误与恢复](../server/docs/design/errors-and-recovery.md)，实施记录见 [恢复实施方案](03-errors-and-recovery-implementation-plan.md)。前端类型也已随该提交同步。本轮在这些实现上修改 API，不重新实施恢复机制。

保留已有消息接受的 202 语义、原消息客户端标识、真实成员区间与受众、后台回应和反思执行规则、冻结任务快照及已批准产物。

## 2. 实施顺序

| 步骤 | 修改内容 | 完成标准 |
|---|---|---|
| 1 | 共同可见性、公共身份、成员规则和错误契约 | 同一规则有明确所属模块，所有读取和写入入口调用共同实现 |
| 2 | 已读记录、成员操作记录及数据库迁移 | 新库和现有数据库升级正确；原消息、成员历史、任务、材料及配置保留 |
| 3 | 玩家发现、创建资格、会话概要和管理独立列表 | 玩家读取按身份筛选；管理对象列表独立完整；列表在后端分页 |
| 4 | 最新消息、历史翻页、单条读取、回复及轮次来源 | 首次直接取得最新可见消息；历史与增量游标各自工作；引用正文遵守可见性 |
| 5 | 已读写入及玩家、管理成员操作 | 已读位置单调推进；成员重试返回原结果；过期请求不修改新状态 |
| 6 | 接口契约、文档、类型及现有调用同步 | OpenAPI、实际响应、前端类型和接入示例一致，旧公开操作退出使用 |
| 7 | 真实验证与必要回归 | 达到第 10 节验收要求；既有聊天、私人隔离和恢复诊断继续工作 |

每一步验证对应规则，最后进行共同验收。P1、P2 是需求优先级，本轮交付包含两者，不拆成能力不完整的过渡接口。

## 3. 步骤一：集中规则与模块职责

### 3.1 规则的唯一实现位置

| 逻辑 | 所属位置 | 入口职责 |
|---|---|---|
| 成员区间、实际受众与历史消息可见性 | 现有 `modules/perspective/` | 消息、历史、预览、未读、引用和轮次调用共同规则 |
| 公共主体身份与模板版本展示 | `modules/characters/services/identity.py` 和所属身份查询模块 | 明确转换玩家、角色与系统来源；公开响应复用公共展示投影 |
| 玩家会话查询、概要与消息读取 | `modules/conversations/services/` 及对应存储查询 | 服务检查范围并组合响应；存储执行筛选、排序和分页 |
| 会话参与身份、成员版本、操作重复检查和成员变更 | `modules/conversations/services/conversation.py` 及专门成员操作存储 | 玩家与管理入口调用同一业务服务，传入各自明确的操作范围 |
| 社群发现、成员资格与创建者加入 | `modules/communities/` | 创建和角色、会话发起入口复用实际社群成员检查 |
| 已读位置及未读计算 | 对话模块的专门已读服务与存储 | 写入检查消息可见性，查询复用玩家可见消息条件 |
| 分页编码与共同错误响应 | 现有共享分页和 HTTP 错误模块 | 复用通用能力，明确区分对象列表、消息增量和历史协议 |
| 应用组合与路由 | `app/composition.py`、所属 `api/` 和管理路由 | 创建并注入服务；路由校验参数、调用服务、转换响应 |

公共展示投影只包含身份、名字和头像；角色私人上下文、记忆、关系及模型配置保持各自边界。系统发送者保留独立的 `system` 来源，不转换成玩家或角色。

查询服务组合实际存储与公共规则。新增列表直接执行玩家范围筛选，避免先取得全体对象后在路由逐项过滤，也避免为每个会话另发成员或状态请求。一次会话概要响应中的成员、预览与未读使用同一数据库读事务。

共享模块不导入具体路由。成员版本、幂等和可见性规则不分别复制到玩家与管理入口；路由中不增加自行计算版本、未读或受众的业务分支。

### 3.2 共同错误契约

保留 `{"error":{"code":"...","message":"..."}}` 业务错误结构和现有 422 字段错误结构。为实际发生的冲突提供明确代码，不从异常文字解析原因。

| 状态与代码 | 规则 |
|---|---|
| 400 `invalid_request` | 业务输入无效 |
| 400 `invalid_cursor` | 无效游标或游标与玩家、查询、筛选范围不一致 |
| 404 `not_found` 或已有明确对象代码 | 对象不存在，或不属于当前玩家的读取、操作范围 |
| 409 `idempotency_conflict` | 同一客户端标识被用于不同请求内容 |
| 409 `membership_version_conflict` | 管理成员操作的期望版本与当前版本不一致 |
| 409 `membership_interval_conflict` | 自身退出指定的成员区间与当前区间不一致 |
| 409 `conversation_archived` | 当前归档状态不允许发送或成员加入 |
| 422 | 继续使用现有请求字段校验结构 |
| 500 / 503 | 保留现有内部响应、存储故障及可重试语义 |

公开路由在 OpenAPI 中声明实际业务错误响应模型。已有后台恢复错误码及管理诊断保持原规则，API 冲突细分不改变任务恢复决定。

## 4. 步骤二：持久记录与现有数据

### 4.1 已读记录

新增 `conversation_read_positions`（会话阅读位置表），以 `(player_id, conversation_id)` 唯一确定记录，保存 `last_read_sequence` 和更新时间。通过外键保持玩家与会话归属，已读序号允许从 0 开始。

位置更新在写事务中取原值与请求消息序号的较大者。重复和较旧请求返回当前结果；同一玩家的多个标签页不会把已读位置向后修改。

### 4.2 成员操作记录

新增 `conversation_membership_operations`（会话成员操作表），保存 `client_operation_id`、操作来源、社群与会话、实际主体、加入或退出、期望版本或区间、规范请求与原响应结果，以及完成时间。

玩家操作编号以发起玩家为范围；管理操作编号以管理来源和社群为范围。跨会话复用同一范围内的编号时仍比较完整请求，避免把别的会话操作当成原操作。相同编号与相同请求返回保存的原结果，内容不同返回 `idempotency_conflict`。

请求和结果使用明确类型及标准 JSON 序列化保存；直接比较规范请求内容。成员修改、版本变化、相关批次和任务处理、原操作结果保存处于同一事务。失败事务不保存成功结果，不增加成员版本。

### 4.3 迁移及历史参与身份

当前迁移已包含 `0003_task_execution_events.sql`，本轮新增下一份迁移，预计为 `0004_player_api_state.sql`；若实施时已有更高版本，顺延。原迁移保持不变。

旧数据的已读位置默认 0，已有可见且由其他主体发送的消息计入未读；不推断曾经阅读。旧成员操作没有可靠请求编号，不补造重复请求记录。

直接会话固定参与身份依据最初建立的真实成员记录确定；当前活跃区间与固定身份分别判断。升级不修改历史消息、受众或成员区间。旧实现允许发生过的身份替换保留为历史；后续加入只能恢复原始固定参与者，曾被替换主体仍按自身真实区间读取旧经历。

迁移验证使用真实旧版本 SQLite 数据库，检查已有业务记录保留、索引和约束有效、重复初始化正确。本轮不主动升级用户实际运行数据库；实际升级使用既有备份与迁移流程。

## 5. 步骤三：发现、创建与会话概要

### 5.1 新增玩家读取入口

新增对象列表返回 `items`、`cursor`、`has_more`，默认 `limit=50`，范围 1—200；结束时 `cursor=null`。游标绑定查询种类、玩家、对象范围和筛选条件。读取无副作用；范围存在但列表为空时返回 200。

| 方法与路径 | 请求、响应及范围 |
|---|---|
| `GET /api/players` | 分页 `PlayerView`，用于本地测试身份选择；只含身份、名字与创建时间 |
| `GET /api/players/{player_id}` | `PlayerView`，用于恢复已选择的测试身份 |
| `GET /api/communities` | 必填 `player_id`；`scope=joined\|available`，默认 `joined`；分页社群卡片 |
| `GET /api/communities/{community_id}` | 必填 `player_id`；已加入玩家读取 `CommunityView` |
| `GET /api/communities/{community_id}/members` | 必填 `player_id`；已加入玩家读取分页公共主体信息 |
| `GET /api/conversations` | 必填 `player_id`，可选 `community_id`；分页 `PlayerConversationSummary` |
| `GET /api/conversations/{conversation_id}` | 必填 `player_id`；返回自身真实参与过的会话概要 |
| `GET /api/conversations/{conversation_id}/members` | 必填 `player_id`；当前会话成员读取分页当前参与者公共身份 |

社群卡片包含 `community_id`、`name`、`timezone`、`status` 和自身加入状态。`available` 在本地模式下列出尚未加入、符合现有加入规则的社群；详情中的完整世界时间和状态版本供已加入玩家读取。

会话列表增加 `membership=current\|past\|all`，默认 `current`；`status=active\|archived\|all`，默认 `active`。至少具有一个真实历史成员区间的玩家可以读取会话详情和旧消息。离开的玩家不读取当前会话名单，历史发送者由消息的公共身份字段显示。

### 5.2 创建和现有角色读取

| 现有入口 | 修改 |
|---|---|
| 创建玩家 | 保留本地测试注册及实际 `PlayerView` 响应 |
| 创建社群 | 请求增加发起者 `player_id`；检查玩家存在；创建与加入同一事务完成 |
| 玩家加入社群 | 保留现有路径，路径中的玩家明确表示当前测试主体 |
| 模板列表 | 保留公共信息，增加 `avatar_url`；私人材料及模型配置不公开 |
| 创建角色实例 | 请求增加 `player_id`，要求属于社群；正式服务继续检查模板和实例归属 |
| 社群角色列表 | 增加必填 `player_id`，要求属于社群；保持现有数组协议，增加名字和头像 |
| 创建会话 | 请求增加 `player_id`，要求属于社群并包含在 `actors` 中；所有参与者归属由业务服务检查 |

创建直接会话仍要求一个玩家与一个角色；群聊使用明确的同社群参与者。创建请求发起者和后续读取、操作使用同一测试身份来源。

### 5.3 公共身份与头像资源

共享公共类型包含 `actor`、`display_name`、`avatar_url`。玩家头像当前为空；角色名字和头像来自实例实际绑定的模板版本。

`avatar_url` 为可空的浏览器可读取图片地址。在模板资源模型、加载器、目录和公开视图中共同支持该字段；模板缺少字段时为空。使用真实图片资源验证加载与版本绑定，不提供图片上传或新的资产管理接口。

`CharacterView` 增加 `display_name`、`avatar_url`。玩家消息保留原 `sender`，增加 `sender_display`；系统来源使用系统标签。历史中已离开的玩家或角色仍能根据正式身份显示。

### 5.4 玩家会话概要

| 字段 | 含义 |
|---|---|
| 原 `ConversationView` 字段 | 会话标识、社群、类型、状态、成员版本与创建时间 |
| `self_membership_status` | `current` 或 `past`，按真实区间计算 |
| `self_membership_id` | 当前自身成员区间编号；离开时为空 |
| `can_send` | 当前实际发送资格，考虑成员关系、归档及已有正式规则；发送时再次检查 |
| `direct_peer` | 私聊固定对方的公共身份，群聊为空；历史中曾被替换主体读取时使用其实际参与区间对应的对方 |
| `last_message` | 最后可见消息概要：编号、发送者公共信息、最多 160 个字符的 `text_preview`、可见性与时间；没有时为空 |
| `last_visible_message_at_utc` | 最后可见消息时间；没有时为空 |
| `last_read_sequence`、`unread_count` | 正式阅读位置与按可见消息计算的未读数量 |

列表按玩家最后可见消息时间倒序，没有消息时使用创建时间，再以会话编号确定同时间顺序。列表刷新从第一页开始，前端按会话编号去重；分页用于当前列表浏览，不承诺在新增消息期间冻结全列表。

不可见私人消息不得改变该玩家的预览、未读或活动排序。概要不提供全局 `next_sequence`，消息读取位置使用服务器游标表达。

### 5.5 管理独立列表

新增 `GET /internal/communities/{community_id}/characters` 和 `GET /internal/communities/{community_id}/conversations`，使用现有管理分页协议。会话支持 `kind`、`status` 筛选，默认完整社群范围；角色列表提供定位现有管理详情所需的实例概要。

移除旧 `GET /api/communities/{community_id}/conversations` 全量读取入口，玩家改用按身份筛选的 `/api/conversations`。管理列表与玩家列表可以复用存储和公共身份转换，各自范围与响应类型保持明确。

## 6. 步骤四：最新、历史、单条消息和回复

### 6.1 最新与历史协议

新增 `GET /api/conversations/{conversation_id}/messages/history`，必填 `player_id`，可选 `older_cursor` 和 `limit`，默认 50，上限 200。响应使用 `messages`、`older_cursor`、`has_older`、`poll_cursor`。

1. 首次不传 `older_cursor`，在同一读事务取得扫描终点，从终点向前查询最多 `limit` 条实际可见消息，响应按序号升序排列。
2. `older_cursor` 绑定玩家、会话、固定读取终点和更早位置。继续查询更早可见消息；结束时 `older_cursor=null`、`has_older=false`。
3. 首次 `poll_cursor` 接在已扫描终点之后，交给现有增量接口读取新消息。后续历史页 `poll_cursor=null`，前端保留首次建立的增量位置。
4. 首次没有可见消息时仍返回有效 `poll_cursor`。大量不可见尾部消息不造成错误的空历史。
5. 历史查询按可见消息选取数量。现有增量接口继续保留按扫描消息数限制一页、可能返回空页且 `has_more=true` 的协议。
6. 两种游标不能互换；服务端验证查询种类与对象范围。历史游标固定扫描终点，每次读取仍检查实际玩家范围。

使用例子：进入聊天取得最新 50 条和 `poll_cursor`；向上滚动使用 `older_cursor`；同时收到的新消息使用增量 `cursor` 读取。三者共享可见性规则，各自维护读取位置。

### 6.2 单条消息与引用

新增 `GET /api/conversations/{conversation_id}/messages/{message_id}`，必填 `player_id`，仅返回属于该会话且对玩家可见的消息。消息不存在或不可见返回 404。

公开消息视图增加 `sender_display`、`recipients` 和可空的 `reply_preview`。历史私有消息及旧轮次回应的 `recipients` 提供发生时实际接收主体的公共身份；新会话范围消息该字段为空，不返回完整受众成员区间。

`reply_preview` 使用短消息概要，只在原引用对当前阅读者可见时返回。单条消息接口用于进一步加载原文；不可见引用的正文和公共身份预览不进入当前响应。保留既有 `reply_to_message_id` 来源编号。

回复合法性改为使用共同的历史可见性规则：允许当前发送者引用自身真实可见的旧区间消息，同时重新检查当前成员资格、会话状态、受众和提及。离开期间消息不会因重新加入变为可见。

### 6.3 轮次来源

公开 `TurnView` 增加 `input_message_ids`。轮次继续按可见来源过滤；新增数组只包含当前读取玩家可见的输入编号，不公开同一批次中的不可见私人消息编号、任务快照或内部恢复详情。

玩家消息接受后，后台失败通过轮次状态显示，前端不自动重新发送已经接受的玩家消息。

## 7. 步骤五：已读与成员操作

### 7.1 已读入口

新增 `PUT /api/conversations/{conversation_id}/read`，正文为 `player_id`、`through_message_id`。返回 200，包含 `conversation_id`、`last_read_sequence`、`unread_count`。

后端确认消息属于会话且对玩家可见，取得实际序号后推进已读位置。无效或不可见消息返回 404；空会话无需发送已读请求。

未读统计已读位置之后、玩家真实可见且发送者为其他主体的消息。自己的消息不计入，私人消息仅对实际可见接收者计入，数量通过查询计算，不用序号相减。

会话读取、消息抓取和后台轮询不标记已读。离开后可以继续阅读原经历并推进位置；重新加入保留位置，同时排除离开期间的消息。

### 7.2 玩家自身成员入口

| 方法与路径 | 请求 | 行为 |
|---|---|---|
| `PUT /api/conversations/{conversation_id}/membership` | 正文 `player_id`、`client_operation_id` | 重新加入自身已经参与过的会话；检查社群成员和会话资格 |
| `DELETE /api/conversations/{conversation_id}/membership` | 查询 `player_id`、`expected_membership_id`、`client_operation_id` | 只结束自身指定的当前成员区间 |

两种操作返回 200，包含实际 `membership`、操作完成时的 `membership_version` 和 `self_membership_status`。重复请求返回原响应；页面需要当前状态时另读会话详情。

自身加入不要求社群会话的全局成员期望版本，业务服务在事务中检查自身实际状态。已经是当前成员的加入请求返回当前成员，保持版本与区间。新加入创建新区间，封闭原收集批次，使用正式受众与生命周期逻辑。

自身退出先检查请求重复，再检查实际范围及指定区间；区间过期返回 `membership_interval_conflict`，不结束新区间。首次加入通过会话创建或管理操作完成。

### 7.3 管理成员入口

新增 `PUT`、`DELETE /internal/communities/{community_id}/conversations/{conversation_id}/members/{actor_kind}/{actor_id}`。加入正文、退出查询均必填 `expected_membership_version` 和 `client_operation_id`。

操作返回与玩家成员操作相同的成员结果结构。先验证社群与会话归属，再检查重复请求；新请求检查期望版本与成员资格，随后执行并保存原结果。相同期望版本的不同请求不会被当成重复请求。

管理加入已经活跃的主体，在期望版本正确时返回当前成员且不增加版本；管理退出要求存在当前区间。旧版本返回 `membership_version_conflict`。管理可以向群聊加入其他同社群主体；直接会话仅能恢复固定玩家与角色。

移除旧 `/api/conversations/{conversation_id}/members/{actor_kind}/{actor_id}` 通用写入路径，同步更新指南、测试和现有调用。

### 7.4 直接会话身份与成员变化

固定参与身份与活跃成员数量分别判断。创建时检查恰好一个玩家与一个角色；退出后允许暂时零个或一个活跃成员，恢复时逐个加入固定主体。因此双方都离开后仍能重新加入，加入顺序不影响结果。

成员变化继续封闭收集批次，并按现有生命周期处理受影响任务。旧退出的重复请求先返回原结果，不能再次结束新成员区间；未被识别为原请求的旧区间操作返回冲突。

消息发送保留 `client_message_id` 的原请求比较和原事实复用，将内容冲突细分为 `idempotency_conflict`。不要求每条消息携带成员期望版本。已读写入以单调推进保证幂等，不增加客户端操作编号。

## 会话发送范围简化

新发送请求只包含玩家身份、幂等标识、正文、提及与回复来源。删除 `visibility` 和 `recipients` 输入及消息接收服务的指定受众分支，发送时保存全部当前会话成员区间。与部分成员交流通过独立会话完成。

消息读取保留历史 `visibility` 与接收主体投影。数据库中的实际受众、批次和轮次范围、冻结任务及共同读取规则继续使用原记录，保证历史私有内容和已有任务恢复不扩大范围。数据库结构无需变更。

携带已删除发送字段返回 422；新请求复用历史私有消息的标识返回 409 `idempotency_conflict`。公共消息的重复请求仍可在成员离开后返回原确认。验收覆盖独立私聊会话、历史记录读取与检索、旧轮次恢复、成员区间变化、幂等冲突和生成契约。

实施结果：核心业务修改集中于发送请求类型、领域输入类型、路由转换和消息接收服务四个文件。125 项非模型测试与两项真实聊天模型场景通过；扩展反思因 GLM 长期记忆提取请求连续超时未通过完整验收，具体结果见 [后端状态](../server/docs/status.md#会话发送范围简化验收)。接口类型、数据库参考说明和相关设计、接入及页面文档已同步更新。
