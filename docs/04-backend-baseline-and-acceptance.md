## 1. 版本初始值

新基线中的有效版本从以下初始值开始。修改生产者、消费者、持久化、测试参考材料与文档引用，删除旧格式分支。

| 类型 | 新初始值 | 规则 |
|---|---|---|
| 服务与发行包 | `0.1.0` | 包元数据与服务返回一致 |
| 人物模板目录、角色子资源、通用行为契约 | `0.1.0` | `status` 单独表达草稿或有效状态 |

| 对话输出契约 | `character_message.v1` | 字段由新契约定义 |
| 反思节点输出契约 | `reflection_node.v1` | 保留已实现节点输出语义 |
| Prompt 布局 | `1` | 模型输入来源与布局统一重新编号 |
| Harness | `harness-v1` | 保留有效执行算法，重新定义当前版本 |
| 检索策略 | `sparse-v1` | 新实例与观察范围下的全文检索 |
| 测试参考材料内容 | `0.1.0` | 更新关联模板、契约与布局版本 |
| 数据库结构 | `0001_initial.sql` / `schema_version = 1` | 一次建立有效结构 |
| ADR（架构决策记录） | `0001` 起 | 只登记当前有效决定 |

类名使用 `ContextSnapshot`，删除 `ContextSnapshotV2`、`ContextSnapshotV3` 的演进命名。版本号只在真实格式与引用中表达。

各资源声明自己的内容版本；公共运行常量由所属模块提供，其他模块引用该定义。避免在多个文件独立维护同一个 schema ID（格式标识）。

下列值是运行事实，使用真实初始状态和实际变化次数：

- 新建角色状态版本从 `0` 开始，实际修改时递增。
- 新任务尝试次数与租约代次从 `0` 开始，领取时递增。
- 首条消息序号从 `1` 开始，后续提交递增。
- 成员区间、快照 ID、来源 ID 与追踪 ID 由实际操作生成。
- 已有内容摘要和来源版本按真实材料生成，继续参与重复处理与过期判断。

依赖库版本、Python 版本、模型供应商名称与模型版本保持其真实含义。`docs/temp_doc/` 的原始材料和用户已有实验数据库保持原样；它们不属于新有效版本集。

## 2. 新数据库的建立

新默认数据路径为 `server/data/echo-commons.sqlite3`，相对位置按显式配置解析。旧 `echo.sqlite3` 与现有实验文件不被新程序选择、修改或删除。

`0001_initial.sql` 从改造后的有效模型建立全部表。当前 `0001` 至 `0016` 的迁移文件在生成并验证新初始结构后删除。源码不保留旧表、旧格式转换或第二套迁移运行路径。

字段、实体关系、索引、状态、事务和保存规则统一定义在 [05 数据库设计](05-database-design.md)。初始 SQL 按业务分节，不重新执行历史演进。

新结构合并社群运行状态、实例可用状态、消息幂等请求、任务快照及 Thought 来源元数据，删除无独立作用的重复记录。成员区间、实际消息受众、精确来源、参与决定和已有反思对象保持独立职责。数据库实现必须按 05 逐表检查必要性及真实消费者。

角色输入共用 ActorRef 批次，窗口为 0 时在输出事务直接结束收集。自动角色接话、活动表与 ActivityTask 不在本次实现范围；初始数据库不为它们创建空执行对象。

## 5. 验证方法

纯领域规则直接使用正式对象。存储验证使用真实临时 SQLite。API 与 Runtime 使用正式服务、真实事务和正式提案审核。需要生成内容的场景使用真实配置模型。

禁止用 Mock、Fake、Stub（模拟与替身）代替模型、存储或业务服务来通过验收。可以直接构造真实 Proposal 测试审核与提交规则，这类测试只证明规则与持久化；端到端模型能力必须另有真实调用证据。

真实模型输出的验收检查契约、身份、来源、读取边界与事实结果，不要求某句文字固定。纯规则与 SQLite 验证无需模型，完整模型场景必须在完成报告中给出实际结果。

| A25 | 玩家等待窗口与角色零窗口 | 玩家只合并窗口内消息；角色批次在提交事务直接 sealed，共用主体结构 |

| A27 | 角色批次与因果来源 | 保存所属轮次；本次不自动创建连续接话，窗口与触发资格分别检查 |

| A29 | 合并后的任务与 Thought 存储 | 重启和重试使用原快照；Thought 清除文本后来源身份仍有效，原文本不能再次提供 |

## 8. 最终交付

完整交付包括新代码、新初始 SQL、真实资源、新配置、新接口、正式开发工具、修订后的工程文档与验收报告。

验收报告记录日期、实际模型与路由、执行命令、通过或未通过场景，以及必要的运行来源 ID。没有真实执行证据的能力明确记为未完成。已实现功能与仍未实现反思消费者分别记录。

项目启动后没有固定玩家或角色实例；用户或开发工具通过显式创建操作建立真实场景。新前端可以直接使用会话、成员、消息、轮次和诊断接口。未来活动和生活功能沿明确职责接入。

## 9. 未来活动验收范围

活动实现时另外执行真实玩法验证：固定行动顺序、非当前角色的操作被拒绝、参与者随时发言、ConversationTask 和 ActivityTask 分别调用模型与提交、聊天未完成时棋局继续推进、状态变化后过期操作不能提交，以及当前行动者得到模型调度机会。

同角色同时存在两类任务时，验证它们共享角色身份但不共享可变执行状态；一种任务重试不重复提交另一种结果。当前文档确认接入方式，以上结果不在本次报告中记为已通过。
