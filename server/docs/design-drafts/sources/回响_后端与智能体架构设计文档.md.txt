# 一、架构总览

## 1.1 一张图看懂

```text
┌─────────────────────────────────────────────────────────┐
│  L1  Unity 客户端（Windows）                              │
│      纯表现：渲染消息/日记/共鸣腔，不判定任何游戏状态        │
└───────────────▲─────────────────────────────────────────┘
                │ HTTP 轮询（玩法 §21 契约）
┌───────────────┴─────────────────────────────────────────┐
│  L2  接入层 API（FastAPI 路由）                           │
│      鉴权 / 参数校验 / 幂等 / 组装响应，不写业务逻辑        │
├─────────────────────────────────────────────────────────┤
│  L3  编排层 Runtime（确定性代码，游戏的心跳）               │
│  ① 会话循环    ② 主动性循环    ③ S5/S6 反思工作流         │
│  ④ 冷却·仲裁·防打扰                                      │
├─────────────────────────────────────────────────────────┤
│  L4  Agent 层（她的大脑，只出提案）                        │
│  小槿 Character Agent ｜ 阿澄 Character Agent            │
│  Narrative Agent                                                │
│  每个 Agent = Profile + Harness + Model；只出 Proposal           │
├─────────────────────────────────────────────────────────┤
│  L5  共享服务层（无状态的公共能力）                        │
│  Model Gateway ｜ Memory ｜ 话题·事件运行时               │
│  Safety ｜ Trace                                         │
├─────────────────────────────────────────────────────────┤
│  L6  存储 SQLite（单文件，唯一持久层）                     │
└─────────────────────────────────────────────────────────┘
```

## 1.2 六层职责表

| 层 | 一句话职责 | 关键禁止 |
|----|-----------|---------|
| L1 客户端 | 表现与输入 | 不持有话题池、不算合法性、不判定关系（玩法 §21.1） |
| L2 API | 请求进出的大门 | 不含业务逻辑，只做校验/转发/组装 |
| L3 Runtime | 决定"现在该发生什么" | 不生成任何自然语言——那是 Agent 的事 |
| L4 Agent 层 | 生成语言与选择（提案） | **永不直接修改任何权威状态**（提案制） |
| L5 共享服务 | 公共能力，被 L3/L4 调用 | Safety 之外的服务不拦截内容 |
| L6 存储 | 唯一持久层 | 客户端永远不直连 |

## 1.3 三条核心分界原则（整个架构的地基）

1. **Runtime vs Agent：确定性 vs 概率**【硬约束】
   需要"判断/表达"的进 Agent 层（说什么、选哪个动作、什么语气）；需要"决定/执行"的留在 Runtime（什么时候调用、调用谁、结果接不接受、写不写库）。判定依据：如果这件事必须 100% 可靠、可重放、可测试，它是 Runtime 的；如果它需要智能但可以失败重试，它是 Agent 的。
   （来源：玩法既定裁决"AI 只选和说，客户端当裁判"的架构版；骨架 v0 §二）
   Agent 内部的 Harness 负责确定性地驱动模型—工具—Observation 循环，但不因此取得世界状态的决定权；“控制流程确定”不等于“模型结果确定”。

2. **后端权威 vs 客户端表现**【硬约束】
   所有改变阶段、关系、记忆、建设的写操作都由 L3 校验并递增版本号（stateVersion）；客户端只缓存、只表现（玩法 §21.1 原则 5）。

3. **提案制**【硬约束】
   Agent 的输出永远是"提案"（共用 `ProposalEnvelope` 外层，按 `kind` 携带类型化 payload；角色消息和行动不是同一字段的隐式组合）。Runtime 审核提案（Safety、合法性、预算），接受后才写入权威状态并下发。**她的"脑子"会犯错，但落库前的每一道闸门都是确定性代码。**

## 1.4 一个请求的完整旅程（先给全景，细节见 §五）

```text
玩家在聊天框打字"今天好累" → POST /message/send (202 Accepted)
  ↓ L2 校验后交给 L3 会话循环
Runtime：入队 → 构造 `AgentInvocation`（人格 Profile+MemoryView+近N条对话+当前情境）
  ↓ 调用 L4 小槿 Agent
Harness：Agent Loop（模型 → 必要的只读工具 → Observation → 继续模型）
  ↓
AgentRunResult.proposals[0]：ProposalEnvelope(kind=character_message, payload={thought, utterance})
  ↓ 回到 Runtime
T3 运行资格检查、Proposal Reviewer 与 Safety 审核
  ↓
approved：同一短事务把 utterance 写入 messages、thought 写入私有 thoughts；否则丢弃 thought
  ↓
玩家客户端 GET /message/sync 轮询 → 拉到新消息 → 渲染
```

注意两个设计点：① 202 立即返回，客户端不等待回复——这同时满足了"异步优先"（§21.1）和"不显示正在输入"（世界规则"三无"）；② 玩家原始文本**原样透传**给 Agent（玩法 §21.1 原则 4），Runtime 组上下文时不得改写、删减或"翻译"玩家的话。

# 二、技术选型与理由

以下选型全部来自问卷结果（2026-08-31，25 题全 A），并经单人开发现实校验：

| 决策 | 选择 | 为什么 | 升级预留 |
|------|------|--------|---------|
| G1 语言框架 | **Python 3.11+ / FastAPI + Pydantic** | LLM 生态最厚；Pydantic 直接消费 schemas/ 的 YAML 定义做校验 | 无需预留 |
| G2 数据库 | **SQLite 单文件** | 零运维零部署，单账号绰绰有余 | 表结构保持标准 SQL，日后可平移 PostgreSQL |
| G3 服务形态 | **单进程单账号域服务** | 所有调度、批处理、API 在一个进程内；asyncio 管并发 | 接口按"多账号可扩展"设计（全部带 accountId 参数位），进程内部不依赖单账号假设 |
| G4 客户端通信 | **HTTP 轮询为主 + 打开 App 全量同步** | 与"异步优先""三无"自洽；不引入 WebSocket/推送 | 轮询间隔与触发条件见 §五.1 |
| G5 LLM 接入 | **直连模型 API，薄封装** | provider 做成配置项；一个 Gateway 类管重试/超时/记账 | 见 §五.5 |
| — 任务调度 | **进程内 asyncio 定时器**（修正问卷 A1） | 问卷填了"外部任务队列（cron/Celery）"，但单进程单账号下引入外部队列是纯负担；Runtime 的四个循环就是调度器本身。若未来多账号化再外移 | A1 答案作为多账号阶段的预案保留 |

**刻意不引入的东西**（以及为什么）：消息队列（单进程内函数调用+进程内事件足够）、独立向量数据库服务（向量检索以嵌入式形态提供，见 ADR-0005）、Docker/微服务（一台机器一个进程）、Redis（SQLite 就是状态本身）。

**模型档位约定**：产品层保持两档逻辑调用——
- **light**：当前使用 DeepSeek V4-Flash，承担日常角色演绎，以及分类、意图识别、轻量提取和结构化等高频任务；当用户关闭 strong 时，可在明确的降级策略下兼任配置为 strong 的任务。
- **strong**：当前使用 `ZHIPU/GLM-5.3-Flash`，承担记忆整理、反思、重要剧情演绎和其他异步高价值操作；不作为每轮日常对话的默认调用档位。
- 分类、结构化等工作后续可由本地训练的小模型承接，但不得改变 Agent、Gateway 和 Runtime 的权限边界；本地小模型未纳入当前默认路由。
- 每次调用必须声明档位，Gateway 按档位选模型、记账、套超时。

# 三、分层详解

## 3.1 L1 Unity 客户端

本文档只约束它的**边界**，不管工程实现：

- 只表现，只上报行为事实（`POST /space/action` 上报动词，不算分）；
- 不等待回复：消息立即本地渲染为 pending，靠 `/message/sync` 收回执；
- `server_only` 字段（隐性进度、话题池内部状态等）在客户端代码中不存在——不是"不解密"，是根本不出现；
- 沉浸页不报错码（玩法 §21.9）：技术故障永远转化为叙事表现或设置页状态。

## 3.2 L2 接入层 API

接口清单**全部继承玩法 §21，不新造契约**。按模块归组：

| 组 | 接口 | 玩法出处 | 实现要点 |
|----|------|---------|---------|
| 消息 | `POST /message/send` | §21.2 | 幂等键 clientMsgId；202 立即返回 |
| 消息 | `GET /message/sync?since=` | §21.2 | 游标增量拉取：messages + chips + traces |
| 状态 | `GET /state/snapshot` | §21.3 | 全量快照，stateVersion 递增；含 foregroundInstanceRef |
| 日记 | `POST /diary/cell`、`GET /diary/latest` | §21.4 | "今天的一格"入库，静默期标记待交换 |
| 收藏 | `POST /collection/pin / annotate / migrate` | §21.4 | 迁移到共鸣腔走空间服务 |
| 空间 | `POST /space/action` | §21.5 | 只有多数动词不触发 AI；triggersAI 的动词进 Runtime |
| 图像 | `GET /image/resolve` | §21.6 | 按 G2→G1→G0 降级链解析，永不返回 G3 |
| 事件 | `GET /events/pending` | §21.7 | 含 requiredVerbs/requiredUI 能力自检字段 |
| 话题 | `GET /topics/visible?conversationId=` | §21.7 | 服务端派生最终 chips 列表（问卷 B3），客户端零逻辑 |
| 小游戏 | `POST /minigame/session/start`、`POST /minigame/turn` | §21.8 | 后端权威局面+乐观并发（expectedStateVersion）；角色回合由 Agent 从 legalActions 中选择 |
| 错误 | — | §21.9 | 降级行为表按 §四.3 实现 |

补充约定：
- **鉴权**：单账号阶段用一个固定 token 即可；接口签名预留 accountId。
- **命名转换**：存储层 snake_case，JSON 响应 camelCase（schemas/README G1 约定，与玩法 §21 示例一致）。
- **错误响应**：统一 `{ code, message, traceId }`；traceId 可在诊断日志中定位完整链路（§五.6）。

## 3.3 L3 编排层 Runtime（本架构的心脏）

Runtime 是**纯确定性 Python 代码**，维护四类外部工作流。它们不是 Harness 内部的 Agent Loop：

### 循环①：会话循环（响应路径）
触发：`POST /message/send`、`POST /diary/cell`、`POST /space/action`（triggersAI 的动词）、小游戏回合。
流程：持久接受输入 → 连发批次封口 → 等待回复资格 → 冻结待回应范围 → 构造 `AgentInvocation` → 调 Agent Run → 复核资格并审 Proposal → 落库。
同一会话按任务串行，一个任务可以覆盖多个输入批次。普通聊天静默 6 秒封口，不设最长收集时间；睡眠、暂忙和剧情消失期间输入持久等待，恢复后合并回应。资格由 Runtime 根据权威规则判定，Agent 不拥有解除限制的权限；等待不占执行租约，不作为技术失败重试。开场登记脚本可采用即时策略。

S2.5 的会话批次、回复资格、任务冻结和 T1/T2/Agent/T3 主路径已经落地；决策见 [ADR-0007](../server/docs/adr/0007-conversation-batching-and-response-eligibility.md)，当前实现细节见 [`server/docs/modules/conversation.md`](../server/docs/modules/conversation.md)。活动／作息按当前现实时间重判，剧情条件不能仅凭时间到期解除。一个 AgentResult 可在 T3 中物化为多个有序 Message 气泡；具体延迟投递和拆句优化后续实现。

### 循环②：主动性循环（她主动开口）
触发：事件驱动（信号到达时）而非固定心跳。
五步管线（蒸馏自 N.E.K.O. §4 主动性设计）：

```text
信号收集 → 动机评估 → 防打扰 gate → 生成 → 下发
```

1. **信号收集**：新事件实例、话题卡状态变化、玩家行为（如深夜在线）、时间点（晚安窗口）都产生"信号"；
2. **动机评估**：轻量模型（light 档）判断"此刻她是否有想说的"——输入=动机源（八类，叙事 §8.1/§9）+ 角色 stage/态度摘要，输出=想说/不想说 + 候选话题引用。**无动机宁可沉默**【硬约束，问卷 A2】；
3. **防打扰 gate**（确定性，见循环④）；
4. **生成**：日常角色内容使用 light；重要剧情或其他高价值异步内容使用 strong；strong 未启用时按降级策略由 light 承接；
5. **下发**：落库，玩家下次 sync 拉到。

**晚安仪式地位**（收口问卷 A6）：晚安不是固定例程，而是一种普通的高权重晚间动机——满足"夜间 + 当日有互动"条件时候选排序加权。**这收口了终检报告遗留的"晚安额度"悬置点。**

**长期离线回归**（收口问卷 A5）：玩家数日未打开 App，回归时按真实时间戳**时间轴重放**——她"这些天"产生的消息（批处理产物、主动开口）逐条补发，玩家滚动读完。消息的时间戳是真实流逝的，不压缩。

### 循环③：S5/S6 Reflection Workflow
ReflectionCoordinator 接收来源事件，选择五种固定图之一：`segment_reflect`、`continuity_compress`、`memory_organize`、`diary_compose`、`view_refresh`。一个段反思图严格处理一个已封段的 MemorySegment；摘要队列维护入口冻结同批段摘要，分别创建连续性压缩与长期整理两个独立图运行，各自提交和恢复。Agent 不能创建图或选择未登记节点。封段由空闲超时、硬上限或游戏日边界决定；关闭 App、HTTP 会话结束或 ConversationTask 完成不等于封段。相邻段可以批量排队，多段汇总由压缩和长期整理负责。 显式封段上限切入一个回复的多气泡组时，退到该组之前，整组回复及对应 thought 不拆分。连续前缀按会话消息顺序判断，不要求全局序号相邻。会话上下文允许少量已被摘要覆盖的近期原文保留在独立预算中，用于承接语气与指代；具体预算见 Memory 模块。

game_day 整理默认按玩家时区每个游戏日最多一次；明确的 narrative_phase 闭合按稳定阶段 ID 幂等且不额外生成每日一篇日记。高影响事件只标记窗口待整理并合并，不逐事件调用。无新材料时跳过生成，空白离线日只做确定性状态补算。按日期落后的任务在服务恢复后顺序补跑。关闭 App 不等于每日结算，也不生成静默期“最后一次批处理”。

Reflection Workflow 由 Runtime 持久化管理。Runtime 按固定图的节点依赖、来源范围和租约执行任务；当前正式纵向入口是 `segment_reflect`。每次模型调用返回节点专用结果，Runtime 保存 Artifact，并在图完成后汇聚为 `ReflectionBatch`，再生成 `ProposalEnvelope(kind=reflection_batch, payload=ReflectionBatchProposal)`。Envelope 的 origin 保存 GraphRun 身份；整图候选统一审核和提交，未提交的 Artifact 不进入对话上下文。LLM 调用始终在写事务外，Reflection 使用独立于会话 T3 的 GraphRun、NodeTask 和事实提交路径。节点 Contract 见 [Agent Contract](../server/docs/infrastructure/agent-runtime.md)，图与来源见 [Reflection 模块](../server/docs/modules/reflection.md)。话题/事件每日结算不属于本轮。

### 循环④：冷却·仲裁·防打扰（纯确定性规则）
- **冷却窗**：每次主动开口后进入冷却（时长按动机类型配，【参数】问卷 A2）；
- **静默窗口**：深夜时段不主动打扰（【参数】问卷 A3）；通知开关客户端自理；
- **每日主动上限**：服务端隐性上限，不显示任何数值（【参数】问卷 A3）；
- **多角色仲裁**（收口问卷 A4）：小槿默认优先；阿澄有独立低频配额；同刻冲突时错峰发送。

### Runtime 的铁律
不生成自然语言；不调用模型（模型调用全部经由 Agent 层或 light 辅助服务）；每一步落 Trace；每一步可单独重放。

## 3.4 L4 Agent 层

Echo 中的 Agent 由角色/叙事 Profile、Harness 和 Model 共同组成：

```text
Agent = Profile + Harness + Model
```

Character Agent 与 Narrative Agent 共享 Harness 的运行能力，但拥有不同的身份指令、上下文视图、工具白名单和 Proposal 能力。反思不是第三种人格 Agent，而是目标 Agent 可选的运行能力；其角色身份仍由被调用的 Agent 提供。Agent 只拥有提案权，永远不直接修改权威状态。

| Agent | 职责 | 不负责 |
|-------|------|--------|
| 小槿 Character Agent | 日常角色对话走 light，重要剧情回复按 Runtime 路由 strong；会话模式提交 `character_message`，reflect 模式提交 `reflection_batch`；按 Runtime 授权检索记忆 | 直接改写记忆/状态/关系、阶段推进、事件仲裁 |
| 阿澄 Character Agent | 解锁后的角色对话和重要剧情回复；使用独立上下文、能力白名单与配额；只有显式登记 reflect 能力后才接入 Reflection Workflow | 未登记时执行 Reflection；直接写库或越权访问 |
| Narrative Agent | 情境提案（`narrative_situation`：主线节点的舞台建议、张力源管理） | 生成角色台词（角色台词只出自 Character Agent） |

Reflection 的持久调度属于 Runtime；反思指令、上下文投影和输出 Schema 属于目标 Agent 的 reflect 能力，并通过 Harness 执行。将来可以让不同 Agent 接入同一 Workflow，但不能把当前 Character 专属的候选 Schema 无条件套给所有 Agent。

### Agent Harness 与内部 Agent Loop

Harness 是围绕 LLM 的 Agent 运行环境，拥有一次 Agent Run 的内部循环，而不是一次模型请求的薄适配器。一个 Run 可以多次调用 Model Gateway：

```text
AgentInvocation
    ↓
Harness 组装 PromptContext
    ↓
Model Gateway：模型响应
    ↓
终态 Proposal / 只读工具调用
    ↓                  │
返回 AgentRunResult ← Observation
    ↑                  │
    └──────继续 Loop───┘
```

Harness 负责身份指令、上下文投影、只读工具编排、结构化输出校验、上下文压缩、预算、停止条件和有限重试。其控制流程可以是确定性的，但模型输出仍然是概率性的。

Agent Run 的终态可以是：

- `completed`：产生一个或多个合法 Proposal；
- `no_proposal`：明确沉默或当前没有可提交内容；
- `suspended`：等待 Runtime 处理外部结果后再继续（后续能力）；
- `cancelled`、`retryable` 或 `failed`。

一次模型响应及其本地工具活动称为一个 `AgentStep`。Agent Run 的结果是 `AgentRunResult`，其中的 `ProposalEnvelope` 才是提交给 Runtime 审核的候选提案。

### Harness、Runtime 与 Model Gateway 的边界

角色回复继续沿用既有外层协议：AgentRunResult.proposals 仍承载 ProposalEnvelope(kind=character_message)，Runtime 仍以 Proposal 为单位审核和提交，不新增绕过 Proposal 的返回通道。变化只发生在 character_message payload：v2 同时包含角色私有 thought 与玩家可见 utterance。Harness/T3 在内存中审核完整提案；持久化到通用 agent_results.payload_json 时剔除 thought，只有 T3 接受回复时才将 thought 写入独立私有表，并与 utterance 在同一事务提交。被拒绝、过期或迟到的结果不保留 thought。

Character Agent 的 reflect 模式返回专用内部节点结果，与 `AgentRunResult.proposals` 互斥。Runtime 保存 Artifact，图汇聚阶段构造唯一 `kind=reflection_batch` 的批次 Envelope；其 `agent_id` 仍标识目标角色，内部 `*Candidate` 没有独立 Envelope 或全局审核生命周期。批次通过通用闸门和 Reflection 专用 Reviewer 后原子提交。普通角色会话继续由 T3 审核 character_message；两者共享提案权限原则，不共用会话结果表或提交事务。

`AgentInvocation` 显式携带 Runtime 选定的 purpose；作用域、图/节点/快照身份、来源范围和版本由 Runtime 固定。节点输出由专用 Contract 约束，不授权节点直接返回全局 Proposal。

```text
Runtime Workflow / Supervisor
  调度、领取、租约、恢复、重试、审核、提交
             ↓ AgentInvocation
Agent Harness / Agent Loop
  模型、只读工具、Observation、上下文、终态 Proposal
             ↓ ModelRequest
Model Gateway
  一次模型推理请求、Provider 隔离、错误和用量
```

Runtime 外部工作流和 Harness 内部 Agent Loop 是两种不同的循环，不应混称。外部框架若自带 Agent Loop，必须由 Adapter 明确声明其为 Loop Owner；Echo 不再额外包一层不可见循环。

提案生命周期仍然是：

```text
AgentRunResult → ProposalEnvelope → Runtime 审核
  → approved：生成 ChangeSet 并写入权威状态
  → rejected：记录原因，按策略重试或结束
  → expired：上下文、租约或时机失效，禁止原样提交
```

详细的 Run 状态、Step、工具、预算和 Provider 边界见[Agent Contract 与模型运行时](../server/docs/infrastructure/agent-runtime.md)。

## 3.5 L5 共享服务层

| 服务 | 职责 | 要点 |
|------|------|------|
| **Model Gateway** | 所有 LLM 调用的唯一入口 | 薄封装：按 light/strong 选 provider、重试、超时、Token 记账（问卷 G5） |
| **State & Relationship（S5）** | 角色自状态、有向关系、客观关系证据 | SQLite 持久化；Runtime 根据已审核证据确定性更新；ContextSnapshot 同一读事务读取并带来源版本 |
| **Memory（S6）** | 来源记忆、阶段整理和对话检索 | 工作/长期/核心记忆；稀疏路为 jieba 预分词写入 SQLite FTS5 并用 BM25 召回，稠密路为 ONNX + sqlite-vec，再以 RRF 和量化精排；向量不可用时回退稀疏/结构化检索（ADR-0005） |
| **话题·事件运行时** | topic_card / event_instance 的家 | 单一话题池双视图的派生（主动候选视图/玩家可见视图）就在这里；前台仲裁（问卷 C1：张力最高且未完成的活跃实例，同分取最近更新）与并行上限（问卷 C2：active ≤ 2~3，超出强制最旧推进 completed）也在这里 |
| **Safety** | 独立安全模块 | 确定性规则（关键词/模式匹配+分级响应），**前置在所有 Agent 输出之后、下发之前**，可拦截可改写可升级（问卷 I1）。违规→拦截并给安全介入，不让角色继续违规内容（玩法 §21.9） |
| **Trace** | 记账与追踪 | 每次模型调用（档位/Token/耗时）、每次提案（产出/审核结果/原因）、每次状态变更（旧值→新值）都落 trace 表；玩家可见的"问题编号"从这里出 |

### S5 状态与关系的实现

S5 有三组权威记录：

- character_state_entries 按角色保存带起止时间和来源的物理体征、慢心境、当前活动。活动默认空置并带 TTL；心境由 Reflection 的趋势候选经 Runtime 聚合。精力、心境和普通疲劳只作为软提示，不单独禁止回复或扣关系分；运行故障、暂停和世界规则缺席继续由现有回复资格规则处理。
- relationship_state 按 account、观察者角色和目标对象保存一个有向关系，包括 relationship_type、H/T/A、自然语言 attitude_summary 和 state_version；是否 initialized 由 relationship_type 是否为 stranger 推导。v1 运行时只有陌生人、熟人、朋友三类，解释 H/T/A 时必须连同关系类型读取。新玩家从陌生人开始，H/T/A 为空；人设 L0–L5 只保留为自然语言设定，不转换成运行时枚举或关系分值。
- relation_evidence 是带唯一来源引用的追加式客观证据账本，和 H/T/A 这种主观连续状态分开。原始交互与确定性玩法事件由 Runtime 形成客观证据；目标 Character Agent 的反思能力只能在 `reflection_batch` payload 中提交有来源的关系影响候选，不能直接写 H/T/A 或关系类型。`character_message` 不承载 S5 状态或关系变更。

玩家有真实互动后，Runtime 按配置将陌生人初始化为熟人；达到 H/T 基线并存在符合条件的关系事件后才转为朋友。普通沉默或离线不导致降级。证据影响使用离散方向和等级（0/1/2/3，对应起步步长 0/1/3/6），不接受模型提交裸分值；A 对普通轻微事件的等级 1 起步为零。Runtime 按关系类型和角色参数计算向上衰减系数 (100−x)/100、向下衰减系数 x/100，中性为 0，结果限幅到 0–100，并在同一事务追加证据、更新关系状态和递增版本。

ContextSnapshotSource 在同一 SQLite 读事务中读取角色自状态、关系及来源版本，构造本轮不可变快照。普通回复及非关系反思节点只看到自然语言关系类型、看法和软提示。仅 `relationship_reflect` 可读取好感、信任、依恋的完整名称、当前值、范围及阶段规则；陌生人保持数值未初始化，不填零。节点仍只能分别提出三维证据、方向和幅度等级，最终数值与关系类型由 Runtime 决定，内部数值不进入公共 API 或 Unity。作者预载记忆包只载入角色自己的过去，使用人设资源 ID/版本作来源；不创建该角色与当前玩家的共同经历。

### S6 Memory 数据与检索实现

原始 messages、有来源的 memory_entries、永久私人 diary_entries 和玩家独立的 player_cells 各有不同语义。作者预载记忆以 authored_preload 来源写入长期记忆；玩家 cell 只有按玩法规则分享后才能被角色读取。thought 是临时角色私有材料：模型输出后随 character_message payload 进入 Runtime 内存，只有回复通过 T3 才写入 thoughts；日记成功提交后按实际覆盖清单清理 thought，并保护仍被未完成段反思使用的材料；具体清理边界见 Memory 模块 §6。核心记忆块、段摘要、实体边、FTS 和向量均为可按真源重建的派生数据；日记、thought、核心摘要不进入普通记忆召回。

稀疏召回路径在入库时用 jieba 对记忆文本预分词，并将分词文本持久化到同库 SQLite FTS5 索引；查询时使用同一分词及过滤规则生成内容词查询，由 FTS5 的 BM25 排序召回候选。稠密路径用本地 bge-small-zh-v1.5 ONNX 生成向量并存到 sqlite-vec。Runtime 授权 memory_search 后并行执行稀疏与稠密召回，按 RRF(k=60) 融合，再用本地量化 bge-reranker-base 对有界候选集精排；扩展、模型或向量路径不可用时退回 BM25/结构化检索，不阻塞普通对话，也不越过记忆可见性过滤。

### S6 Reflection Workflow 的任务与事务

Runtime 创建固定 GraphRun 和 NodeTask，冻结图级 ContextSnapshot，各节点只读取专用投影和前置 Artifact。`segment_summary_plan` 产生段摘要，关系和状态节点分别提出影响；启用的节点全部完成或明确 no_op 后，整图汇聚审核。摘要、关系证据和状态事实在一个短事务中提交。图中必需节点失败不会局部提交。视图刷新只读取已经提交的事实，并由独立策略决定是否创建请求。旧的分支任务形态已从正式运行时代码删除。

消息段按空闲超时封口，消息数或 token 硬上限强制切段，玩家本地游戏日边界封住当日尾段；v1 起步为闲置 30 分钟、约 100 条消息并受 token 上限约束，均可配置。相邻已封段按角色/目标对象批量排队，每段独立反思，关闭 App、HTTP 会话结束和 ConversationTask 完成不封段。game_day 默认每个玩家本地游戏日最多整理一次；narrative_phase 只由 Runtime 的明确闭合事件以稳定阶段 ID 触发，不额外生成日记。高影响事件只标记窗口待整理并合并；空白离线日不生成虚构日记，也不产生关系惩罚。

Reflection 使用独立 GraphRun、NodeTask、Artifact、GraphResult 和 Reflection Worker，不进入 ConversationTask T3 或 `agent_results`。Agent 与 ONNX 计算均在写事务外运行；Runtime 先校验 Proposal Envelope，再由 `ReflectionReviewer` 校验来源、边界、版本和候选组合。通过审核的 ReflectionBatch 生成 ChangeSet，在短事务中写入 S5/S6 事实并入队 Trace outbox；失败或租约过期不会推进图完成状态，Worker 重启后恢复节点和汇聚进度。详细字段和验收边界见 [状态与关系模块](../server/docs/modules/state-and-relationship.md)、[Memory 模块](../server/docs/modules/memory.md) 与 [Reflection 模块](../server/docs/modules/reflection.md)。

# 四、模块间通讯规约

## 4.1 三种通讯方式，各管一类事

| 方式 | 用途 | 例子 |
|------|------|------|
| **函数调用**（同进程同步） | 请求-响应式、需要立即结果 | Runtime → `Agent.run(invocation)`；Harness → `ModelGateway.generate()`；Runtime → Safety.check() |
| **进程内事件**（发布/订阅） | 广播"某事发生了"，不关心谁响应 | EventBus.publish("message_stored") → 话题运行时提取、主动性信号收集订阅 |
| **持久化消息**（落库，轮询取回） | 跨时间的投递：现在产生、稍后被客户端取走 | 一切对客户端的下发（messages/chips/events/snapshot 的变化） |

**判别法**：要结果→函数调用；要通知→进程内事件；要跨网络跨时间→落库。客户端永远只见第三种。

## 4.2 事件命名与负载

进程内事件统一 `{domain}.{action}`（如 `message.stored`、`signal.raised`、`proposal.approved`），负载只带 ID 不带全量对象（订阅方自行查询，避免数据漂移）。禁止跨层直接 import 绕过事件——L4 不得感知 L2 的存在。

## 4.3 失败传播与降级链【硬约束】

全线失败处理继承枯萎庭院 v0.5 §14.4 的分层降级思想（蒸馏见 §八），落地为：

```text
strong 异步任务：用户关闭 strong 时按任务策略交给 light；已经调用 strong 但失败时按原档位重试/恢复，不因调用失败自动换档：
  记忆整理/反思 → 延后重跑，不伪造产物
  重要剧情 → 延后或交给 Runtime 既定演出，不伪造剧情事实
  日记/长文本 → 标记待重跑，不伪造已完成内容
light 日常角色演绎失败 → 重试 → 受控的保守降级；分类/意图失败 → 规则兜底
校验失败 → Harness 重试 → 超限进入 Runtime 重试或登记的降级路径
Safety 拦截 → 按分级：改写 / 替换安全话术 / 安全介入
```

原则重申（玩法 §19.4）：**永远不让技术故障以技术故障的样子出现在玩家面前**。沉浸页无报错码；真实状态放设置页与诊断日志。

# 五、三条关键全链路（Walkthrough）

## 5.1 玩家发消息（会话循环全链路）

1. 客户端 `POST /message/send {conversationId, playerText, images, clientMsgId, localTimestamp}`；L2 校验，经 Runtime 幂等判断并持久化消息与待回应工作后返回 202；
2. Runtime 收集并封口输入批次，等待角色回复资格；图片走"客户端压缩→服务端审核→通过后才进模型与存储"（玩法附录 B，图片仍属后续能力）；
3. Runtime 在可执行时冻结输入和历史可见边界，构造不可变 `AgentInvocation`：人格 Profile、MemoryView、允许的历史、当前情境、只读工具白名单和 **玩家原文原样**均进入允许的上下文快照；长期积压超出容量时必须显式进入输入准备阻塞，不得静默截断并宣称全部已处理；
4. 小槿 Agent 的 Harness 启动内部 Agent Loop：模型调用 → 必要的只读工具 → Observation → 继续调用，直到返回 `AgentRunResult`；
5. Runtime 从结果取得 Proposal，复核租约、回复资格与快照依赖，再执行 Safety → 合法性（action 是否可执行、话题卡引用是否有效）→ 预算（Token 记账）审核；若资格关闭，未提交提案过期，输入恢复等待，之后重新生成；
6. approved：utterance 落 messages，action 作为演出指令随消息下发，topic_cards 更新消费状态，trace 记录；
7. 客户端下次 `GET /message/sync` 拉到（含 chips——由话题运行时从玩家可见视图派生，问卷 B3）；
8. 轮询节奏【参数】：前台活跃 5~10s，后台降频；打开 App 立即全量 sync 一次（问卷 G4）。

## 5.2 她的主动开口（主动性循环全链路）

1. 某处产生信号（如：事件实例"她的作品截稿日"进入前 24h；或玩家刚才的话留下了未完话头）→ 落 signals 表；
2. 主动性循环被唤醒：防打扰 gate 先跑（冷却窗？静默窗口？今日上限？）——**不过 gate 直接丢弃信号，不调用任何模型**（省钱且保证"不打扰"是硬保证而非概率行为）；
3. 过 gate → 动机评估（light）：输入=信号+动机源+态度摘要 → 输出=想不想说+候选话题；
4. 想说 → 日常主动消息使用 light，重要剧情型主动消息使用 strong；用户关闭 strong 时按降级策略由 light 承接 → 同 5.1 的 5~6 步审核落库；
5. 进入冷却窗；阿澄的开口走同一管线但用独立低频配额（问卷 A4）。

## 5.3 Reflection Workflow（S5/S6 全链路）

1. Runtime 根据封段、摘要队列、日窗口或刷新请求选择固定图，冻结来源范围及版本；
2. 在统一只读边界构造图级快照，各模型节点仅取得获准的材料投影；
3. Agent 通过 Harness 返回节点专用结果；Runtime 持久化 Artifact 与条件分支，按依赖激活后继；
4. 图汇聚产生唯一 reflection_batch Envelope，由 ReflectionReviewer 校验来源、权限、预算、版本和候选组合；不允许局部批准或模型指定关系最终数值；
5. Runtime 在短事务复核租约及版本，原子提交整图事实、结果、对应来源进度、变更信号与 Trace outbox；事实变更再由独立视图策略处理；
6. 日记按实际覆盖清单及未完成消费者清理 thought 和包含全文的私有缓存；失败保留材料，具体规则见 Memory 模块 §6；
7. 故障恢复未提交节点与汇聚，不混合不同快照结果；原文不因摘要失败丢失。压缩与长期整理分别记录处理进度，一方失败不撤销另一方结果。

# 七、工程守则（单人开发）

1. **Stub 优先**：每个里程碑先用假实现跑通链路再换真的——基础会话阶段用返回固定台词的 Stub Agent 验证"API 起得来、库落得下、轮询拉得到"；Model Gateway 先接一个假 provider。**骨架与模型效果两个变量永远不混着调**。
2. **Schema 就地定稿**：schemas/ 八份 YAML 是草稿；对应模块实现时以它为起点、按实际需要修正并升版本（修订程序见 schemas/README §四）。不要一次性"冻结"全部。
3. **Trace 第一天就有**：哪怕只有 print 级日志，也要从 M0 起按"请求→提案→审核→落库"四点留痕。后期所有攻关都靠它。
4. **每步可重放**：批处理各步幂等；消息处理按 clientMsgId 幂等；Runtime 审核与提交可重放；模型调用除外——温度与随机性只存在于 Agent Harness 内部。
5. **目录结构建议**：
   ```text
   Echo/
   ├─ server/
   │  ├─ src/echo_server/
   │  │  ├─ api/          # L2 路由（按玩法 §21 分文件）
   │  │  ├─ runtime/      # L3 外部工作流、审核与提交
   │  │  ├─ agents/       # L4 contracts + harness + character/narrative
   │  │  │  ├─ contracts/  # AgentInvocation / AgentRun / Proposal
   │  │  │  ├─ harness/   # Agent Loop 与框架 Adapter
   │  │  │  ├─ character/ # Character Profile 与 Agent 组合
   │  │  │  └─ narrative/ # Narrative Profile 与 Agent 组合
   │  │  ├─ services/     # L5 共享服务（含 Model Gateway / Memory）
   │  │  ├─ store/        # L6 数据库、迁移与 Repository
   │  │  ├─ domain/       # 与框架无关的领域值对象和规则
   │  │  ├─ observability/
   │  │  └─ config.py     # provider/参数集中，含【参数】项全部默认值
   │  └─ tests/           # 每层至少冒烟测试；Runtime 全部可离线测
   └─ docs/schemas/       # 字段级草稿；正式 Schema 随模块实现就地定稿
   ```
6. **测试策略**：Runtime 与 Safety 全部离线可测（stub 模型）；Agent 层做金样本回归（固定输入比对结构合法性）；每次改 prompt 跑一遍金样本看漂移。
7. **里程碑顺序**：S2.5 canonical Conversation Runtime → S3 Identity → Runtime 加固 → S4 Character Agent（默认 `light=DeepSeek`、`strong=GLM`）→ S5 状态与关系持久化 → S6 Memory、thought 和固定 Reflection Graph → S6.5 模型盲测 → S7 巩固 → S8 人格稳定打磨 → S9 E2E 与交接 → 主动性、话题/事件每日结算和三验证切片（玩法 §22.1：独奏核心/时间核心/空间核心）。

# 九、术语表

| 术语 | 含义 |
|------|------|
| Runtime | 编排层，确定性游戏逻辑所在 |
| Agent | Profile、Harness 与 Model 的组合；只能向 Runtime 提交候选提案 |
| Harness | 围绕 LLM 的 Agent 运行环境，拥有一次 Agent Run 的内部 Agent Loop、上下文、工具、预算和终态处理 |
| Agent Loop | Harness 内部的模型—工具—Observation 循环 |
| Agent Run | Harness 从 `AgentInvocation` 开始到终态 `AgentRunResult` 的一次完整运行 |
| Agent Step | 一轮模型响应及其本地工具活动，不等于一次完整 Agent Run |
| 提案 proposal | Agent 按 Proposal schema 输出的结构化建议（角色文本、行动或叙事提案），经审核才生效 |
| light / strong | 两档任务路由：light 负责日常角色演绎并可降级承接；strong 负责记忆整理、反思和重要剧情演绎 |
| 信号 signal | 主动性循环的输入：任何"可能有话要说"的触发源 |
| 冷却窗 | 主动开口后的强制静默时长 |
| server_only | 永不下发客户端的字段标记 |
| 时间轴重放 | 长期离线回归时按真实时间戳逐条补发 |
| 三验证切片 | 玩法 §22.1 的独奏核心/时间核心/空间核心 |
