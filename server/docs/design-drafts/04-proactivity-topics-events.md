## 三个机制

| 机制 | 职责 | 边界 |
|---|---|---|
| 话题卡 | 保存角色可能想谈的内容、来源、态度和进度 | 提供方向，实际发言由角色产生 |
| 事件卡与实例 | 可复用的生活或世界处境模板，实例保存具体参与者、进展和结果 | 模板、实际事件及角色对事件的看法分别保存 |
| 主动开口 | 根据可见信号、动机和发送资格发起交流 | 允许不发言；发送走正式消息审核和提交 |

话题线程表达跨事件的长期主题，原设计归属叙事侧，通过话题卡影响交流。本项目是否需要独立叙事调度器和线程系统待定；完整原意保留在来源文档。

## 话题卡需要保留的设计

每个角色维护自己的话题池。来源包括生活、创作、参与者近况、关系、世界事件及长期主题；每个实例保留来源引用、话题提示、态度、新鲜度、触碰次数和过期条件。

主动候选与玩家可见话题建议来自同一池的不同读取视图。玩家可见视图不能暴露角色私有内心、秘密背景或其他私有来源。主动触碰和玩家发起都更新同一实例的进度。卡片提供话题方向，不保存预制台词。

原文区分持续供材、一次性耗尽、跟随宿主状态及事件驱动的内容，记录聊过、冷却、关闭和重新出现等状态。当前正式状态枚举、更新事务、重复消费、来源变化和重置处理待设计；不能照搬全部枚举即认为功能完成。

多角色社区需要额外确定社群与会话适用范围、目标玩家或角色及成员可见性。角色全局话题池不能成为跨会话传播私人内容的入口。

## 事件卡需要保留的设计

事件卡定义领域与规则；事件实例承载具体状态、参与者、行动、结果和持久影响。有需要追踪的进展才创建实例，普通问候无需生成事件。一个具体发生可以关联多个领域，避免建立多份重复事实。

原文允许后台持续事件与当前主要处境并存。并行限制、前台选择及结束规则需要按当前用法确定，不能为了满足数量限制强行把未完成事件写成已完成。

游戏 Activity 已有独立规则与权威结果。事件实例如何引用活动结果、与其他生活事件共享哪些设施，需要明确对象边界；不能让叙事候选改变棋局或把模型讲述保存为已执行活动。

旧剧情涉及的世界状态须有正式业务入口和来源。AI 可参与生成作者候选内容，但新增事件类型及规则需要经明确确认、校验和版本登记后使用。

## 主动开口的运行建议

建议流程为：保存信号 → 程序检查资格与发送限制 → 模型评估动机及候选话题 → 生成发言或沉默 → 提交前重新检查资格 → 保存正式消息和消费结果。

信号可来自真实事件进展、未完话题、约定或时间窗口。时间只提供机会，不自动编造新的生活经历。定时窗口如何转化为信号、重复与过期如何处理，以及受限信号延期还是关闭均待设计。

保留冷却、静默窗口、调用预算及多角色安排。明确模型评估前检查和提交前检查，避免评估期间条件变化后仍发送。旧文 §3.3 与 §5.2 的防打扰检查顺序不一致，本草案建议采用上述顺序，尚待正式确认。

需要重新确定私聊、群聊、角色之间主动交流的范围；用户是否接受离线期间继续运行；真实时间与世界时间分别触发什么；多角色是否错开，以及消息数量限制的具体规则。服务未运行期间不得伪造主动消息或倒填发送时间。

## 开发安排与验收

优先完成角色身份、参与接话及记忆来源，再接入本项。话题池的最小正式来源可以来自可见聊天和已保存摘要，不要求等待所有叙事玩法完成。事件型话题依赖对应正式事件来源，完整事件体系可以后续扩展。

验收覆盖无玩家新消息的主动发起、有动机也可沉默、受限时不发送、重复信号不重复发言、多人发言安排、私有话题隔离、恢复及话题消费可追溯。游戏反应与主动回顾分别验证，角色事实采用正式来源。
