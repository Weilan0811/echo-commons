# ADR-0005：记忆检索引入嵌入式向量能力，修订问卷 D1 的"纯结构化 SQL 起步"

> 状态：Accepted
> 日期：2026-09-04
> 相关模块：Memory（模块设计文档建立后在此补充引用）
> 相关文档：[回响_后端与智能体架构设计文档](../../../docs/回响_后端与智能体架构设计文档.md) §二（刻意不引入清单）、§3.5（Memory 服务）、§六（攻关清单）

## 1. 背景

顶层架构文档在问卷 D1 基础上决定"记忆检索起步用结构化 SQL（标签+时间范围+卡型过滤）"，并把"向量数据库"列入刻意不引入清单。该决策的**真实意图是零运维、单文件、单进程**，这个意图仍然有效。

但 Character Agent 的记忆设计（分层记忆：热/温/冷/神圣，两阶段检索重排）以语义召回为核心路径——"语义相似但措辞不同的过往被想起"是结构化过滤无法承担的需求，纯 SQL 起步方案与该设计冲突。

同时存在一个此前未纳入考量的规模事实：单账号陪伴游戏的记忆条目量级约在 10⁴–10⁵，远低于独立向量数据库服务的适用门槛。向量检索在这个量级上是普通计算问题，不是基础设施问题。

## 2. 决策

1. **引入向量检索能力，仍不引入独立向量数据库服务**。修订架构文档"刻意不引入的东西"清单与 §六 攻关清单相应条目；问卷 D1 的"结构化起步"结论由本 ADR 取代。
2. **具体计算形态在 Memory 模块设计文档中另行确定**，候选包括进程内数值计算（embedding 存 SQLite BLOB 列）与 SQLite 向量扩展等嵌入式方案；本 ADR 只约束边界：不新增外部服务、不破坏 SQLite 单文件与单进程形态。
3. **非向量基线永远保留**：结构化过滤（层/时间/重要性/标签）与 SQLite 全文检索构成可用基线；向量不可用或命中不足时降级返回，不得阻塞对话链路（对齐"在线路径不做重活"与实现状态文档的降级纪律）。
4. **embedding 来源作为模型档位配置的一部分**（对齐 light/strong 档位约定与问卷 G5 薄封装原则）；embedding 列写入时登记来源与维度标识，更换来源需要全量重算与迁移设计，未完成迁移前新旧来源不混用。

## 3. 结果

- 语义检索可以进入记忆设计主线（温层召回、两阶段重排），不再被选型排除；
- 基线与降级路径保证向量能力缺失时对话链路仍然完整；
- 新增成本项：embedding 生成调用量（按 light 档记账）与向量存储体积；
- 新增不变量：embedding 来源标识必须随条目落库，检索只使用与查询同来源的向量。

## 4. 重新评估触发条件

- 记忆条目规模或检索延迟超出进程内方案舒适区（如条目 > 10⁵ 或检索 P95 明显超标）→ 引入 SQLite 向量扩展或等价嵌入式索引；
- 多账号化或记忆跨设备同步需求出现 → 重新评估存储与检索边界；
- embedding 来源更换或模型升级 → 启动全量重算迁移，期间基线检索兜底。

## 5. Memory 模块落实（2026-09-15）

[Memory 模块设计](../modules/memory.md) 落实了 §2.2 留待 Memory 决定的具体形态：

- 向量存储选择 SQLite 内嵌 sqlite-vec，不增加独立服务；本机 smoke 已验证 Python 扩展可经 aiosqlite 连接加载，加载后立即关闭扩展加载权限；
- 稠密路使用本地 bge-small-zh-v1.5 fp32 ONNX 生成向量；稀疏路使用 SQLite FTS5 + jieba：写入时用 jieba 预分词，并将分词文本持久化到同库的 FTS5 索引，查询时采用同一分词与过滤规则，按 FTS5 BM25 排序召回候选；两路候选经 RRF 融合后由量化 bge-reranker-base 精排；
- 权重/tokenizer 由本地配置目录提供，不随仓库或 Python 包发布，不自动联网下载；缺权重、扩展或向量功能失败时回退 FTS5 + 结构化检索；
- Python 运行依赖锁定在 server/pyproject.toml 与 uv.lock；升级 sqlite-vec 必须通过 Windows Python 与 aiosqlite 集成门禁。

spike 指标来自小规模合成语料，只用于选择 v1 起点。上线门禁仍须抽验量化 reranker 排序质量，并以真实中文记忆语料验证质量、延迟和内存；此处不把现有 spike 指标写成产品质量承诺。
