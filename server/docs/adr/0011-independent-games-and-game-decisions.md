# 独立游戏运行与角色局内决策

更新日期：2026-10-16。状态：采用，尚未实现。实施状态见[后端状态](../status.md)。

## 背景

游戏需要在真人操作和角色参与时使用相同规则，并能独立开发、验证和保存。Activity 是社群中角色的能力，局内交流仍需要已有会话、人格和记忆。日常群聊与局内行动各自调度，会让同一消息产生重复回答，也会增加模型调用。

## 决定

顶层 `games/` 提供独立 `echo_games` 包，拥有规则、对局、席位、状态、随机结果、回执和正式事件。宿主通过正式包依赖加载，继续使用一个进程、端口和 SQLite。游戏不导入社群实现。

游戏维护稳定主体引用、席位占用与参与区间，宿主转换社群身份并维护对局与会话关联。会话模块管理每场独立的 `game` 会话。局内消息按类型只进入局内协调，复用群聊参与机制；ActivityTask 协调同一角色的接话与行动，在冻结前合并来源，一次模型决策允许同时输出动作与发言。

游戏与会话分别检查并保存所属事实。当前部署下，创建、加入、等待时离开及结束活动使用同一短事务保存游戏占用、会话成员与宿主关联；合法动作、获准配套发言与角色决策结果同样通过共同短事务提交。角色经历引用正式事件、消息和实际私人材料，继续使用既有记忆模式。

## 影响

游戏可以独立验证规则与真实存储，开发者继续使用现有启动方式。安装和发布需要同时包含游戏包与宿主包，共享数据库升级由宿主统一安排。

会话需要新增正式类型和活动消息来源；社交规划需要按类型分流，记忆需要接入真实游戏来源。相关改动必须随完整真人基础和角色接入验收，不用空处理器表示完成。

行为与调用策略由[角色活动设计](../design/activity-integration.md)维护，文件与迁移安排见[共同基础](../../../docs/gameplay/共同基础与文件结构.md)，游戏目录、生命周期、内部职责、角色加入和进行中能力统一见[接口契约](../../../docs/gameplay/游戏与角色活动接口.md)。
