# 社群运行状态前端接入说明

后端已实现社群状态修改接口，新社群默认暂停。前端需要增加明确的唤起与暂停操作；创建、加入、选择社群和打开页面均不自动唤起。本说明用于前端分支独立实施，页面位置及组件组织沿用该分支当前结构。

## 1. 读取与修改状态

读取 `GET /api/communities/{community_id}?player_id={player_id}`，返回的 `CommunityView` 包含 `status` 和 `state_version`。界面显示以下两种状态：

| 后端值 | 展示文字 | 可执行操作 |
|---|---|---|
| `paused` | 已暂停 | 唤起社群 |
| `active` | 运行中 | 暂停社群 |

状态修改请求：

```http
PATCH /api/communities/{community_id}/status
Content-Type: application/json
```

```json
{
  "player_id": "lin",
  "status": "active",
  "expected_version": 0
}
```

暂停时将 `status` 改为 `paused`。`expected_version` 必须取自最近读取的 `state_version`，不能固定填零。社群列表卡片不含版本，修改前需要社群详情。完整字段以 [OpenAPI](../reference/openapi.json) 和 [接口参考](../reference/http-api.md) 为准。

成功返回 200 和最新的完整 `CommunityView`。状态发生变化时版本增加；版本有效且状态没有变化时返回原对象，版本不增加。

| 响应 | 前端处理 |
|---|---|
| 200 | 使用返回对象更新社群详情缓存，并刷新已加入社群列表、相关会话列表和任务展示 |
| 409 | 社群版本已经变化；重新读取详情并提示用户重试，不自动覆盖其他操作 |
| 404 | 社群不存在、玩家不存在或玩家不属于社群；展示接口错误并刷新当前社群信息 |
| 422 | 请求格式错误，例如状态无效、版本为负数或包含未知字段 |
| 网络错误 | 保留最后确认状态并展示错误，重新读取后允许重试 |

当前为本地玩家身份模式，社群成员均可修改运行状态，权限沿用现有 `player_id` 规则。

## 2. 界面与请求实现

- 在当前社群的详情或管理区域展示运行状态和对应操作；聊天页面也应能看见暂停提示，并能找到唤起入口，避免创建后进入聊天却无法让角色回应。
- 新建社群成功后保留后端返回的暂停状态。创建说明应提示“新社群默认暂停，进入后可手动唤起”。
- 暂停提示可使用“消息会保留，角色回应和记忆整理将在唤起后继续”。暂停期间后端仍接受并保存玩家消息，角色不会立即回应。
- 修改请求进行中禁用按钮，避免重复提交；界面状态以服务端成功响应为准。
- 修改失败后重新读取社群详情，以便下一次操作携带正确版本。切换社群时清除前一个社群的操作错误，缓存与请求必须绑定当前玩家和社群。
- 如果请求工具限制 HTTP 方法，增加 `PATCH` 支持。根据更新后的后端 OpenAPI 重新生成前端类型，使用 `UpdateCommunityStatus` 请求类型；沿用前端分支已有的数据请求与缓存方案。

暂停与恢复对后台任务的具体影响见 [社群运行规则](../design/identity-and-communities.md#5-世界时间与运行时间)，界面不应承诺暂停能够撤销已经产生的模型用量。

## 3. 验证与测试数据

使用真实后端和独立临时数据库验证以下流程：

1. 新建社群返回 `paused`，页面显示“已暂停”和唤起入口。
2. 唤起后返回 `active`，页面显示“运行中”和暂停入口。
3. 暂停后刷新页面、离开再进入，仍保持暂停；进入页面不自动唤起。
4. 版本过期时展示冲突，重新读取版本后可以再次操作；非成员修改返回 404。
5. 原有聊天测试创建社群后，凡需要角色回应或后台记忆处理的用例，应通过状态接口明确唤起，再继续原流程。

已有测试准备流程如果默认社群立即运行，需要增加唤起请求。测试结束清理临时数据库，避免向日常数据库积累社群和后台任务。
