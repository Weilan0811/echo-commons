# 故障定位与恢复

## 1. 按执行阶段寻找

| 现象 | 检查顺序 |
|---|---|
| 请求未接受 | HTTP 状态和 error/detail、玩家社群成员、会话身份、字段与幂等内容 |
| 消息接受后未回应 | 窗口是否结束、Workers 是否启用、turns 参与原因、角色可用状态 |
| 角色任务停留处理 | 任务原快照、当前租约、共享模型额度、实际供应商期限及重试 |
| 模型有输出但没有消息 | 审核结果、租约代次、原成员区间、暂停或归档 |
| 没有记忆产出 | 段精确来源、节点状态、Artifact、图级审核、消费记录 |
| 追踪暂时不完整 | outbox 投递状态和重试；先读取对应业务事实 |

使用 receipt 的 trace_id 及任务、轮次或图身份查询 [内部诊断](../reference/http-api.md)。普通日志提供阶段和错误码；只有需要检查具体生成内容时才启用完整捕获。

任务和反思节点详情提供分页 `recovery_history`（恢复历史），可查询具体原因、实际动作、等待、耗尽及已经使用的短提示。先检查领取和调用开始，再查看运行结束和恢复决定；规则见 [错误分类、重试与恢复](../design/errors-and-recovery.md)。关闭完整捕获后这些记录仍然保存。

查看模型完整提示时，在使用的 TOML 配置中设置：

```toml
[observability]
debug_capture_enabled = true
debug_capture_path = "../data/debug-captures"
```

修改已有 `[observability]` 表内的字段，然后重启服务。目录按配置文件位置解析；生产环境不启用完整捕获。打开本次会话目录中的 `*-model_call.started.txt`，可以在等待模型回复时查看实际发送的全部消息、工具定义和请求参数。对应 JSON 保留结构化请求，`*-model_call.json` 记录实际响应、用量或错误。根据调用编号、步骤及供应商尝试次数查找同一次请求。关闭 `debug_capture_enabled` 并重启即可停止生成完整捕获。

反思图详情用于检查节点状态、产物和补充运行；节点输入接口显示冻结材料；恢复历史显示尝试、用量、错误和动作。这些管理响应不包含每次完整模型请求，逐步提示与工具往返需要读取当时启用的捕获文件。

## 2. 配置和期限

先运行 inspect 检查数据库和模型登记。确认凭据名称与 credential_ref 一致、文件路径按设置解析、选定条目启用。配置错误不会自动选择其他模型。

供应商请求期限、整次节点期限和租约分别限制不同环节。持续心跳允许长模型执行，但失去租约后结果仍拒绝。观察真实 provider_attempt、持久 attempt 和错误信息，不把一项计数当成全部尝试。

## 3. 暂停、重启及图恢复

对话暂停保留原快照，正式恢复继续；归档和成员离开取消原任务。当前没有公开暂停和归档接口，操作入口属于相应业务服务，不直接修改数据库绕过生命周期。

正常退出后重启，过期租约通过正式队列恢复。未到期租约需等待期限；不能手动改为成功或删除任务来获得“恢复”。段反思与认识刷新 partial 图通过管理重新启动入口创建补充运行，只执行失败分支。查看图详情中的 supplement 和 supplement_run_ids 可追溯原运行与补充运行。进程重启不会自动重做耗尽或部分成功的图。

## 4. 只读检查和资源

inspect/export 使用正式只读路径；导出保留现场供后续复查。不要公开包含私有信息的数据库和完整捕获。日志轮转参数控制文件数量和大小；清理本轮不再需要的捕获及临时进程，保留用户数据与密钥。

健康接口没有模型探测；ready 返回成功只说明应用、数据库及配置要求的 Workers 就绪，供应商仍可能超时。真实模型及安装验证的证据边界见 [验证指南](verification.md)。
