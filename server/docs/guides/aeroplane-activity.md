# 飞行棋角色对局与验收

更新日期：2026-11-05。

## 使用流程

1. 按[根目录说明](../../../README.md)配置普通角色模型的密钥并启动后端、前端。飞行棋采用内置规则评分，无需安装 Rapfi。启用本地决策时另按[本地模型说明](../design/decision-models.md)启动对应服务。
2. 选择一个运行中的社群，准备至少两个记忆状态正常、当前可参与的角色。在游戏大厅选择飞行棋，创建对局，邀请角色进入其他颜色的席位。传统玩法支持两至四人。
3. 点击开始对局。玩家在棋盘上掷骰和选择飞机；角色通过正式任务轮流行动。唯一合法动作自动执行，多种选择由角色结合候选、聊天与局内意图判断。
4. 在桌边聊天中与角色交流。角色也能根据游戏变化及安静期间的机会主动发言；发言与行动分别安排，保持安静时继续正常行动。
5. 获胜者的四架飞机全部归航后正常结算。此时可以继续赛后交流。点击结束活动后，聊天归档，记忆系统继续整理包含赛后内容的整局经历；随后可以在普通聊天中询问比赛结果与精彩经过。

社群暂停和应用重启保留游戏状态及未完成任务。取消对局和结束活动会关闭交流；进行中的飞行棋不支持认输。含义与入口见[活动集成](../design/activity-integration.md)。

## 分析与故障检查

分析器提供规则事实、固定策略评分和推荐，最终行动由角色选择。评分及单次掷骰威胁的范围见[玩法分析设计](../design/game-analysis.md#7-飞行棋规则分析)。

行动等待较长时，在管理页查看角色活动任务和反思任务。历史需要摘要时，原行动等待摘要完成；反思模型输出未通过审核时，可以通过管理页重启失败的反思任务。模型服务故障、输入容量和审核失败分别记录实际错误，任务恢复不会代替玩家修改棋盘或产生随机结果。

## 本轮验收记录

实施顺序与提交要求见[06 号计划第 8 节](../../../docs/06-activity-implementation-plan.md#8-联合验收与开发交接)。

- 规则与分析器针对性检查 23 项通过；两种模型配置均已完成两个角色的实际行动选择。
- 后端非模型全量回归 441 项通过；随后处理位置与表达意图修复的 42 项活动检查通过，其中包含两项新增规则检查。
- 源码目录外的安装检查已验证启动、迁移 35、HTTP、SSE、Rapfi、冻结输入与共同记忆预算，无模型调用。
- 普通配置完成真实前端整局、赛后交流、结束活动和普通聊天回忆。本地配置完成 436 次正式动作，停在版本 440；用户要求停止测试，该局未产生胜负，也未执行局后交流、正式关闭及整局摘要检查。

验收使用独立临时数据库。普通配置保留排查、服务重启与恢复的全部记录，实际请求与消耗包含失败调用。两局的随机骰点及游戏经过各自独立，性能记录反映各自实际运行条件。

### 实际调用与延迟

| 记录 | 普通配置 | 本地决策配置，未完成整局 |
|---|---:|---:|
| 已开始的真实模型请求 | 356 | 644 |
| 已报告输入 token，含缓存读取 | 4,093,557 | 11,556,179 |
| 已报告输出 token | 111,979 | 131,009 |
| 已报告合计 token | 4,205,536 | 11,687,188 |
| 非自动判断任务完成 P50／P95 | 7.03／18.09 秒 | 24.17／38.39 秒 |
| 角色表达到达 P50／P95 | 7.85／30.03 秒 | 32.54／67.80 秒 |

token 为供应商报告的文本计量单位；P50 为中位数，P95 为 95% 分位数。请求统计包含重试、摘要、群聊和排查；停止时尚未返回的请求也计入开始数量。未返回用量的调用无法计入 token 合计，费用没有取得供应商账单。本地配置的已报告合计中，7,155,654 来自 StartLux，其余来自普通模型。本批两局经过、动作数和恢复次数不同，不能据此断定哪种配置更省成本。

判断任务延迟从登记至完成，包含行动、回应和观察判断；表达到达从原活动任务登记至消息正式保存，包含等待、模型调用与保存。上述记录保留了故障、暂停和人工恢复造成的实际影响。

### 已确认的体验限制

普通配置完成 339 次正式动作，黄方正常归航获胜。界面完成赛后提问、结束活动和新群聊回忆；两个角色均登记了包含赛后材料的整局摘要。两个普通群聊的约定能够延续到局内交流。

本批两个角色采用同一个小槿模板。实际文字出现双方抢认同一获胜身份、复述对方经历和相似接话；整局摘要也混淆角色颜色，并保留过多逐步移动细节。程序流程和文字质量分别记录：行动服务依据正式身份执行，人物与摘要文字质量仍需改进。本批没有完成不同人设、关系及承诺的受控比较。

模型格式错误仍会造成有限重试和最终失败。普通配置保留 7 个修复前失败的判断任务；本地配置保留 2 个修复前容量失败、10 个表达失败及 1 个反思失败。失败的摘要曾通过正式管理入口人工重启，两局均经历服务重启，均未作为无中断运行通过的证据。现有检查支持本轮代码交付，完整人物质量与本地整局验收保留未完成状态。

输入与恢复修复包括：工具结果按当前剩余容量返回摘录；输出格式错误提供具体字段反馈；局内提示省略无关处理进度；当前消息与历史共同进入摘要时仍能恢复判断；简单记忆模式按原规则跳过后续关系、状态反思的审核和执行。本地直接选择按实际读取来源推进处理位置，避免旧消息无限累积；逐条文字理解与内心继续只来自实际生成。表达更新意图时引用正式原输入，避免把独立表达快照编号写入输入外键。

### 复用验收

真实整局脚本为 `frontend/e2e/aeroplane-activity.spec.ts`。启动独立后端和前端后，设置 `E2E_ACTIVITY_ACCEPTANCE=1`、`E2E_API_BASE_URL` 和 `E2E_BASE_URL`，在前端目录运行 `npx playwright test e2e/aeroplane-activity.spec.ts --project=chrome`。脚本通过正式接口准备角色，通过实际页面创建、邀请、开始、行动、发言和结束；正常骰点决定胜负。该流程会产生真实模型消耗，日常针对性检查无需启用。

本地证据保存在 `server/data/verification/aeroplane-acceptance/`；规则与短流程报告位于 `server/data/verification/aeroplane-*.xml`。原始材料包含角色私有输入，供本地诊断使用。
