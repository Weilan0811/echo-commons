# 活动任务与角色行动

更新日期：2026-11-01。角色已经能够在正式五子棋对局中自动行动，并通过[局内协调](activity-coordination.md)处理接话。活动输入和意图规则见[活动上下文](activity-context.md)，分析器扩展见[玩法分析](game-analysis.md)。正式发布表达及经历整理继续按[实施计划](../../../docs/06-activity-implementation-plan.md)的后续单元接入。

## 从行动机会到正式落子

`ActivityCoordinator` 从持久参与记录发现进行中的真实机会，按游戏、参与区间和机会保存唯一 `activity_tasks`。重复扫描返回原任务。任务固定原会话成员、观察版本、输入编号、游戏请求编号和模型方式；暂停、重试和重启保留这些身份。

| 实际情况 | 执行方式 |
|---|---|
| 游戏公开机会只有一个合法动作 | `automatic`：直接使用这个动作，不准备模型输入、不生成模型结果或内心 |
| 多个合法动作，决策配置关闭 | `ordinary`：普通角色模型返回有类型的动作、理解、内心、完整意图列表及可选表达 |
| 多个合法动作，决策配置开启 | `decision`：本地模型选择分析候选、表达意愿、意图是否需要修改及原意图的去留 |
| 本地模型选择进一步理解 | `decision_then_ordinary`：使用同一冻结输入调用普通角色模型，形成完整提议 |

判断单选使用游戏提供的合法动作数量。分析器只推荐一个候选时，多选机会仍然调用模型。多选只安排已有分析器支持的玩法；注册其他分析器后复用相同队列和提交路径。

本地问题共用人物、局势、聊天和当前意图，各问题独立判断。表达和意图问题不假定已知道动作问题的答案。新增或改写意图需要开放理解；本地模型可以保留或结束既有意图。对打趣、挑衅、求情和约定的理解由角色根据语境与自身态度决定，程序不按话术匹配固定落子策略。

## 输入、阶段结果与来源

任务领取后通过 `ActivityContext.prepare_turn` 固定输入，分析和模型调用均在写事务之外。普通模型使用 `activity_{game_type}_turn:v1`，本地选项转换使用 `activity_{game_type}_selection:v1`；游戏规则注册定义提供正式动作类型。

普通输出中的 `understanding.messages` 必须恰好覆盖本次待处理消息，`event_ids` 必须恰好覆盖本次可见事件。已经理解的历史消息继续提供背景，不重复登记为新消息。表达核查引用使用明确来源编号，理解和意图引用使用真实消息编号。

任务分别保存完整本地请求与响应、最近普通调用及结果，以及通过活动审核的完整 `prepared_json`。只有完整保存的阶段可以恢复使用；保存失败的未完成阶段按原输入有限重试。普通路径保存实际理解后推进处理位置；本地直接选择完成审核及提交后，同样登记已读取的冻结来源，其选择记录构成实际处理依据，逐条文字理解与内心保持空值。自动步骤保留待处理交流来源。恢复准备时可由已提交的选择结果补齐尚未推进的位置，已推进的位置保持原值。

## 事务与重复执行

`ActivityCommit` 在一个短写事务内完成：

1. 检查租约的拥有者、尝试次数、代次和期限，复核社群、角色资格、原参与区间、会话成员、游戏版本和机会。
2. 读取该任务已经保存的完整决定，检查动作属于原机会的合法动作。
3. 保存真实理解和局内意图，通过游戏公开的 `submit_action` 执行动作。
4. 保存 `activity_results`、真实游戏回执、表达安排及实际角色内心，完成任务。

任意数据库写入失败，动作、处理位置、意图、内心及结果一起回滚。已经生成并保存的决定保留在任务中，重试提交复用它。游戏请求编号固定；完成任务重复提交直接返回原结果与回执。

角色内心只来自实际 `understanding.thought`，写入 `thoughts.activity_result_id`。原聊天内心继续使用 `thoughts.result_id`；数据库要求二者恰好一个有值。本地选项判断没有生成角色内心，供应商内部推理也不写成角色内心。经历消费者在后续单元接入活动来源。

## 生命周期与恢复

队列注册为 `activity_turn`，复用执行分发器、心跳、共享模型额度、失败分类和次数限制。`activities-*` 后台工作与普通会话、反思共用模型并发预算。

- 社群暂停或角色暂时不可用：停止有效租约，保存输入、决定和当前意图；恢复资格后继续原任务。
- 机会或版本改变：取消旧任务，拒绝迟到结果；下一次扫描根据新机会安排独立任务。
- 游戏结算、取消、角色退出或会话归档：清除该范围的当前工作记忆，结束相关行动任务。历史冻结输入和正式结果保留诊断依据。
- 进程重启：从持久记录发现任务；过期租约按共同恢复策略处理，新领取使用新代次。
- 本地服务故障：按真实调用失败有限重试。开启配置下的故障不改变任务已经确定的模型方式。

游戏变化、社群状态和会话生命周期通过所属业务事务通知活动模块；扫描、续租和启动恢复也检查持久状态。

社群清理同时检查持久状态和运行中的任务调用。活动任务暂停后，仍在运行的执行器会阻止清理；调用结束后才允许删除所属数据。

## 表达安排与管理查询

行动结果保存完整调用材料和真实回执。表达状态为 `silent`（保持安静）、`pending_generation`（等待生成正文）或 `pending_review`（已有正文，等待审核）。正式发布由独立表达阶段完成，发布进度与原决定分别保存；生成、审核、social 完成通知及恢复见[局内表达](activity-expression.md)。

管理入口按社群和角色限定范围：

- `GET /internal/communities/{community_id}/characters/{character_id}/activity-tasks`：分页概要。
- `GET /internal/communities/{community_id}/characters/{character_id}/activity-tasks/{task_id}`：任务、冻结输入、完整阶段结果、回执、表达进度、当前工作记忆和执行历史。

列表复用共同管理游标，私人内容只在详情中读取；跨角色详情返回 404。字段见[管理接口](../reference/management-api.md)与[数据库参考](../reference/database-schema.md)。

## 使用与验证

安装 Rapfi，配置普通模型凭据，启动后台工作并将社群设为运行状态。玩家邀请已经就绪的角色进入对局并开始游戏，轮到角色时后台自动处理。普通生成模型路由为 `activity_turn`，没有单独指定时沿用默认档位；本地选择使用现有 `[decision]` 配置。两种配置都读取同一活动上下文。

`test_activity_actions.py` 使用真实 SQLite、游戏服务和 Rapfi 检查自动行动、幂等、旧租约、旧机会、暂停恢复、实际期限、取消与意图清除。`test_activity_models.py` 显式选择 `-m model`，使用真实普通供应商和本地 StartLux，覆盖落子、进一步理解、完整对局、同局面语境变化、真实事务失败及重启恢复。
